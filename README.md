# Finance Task Studio

A workspace for building the **trap ledger** of a derivative finance task: the traps that make one required conclusion turn on reading the documents (the deciding rule, the confident decoy built on the wrong terms, any superseded version, the room at the bright line, and the right and wrong figures), each anchored to source evidence and recomputed economics, then carried into lint-checked grader guidance and an upload pack. A project from earlier work keeps its **failure-mode set** (three historical modes from a failure-mode library plus two net-new modes); the project guide has no failure-mode library, so new projects start as a trap ledger. It reads task packages (ZIP, XLSX, DOCX, CSV, text) in the browser, proposes source-linked candidate roots, and exports the solver draft, the private evaluator draft, the failure-mode records, and the persistent working document separately.

It comes in two editions:

| Edition | How you run it | Agents | Network |
|---|---|---|---|
| **Local agents** (primary) | `npm start`, or `Start Finance Task Studio.command` on macOS. A companion server listens on `127.0.0.1`. | Yes, after you approve each round. | The page talks only to its own companion on `127.0.0.1`. The agent runtime (the `claude` CLI) talks to Anthropic. |
| **Offline** | Open `Finance_Task_Studio.html` from disk. | No. The Agents page says so. | None. The page's content security policy is `connect-src 'none'`, and no model is called. |

Private task evidence never ships with the app. A bundled task audit is kept locally as a *private evidence module* (see below), loaded through a file picker, and ignored by git.

## What the agents do

The Agents page runs the loop used to harden a task by hand, on your machine, with Claude Code (`claude -p`):

- **Blind pilots.** Up to 5 agents per round solve the task from the solver files you approve and the prompt you write, after a short fixed text that the companion puts in front of the prompt (the approval dialog shows it word for word). Each runs in its own folder. No grader file, gold, fingerprint, evidence module, log, or earlier output is copied into that folder.
- **Audit.** Every tool call a pilot makes is checked. Any read or write to a path outside the pilot's folder, any search of the whole computer for files (`mdfind`, `locate` and the like), any reach for this computer over the network, and any start of the agent runtime (`claude`) marks the run `DISCARDED`: it stays on disk and visible, and is excluded from classification and export counts. The audit reads commands as text and does not run anything; see *What the audit cannot see* below.
- **Classification.** Answers are compared with a gold and with fingerprints of expected wrong answers that you freeze **before** launch. The app suggests a verdict by matching figures (with your tolerances) and tokens in the final answer. Output files are only searched to say where a figure also appears. A decision keyword does not count when *not*, *no*, *never*, *cannot* or a word ending in *n't* comes within three words before it in the same clause, or when *avoid* comes directly before it; a comma, colon, semicolon, full stop, `!`, `?`, a dash with spaces around it or a new line ends the clause. A gold figure written as a bare single digit (3, -4; not 3.0, 2.0x or 5%) is weak evidence and cannot make a match alone, and a reason sentence explains anything left uncounted. That suggestion is a heuristic. The verdict you record is the one stored and exported.
- **Simulated grader.** A tool-less agent reads the guidance text and one answer and returns a verdict and a reason, and, when it gives them, a score from 0 to 1 and item-level reasons. The answer is a pilot's final answer or a pasted reference answer (*Reference answer (paste)*): a calibration run, which should score about 0.98; below 0.95 (compared on the rounded score the page shows) the page says the guidance likely needs fixing before any pilot score means anything. A score outside 0 to 1 is read as no score, and the page says the guidance reads the reference as meeting it only when the verdict is also *meets-guidance*. The dialog offers `claude-opus-4-8` first (the writer's grading instrument); pilots keep their own model. It is a simulation and a single sample, not the evaluation's grading.
- **Author review.** A tool-less agent reads an extract of the task package loaded on Overview and writes one analysis. The dialog leaves out, by default, loaded files marked evaluator-only, run evidence or author review (one *Leave out* box covers all three) and says how many files are left out.

## Safety model

- **Approval per round.** Nothing starts without an explicit approval click for that round. The approval dialog shows the model, effort, number of pilots, how many run at once, the spending cap per pilot and for the round, tool list, working folder, packet hash, the fixed text pilots see before your prompt, and the isolation statement, and asks for three acknowledgements: shell access as you, network use by the agent runtime, and isolation by audit only. The simulated grader and the author review each ask for their own approval of a single run.
- **Cap of 5 pilots per round.** The cap is a constant in `backend/agents/constants.cjs` and is enforced on the server as well as in the page. A new round needs a new approval. By default every pilot of a round starts at once, so a round ends within one 50 minute limit; you can choose fewer at a time.
- **Spending cap per pilot.** Every agent process the Studio starts gets `--max-budget-usd`: USD 3.00 per pilot by default (0.05 to 20.00, chosen per round), 0.50 for a simulated grader or an author review. The runtime stops a pilot that reaches it, and the run details say so. **The cap is not a ceiling on everything a pilot can start.** A pilot has a shell, and the `claude` program and your sign-in stay reachable from it (they must, for the pilot itself to run). A `claude` process that a pilot starts from its shell has no cap, and its tool calls are not audited. The audit discards a run whose tool calls start the runtime (kind `runtime`: `claude` as a command or argument, `claude -p` in code or in a file the pilot writes, the runtime's own path), but only after the fact, and it cannot see a start under a name built while a command runs. The approval dialog, the settings card and the approval summary say so.
- **Pre-flight before anything starts.** Before approval (and again at launch, and before a simulated grader or author review) the companion checks that `claude --help` lists every option it will pass, reads the pilot token if you stored one, refuses an environment that would send a pilot through a gateway or rename its models (`ANTHROPIC_BASE_URL` at any host but Anthropic's, `ANTHROPIC_AUTH_TOKEN`, Bedrock, Vertex or Foundry switches, model overrides) unless the pilot token is there to replace them, and checks that `claude auth status` says it is signed in under the exact pilot environment. No check runs a model. A problem is named, by variable name and never by value, and nothing starts.
- **Pilot sign-in.** Pilots can run under a dedicated token of your own Claude subscription instead of your everyday sign-in (see "Pilot sign-in" below). The token is read from the macOS Keychain item `finance-studio-pilot-token` (or `FINANCE_STUDIO_PILOT_TOKEN`) at each pre-flight, handed only to the processes the Studio starts as `CLAUDE_CODE_OAUTH_TOKEN`, and kept out of the record: the companion blanks it out of the runtime's output before anything is parsed or written, discards a run whose tool calls read the environment (`env`, `printenv`, `/proc/*/environ`, `os.environ`, the variable names, and so on; kind `environ`) or show the token anywhere (kind `secret`), and after each run scans the whole pilot folder and the evidence copy and blanks the token out of any file that holds it. Seen live in two runs (macOS, Claude Code 2.1.287): the environment of a pilot's Bash tool did not contain the variable (`printenv` printed nothing), so a pilot's commands did not see it; the Studio does not rely on that, because the same user's processes can still read the `claude` process's environment (`ps -E`, `/proc/<pid>/environ`; the audit flags those) and a future runtime may behave differently. It cannot stop a pilot that does obtain the token from sending it away while it runs; a token that was sent away is compromised, so make a new one with `claude setup-token` and store it again.
- **Gold frozen before launch.** The server refuses to launch a round without a freeze record (hash and timestamp). Edits after launch create a new version labelled post-hoc and never overwrite the original.
- **Shell access as you.** A pilot is a Claude Code agent with Bash, Read, Write, Edit, Glob, and Grep, running with your user permissions.
- **Isolation by instruction and audit, not by an operating system sandbox.** The pilot folder is created in the operating system's temporary directory (`finance-studio-pilots/<run id>`), outside the project. It holds only the approved solver files, an empty `outputs/`, and an empty `.tmp/` that is the agent's `TMPDIR`. The runtime's own configuration folder is moved to `.tmp/claude-config` inside it (`CLAUDE_CONFIG_DIR`), so files the runtime saves for the agent stay inside the folder; your sign-in is still read where it always is, and nothing is copied. (Checked live on macOS with Claude Code 2.1.287 by `npm run smoke` stages S0 to S2: the runtime reports the moved folder, signs in there with the pilot token, and a real pilot's large tool output landed under it; see `VERIFICATION.md`.) Memory and `CLAUDE.md` files are switched off for pilots. Nothing at the operating system level stops a command from touching other files or the network. The audit finds path violations afterward and discards those runs. There is no allowance for harness paths and no setting that relaxes it. **Pilot folders are kept**: they hold copies of the packet files and the pilot's work, and they stay in the temporary directory until you delete them (the approval dialog says so). The companion checks that the folder holding them is a real directory that your account owns, makes it private (mode 0700) if it is open, and refuses a link.
- **Blind while a round runs.** A pilot can reach the companion like any program on your machine, so while any round runs the companion leaves the gold, fingerprints, prompt, approval summary, source folder, final answers and classification details out of every round answer (the page says what is hidden; the answer to a freeze keeps that round's approval summary, which elides the prompt), refuses a simulated grader or author review (their text would be on a command line a pilot can read), and the audit discards any pilot whose tool calls reach for this machine over the network (`localhost`, `127.x.y.z`, `::1`, or the companion's port). When a pilot finishes normally, anything it left running in its process group is stopped before the audit and the output snapshot, and a note says so. Known gaps, not closed yet (`docs/local-agents.md` section 16): the export answer is not withheld (fingerprint ids and your classification notes, no gold), `GET /api/status` still carries the archived adapter's state, and the routes that change a round still accept a request that carries the nonce (their answers are withheld).

### What the audit cannot see

The audit works on the text of the tool calls. It follows `cd`, variables the command sets, quoting, command substitution, here documents, `eval`, `bash -c`, `${IFS}` splitting and brace words, and it resolves symbolic links that exist. It does not execute anything, so these are **not** seen, and a run that used one can still be `CLEAN`:

- a path assembled while a command runs (a variable or command output the audit cannot see, a script that builds a path, encoded text passed to `eval` or a shell, a program started from a name built at run time);
- a directory change whose target cannot be resolved (`cd "$SOMEWHERE"`): later relative paths are then not checked, and only `..` paths are still flagged;
- anything done by a program the pilot started that the text of the call does not name;
- a `claude` process started under a name assembled while a command runs, or from a copy whose name the call does not show. Such a process runs with your sign-in and without the spending cap until it ends;
- a connection to this machine through a host name assembled at run time, the machine's own host name or LAN address, or a bare `localhost` on a line that names no network client.

Where the text shows that one of these happened, the run gets a **note** (`cwd-unresolved`, `unverifiable-command`, `unverifiable-code`, `unverifiable-input`, `unverifiable-path`). A note never discards a run. Read the notes in the run details. The audit is told the environment the pilot received, so a path held in an inherited variable (for example one that `npm start` sets) is checked when a command uses that variable by name. The environment is still passed on whole, as the design says. `npm start` adds variables that name the project folder (`INIT_CWD`, `npm_config_local_prefix`, and others), and your shell may export `OLDPWD`; if you do not want a pilot to be able to read them, start the companion with `node backend/server.cjs --open` from a shell where they are unset. `cd -` is only trusted after a `cd` in the same command, because its target is otherwise whatever the shell inherited. The work per call is capped and timed; a call that exceeds a cap fails closed and discards the run.
- **The agent runtime talks to Anthropic; the page talks only to localhost.** The solver files and prompt you approve are sent to Anthropic by the `claude` program, as are the guidance text and one answer for a simulated grader, and an extract of the loaded package text for an author review. A pipeline also sends the task, the guideline and the golden answer to its classifier, designer, graders and reviewers, and, for a new task, the reference documents in `private/references/` to its designer. The page itself makes requests only to `127.0.0.1`.
- **Nothing starts on launch.** Starting the companion, with `npm start` or the launcher, never starts a model. The launcher only asks `claude --version`.
- **No workarounds.** If `claude` cannot start (not found, not signed in, blocked by a permission policy), the run is marked `failed` with the real error text. Run the command from your own terminal instead.
- **Directional results only.** With fewer than 20 runs every count is shown as "directional only, n = k". The Runs card computes no rate, no difficulty score, and no works/fails label. The one exception is the *Pilot gate* card (see *The Agents page*), which shows a projected batch mean and a chance of a batch averaging 0.60 or lower, labelled pilot-based and directional, from instrument constants measured on the writer's own earlier tasks; it is a planning aid, not a prediction of the platform's grading. Scores in a precedent workbook you load on the Mode ideas page are values you recorded: they are shown as written and only order ideas.

## Quick start

Requires Node 22 or newer and the `claude` CLI, installed and signed in (run `claude` once in a terminal). There is nothing to install with npm.

Your first pilot:

1. `npm run setup`, once per clone. It turns on the privacy check for pushes (see *Privacy*).
2. Store the pilot token ([Pilot sign-in](#pilot-sign-in)).
3. `npm start` (below). Keep that window open and use a second terminal for the next two steps.
4. `npm run smoke`. This is stage S0 and calls no model.
5. Once, run S3 and S4: `npm run smoke -- --stage S3 --i-approve-model-calls`, then the same with `--stage S4`. Each calls a model under a small spending cap (USD 0.25 and 0.50); [Pilot sign-in](#pilot-sign-in) says what they check.
6. On the Agents page, run a first round with 1 pilot before you scale up ([The Agents page](#the-agents-page)).
7. Classify the answers, then export them.

```sh
npm start
```

This runs `node backend/server.cjs --open`. The companion listens on `127.0.0.1:47321`, prints its address, writes `LOCAL_SERVER.json` (ignored by git), and asks the system to open the page (`open` on macOS; elsewhere use the printed address). Open the **Agents** view in the sidebar. The browser keeps its saved work (the project and the Agents draft) per address, so the fixed port brings it back at the next start.

If `FINANCE_STUDIO_PORT` is unset or empty and 47321 is busy, the companion takes a free port and prints `The usual port 47321 is busy, so this start uses another address. Work saved in the browser by earlier sessions (the project and the Agents draft) will not show at this address.` A `FINANCE_STUDIO_PORT` you set, `0` included, is used as given, and if that port is busy the start fails with exit code 1. Only one companion runs per project folder. A start first claims the folder with `LOCAL_SERVER.lock`, then looks at `LOCAL_SERVER.json`. If the address in that record answers as a companion with the recorded process id, the second start prints `Finance Task Studio is already running at <url>`, opens that address when it was started with `--open` (`npm start` and the launcher do), and exits with code 0. A record is stale, and the new start replaces it, only if its process is gone, the connection to its address is refused, or the address answers as a companion with a different process id. Anything else with a live process (no answer within 5 seconds, an error, or something that is not a companion) refuses the start with exit code 1 and a message that names the process and address and gives two ways out: close that companion, or delete `LOCAL_SERVER.json` if none is running. `LOCAL_SERVER.lock` (ignored by git) holds the process id of the start that made it, is taken over when that process is dead, and is removed on exit; delete it by hand only if no companion is running. Two starts at the same moment give one companion.

The companion prints `Keep this window open while a round runs; closing it stops the companion and its pilots.` Ctrl-C, closing the window, `SIGTERM` and `SIGQUIT` cancel the running round and remove `LOCAL_SERVER.json`. When the process exits for any reason, it also sends `SIGKILL` to the process groups of pilots, simulated graders and author reviews that are still running. A `kill -9` cannot be caught, so a pilot can outlive it. The next start stops a leftover pilot only if the process leads its own group, a whole word of its command line is the recorded runtime binary (the same path or the same file name), and `ps etime` puts its start within 10 seconds of the spawn time recorded for it; otherwise nothing is killed. When it stops one, it adds `A pilot process left over from the previous companion was stopped at startup.` to that run's stderr tail, and the run still ends `failed` with the reason `interrupted`.

To use a specific `claude` binary: `CLAUDE_BIN=/path/to/claude npm start`. Detection order is `CLAUDE_BIN`, then `claude` on `PATH`, then `/opt/homebrew/bin/claude`, `/usr/local/bin/claude`, `~/.claude/local/claude`, and `~/.local/bin/claude`. Detection runs `claude --version` with a 5 second limit and nothing else.

### Pilot sign-in

Pilots load no settings (`--setting-sources ""`), so a sign-in that lives in your `~/.claude/settings.json` (for example a gateway reached through `ANTHROPIC_BASE_URL` and `ANTHROPIC_AUTH_TOKEN`) never reaches them, and the companion refuses to send a pilot through a gateway it cannot see through. Give pilots a token of your own Claude subscription instead. On macOS, store it in the Keychain from the clipboard, so that the token is never typed or pasted into the terminal. Use two Terminal windows, because copying a command would replace the token on the clipboard.

In the first window, paste this and press Enter. It empties the clipboard, waits until a whole token is copied, stores it, and empties the clipboard again:

```sh
pbcopy < /dev/null; echo "Clipboard cleared. Now copy the token in the other window..."; until pbpaste | tr -d ' \n\r\t' | grep -Eq 'sk-ant-oat01-[A-Za-z0-9_-]{80,}'; do sleep 1; done; T="$(pbpaste | tr -d ' \n\r\t' | grep -Eo 'sk-ant-oat01-[A-Za-z0-9_-]{80,}' | head -1)"; security add-generic-password -U -a "$USER" -s finance-studio-pilot-token -w "$T" && echo "Stored, length ${#T}"; unset T; pbcopy < /dev/null
```

In the second window, run `claude setup-token`. It may open a browser and ask you to paste a code back; copying that code does not trigger the first window. When it prints the token, select the whole token (all of its lines if it wraps) and press Cmd-C. The first window prints `Stored, length 108` (108 for the tokens made in testing). Then run `clear` in the second window.

To check what is stored, `security find-generic-password -s finance-studio-pilot-token -w | tr -d '\n' | wc -c` prints the length only. Thirteen means only the `sk-ant-oat01-` prefix was stored: that happens when the clipboard holds a command that contains the prefix instead of the token, so store it again with the two windows. The companion also refuses a token that short when it starts. Do not use the bare `-w` password prompt: pasted text reached it with the wrong content twice in testing, and the pre-flight cannot tell, because `claude auth status` accepts any value of the right shape (only a model call, smoke S1, proves the token). The `-U` replaces an existing Keychain item in place.

On other systems, or to override the Keychain, start the companion with `FINANCE_STUDIO_PILOT_TOKEN` set in its environment. `FINANCE_STUDIO_KEYCHAIN=off` makes the companion ignore the Keychain altogether (the tests set it). The companion prints `Pilot sign-in: …` when it starts, and the pre-flight notice in the page says where pilots sign in from. Without a token, pilots use whatever sign-in `claude` finds on its own, as before.

The token is on your screen after `claude setup-token`, so never paste terminal output into a chat, an issue or a file in this repository or `private/`. If the token was shown anywhere, run `claude setup-token` again and store the new one; making a new token does not revoke the old one, so also look for a sign-out-everywhere option in your Claude account settings.

Before your first round, `npm run smoke` checks the installed `claude` without starting a model: its version, that `claude --help` lists every option the Studio passes, where the pilot token comes from (its length, never its text), which gateway variables a pilot would inherit, and that `claude auth status` says it is signed in in the pilot environment (with the configuration folder moved into a scratch folder and the token, if any). Four further stages call a model and run only when you add `--i-approve-model-calls` (`--stage all` runs S0 to S4, with S4 after S3); see `scripts/live-smoke.cjs`: S1 (one tool-less call), S2 (one pilot through a round), S3 (one pilot told to print its token, which must end `DISCARDED` with the token in no kept file) and S4 (one pilot on `claude-haiku-5-5` at effort low, spending cap USD 0.50, that uses its Read, Write, Edit, Glob and Grep tools inside its folder and makes one Read of a canary file outside it). S4 checks that each tool call was seen in the live stream, that the calls inside the folder are clean, and that the outside read is flagged and the run `DISCARDED` (reported as INFO if the pilot declines to read the canary; the last line then reads `PASS, but outside-read detection was not exercised: run S4 again`). It saves the stream, with the token redacted and your home folder shown as `~`, under `private/live-smoke/`. Exit codes: 0 all passed, 1 a check failed, 2 a stage was refused or the options were bad, 3 nothing failed but the outside read was not exercised. On macOS with Claude Code 2.1.287 and the token in the Keychain, S0, S1 (USD 0.0059) and S2 (USD 0.0271) passed on their first run. S3 first ended with two FAIL rows (USD 0.0252) because the stage expected a leak this runtime does not allow; after the stage was corrected it passed (USD 0.0199). Its rows were rewritten again since, so run S3 once more after updating. On 2026-10-23 S4 passed on the Mac: the audit read live Read, Write, Edit, Glob and Grep calls and discarded the run for the Read outside the folder. In the same session the S3 pilot refused to read its token, which S3 now reports as not exercised (exit code 3) rather than a failure. Not yet seen live: a pilot that reaches its spending cap, and a prompt delivered on stdin.

On macOS you can double-click **Start Finance Task Studio.command** instead. It looks for Node in `/opt/homebrew/bin`, `/usr/local/bin`, and on `PATH` (the runtime bundled with the archived harness app is the last candidate), prints the Node version and whether `claude` was found, then starts the same server. It prints `Privacy hook not installed: run npm run setup once` when no pre-push hook is where git looks for this checkout's hooks, and only when its folder is the top of a git checkout.

## Open it

- **Finance_Task_Studio.html** is the single-file Offline edition: download it and open it in a current desktop browser. No installation, account, server, or internet connection is needed. It never runs agents.
- **index.html** is the source-folder edition for development; keep every file beside it. Served by the companion, its Agents page can run agents; opened from disk it behaves like the Offline edition.

## The Agents page

Seven cards, top to bottom, under a status strip that shows the selected round, how many pilots are done, running, waiting, failed or cancelled, the elapsed time, and any other running round (the browser tab title shows `(ended/total)` too). Launch stays disabled until the earlier steps are done. The form is kept as a draft in the browser while you work (never while a round runs; *Clear draft* empties it; a launch removes it).

A step rail on the left (a stepper across the top on narrow screens) marks each of the six cards as done, needing attention or running, says what to do next, and jumps to the card.

1. **Runtime.** Whether Claude Code was found, its version and path, and a *Check again* button.
2. **Packet.** Enter the folder that holds the solver files and press *Inspect*. Unzip the task ZIP outside the project, then paste the full path of its `filesystem` folder (in Finder, select it and press Option-Command-C). The path may carry surrounding quotes, Terminal backslash escapes or a leading `~`; your home folder itself is refused. Pilots see the ticked files under `./filesystem/` with their folder structure kept, so choose the folder that is the production `filesystem` folder itself (the page warns when the folder you chose already contains one). Regular files only (no symlinks, depth up to 4, up to 150 files, up to 100 MB; a file name with a control character is listed but cannot be used). Files that look like grading material are excluded by default, with the reason shown: anything under a `grader(s)`, `grading`, `evaluator(s)`, `reference(s)`, `answer(s)` or `private` folder (also inside `gaf/`), and, outside a `gaf/` folder, paths with a whole grading word in a folder or file name (guideline, guidance, grading, grader, rubric, solution, expected, answer, golden, gold, reference, memo, evaluator, fingerprint, attestation, private, and their plurals; two-part run-together names such as `answerkey` too, but not longer ones such as `answerkeyfinal`). Evidence of earlier runs (`trajectory`, `run 03`, `run_log`, `pilot run`) and review or audit notes (`review`, `audit`, `candidate`, but not `audit committee` or `credit review`) are excluded too. Words count only whole, so `Goldman_Comps.xlsx` and `Cash_Runway_Model.xlsx` are sources. Guideline, guidelines and guidance are softer: they withhold a plain-text or markdown file, a name with no other content word (`Guidelines.pdf`) and a name beside another grading word (`Grader_Guidelines.txt`), but not a named Office or PDF document (`Currency_Overlay_Guidelines_ScheduleC.docx`, `Revenue_Guidance.pdf`). Some ordinary finance names are still withheld by this rule on purpose (for example `Expected_Returns.xlsx`); each shows its reason and can be overridden. **Inside a `gaf/` folder only the folder names above withhold a file; grading words in the file name do not**, because `gaf/` is what the production solver sees, so `gaf/Golden_Response.docx` is included by default and goes to every pilot while the gaf toggle is on. The packet table marks such a file *Check: grading word in a gaf/ file*; untick it, or turn the gaf toggle off, if pilots should not see it. Including an excluded file needs an explicit per-file override, which is recorded in the round. The page and the companion use the same rule (`classifyPath` in `package-engine.js`). Folders inside the project or under `private/` are refused. This refusal, and the ones for your home folder and for earlier pilot folders, run on the real folder that the text resolves to after it is cleaned once; that folder is what the round stores. Write the pilot prompt in the box (word count shown against the project limit). Pilots also see a short fixed text before it: it says the materials are in `./filesystem`, that files go to `./outputs`, that the answer goes in the final message, and that a missing file is to be reported in the answer, not searched for elsewhere on the computer. The Round card and the approval dialog show it word for word under *Pilots also see this fixed text before your prompt*. The `gaf/` toggle (on by default) records whether that folder is part of what the solver sees; it matches production only if the production solver sees it. A file counts as a gaf file when `gaf` is a word in its path with a slash, an underscore, a space or a dash (or the start) before it and one of those, a dot (or the end) after it: `gaf/x.csv`, `gaf-hedge.csv`, `GAF_notes.txt` count; `gafHedge.csv`, `gaf2024.xlsx` and `x.gaf.csv` do not, and are sources. The role column, the toggle, the page and the companion all use this one rule (`GAF_PATTERN` in `package-engine.js`), so every file shown as a gaf template is hidden when the toggle is off. The choice is shown in the approval dialog and recorded in the round and in every exported record.
3. **Settings.** Model, effort, the number of pilots (1 to 5, default 5), how many run at once (all by default), and the spending cap per pilot, with the round maximum for the pilot processes the Studio starts (the card says what the cap does not cover, see *Safety model*). Changing one after freezing marks the freeze stale.
4. **Freeze.** Enter the gold decision phrase, the gold figures with tolerances, and the fingerprints of expected wrong answers (id, label, tokens or figures). A figure takes the same forms as the companion reads: `12450`, `12,450`, `$12,450`, `(1,200)` for -1,200, `3.2x` or `12%` (kept as 12, not 0.12). A figure carried into the next round is typed back as plain digits (no exponent), so a carried `1e-7` freezes without retyping. The tolerance field is labelled "Tolerance (absolute, same unit as the value)". An optional **ship bar** (at least W wrong of N completed runs, whole numbers up to 20; 5 of 6 is suggested) is set here, before the first run, and frozen with the gold: it is covered by the content hash only when it is set, so a freeze without one keeps its old hash, and a refreeze cannot change it. *Start next round from this round* carries it. *Freeze gold* shows the hash, a content hash of the gold, fingerprints and any ship bar, and the timestamp.
5. **Round.** The round's settings, the fixed text pilots see before your prompt, and the shell-access and isolation statements. *Review and approve* first runs the pre-flight (a problem shows "Fix this before you approve." and *Check again*), then opens the approval dialog. It shows that fixed text word for word, the prompt and its hash, the files delivered and the files withheld, the command line with the prompt elided, and the exact text that the approval hash covers (that text includes a `Fixed prompt prefix sha256:` line, so the approval covers the fixed text too). The approval also stores the hash of the fixed text on its own: if a Studio update changed that text after you approved, the launch is refused with `APPROVAL MISMATCH: The Studio's fixed pilot text changed after this round was approved. Cancel this round, then freeze and approve it again. Nothing was started`. *Approve and launch* stays disabled until all three acknowledgements are ticked. If the launch is refused after the approval (another round is running, or Claude Code is missing), the round stays approved and the same dialog launches it once the cause is gone. *Review and approve* is disabled while Claude Code is not found.
6. **Runs.** One row per pilot with state, turns, tool calls, resolved model, audit badge, and elapsed time. *Details* opens the final answer, outputs, and any violations with the offending call. A failed run explains itself: the reason in words, the runtime's own message, and the command (prompt elided) to run from your terminal. Classify each `CLEAN` run (suggested verdict, your verdict, fingerprint chips, note). The chips include fingerprints that a post-hoc freeze added. Under the table: *Start next round from this round* (for a frozen round that is running or has ended: finished, failed or cancelled; disabled while any round runs) makes a new draft with the same files, prompt, settings, gold and fingerprints, to edit, freeze and approve again; the freeze then says whether gold and fingerprints changed. Then *Simulated grader* and *Author review* (both disabled while any round runs), and **Export**, which adds run-evidence records to the project's experiments (after a confirmation) or downloads the round JSON. `DISCARDED` runs are exported only in a separate list.
7. **Pilot gate (pilot-based).** It pools the rounds of one design (same packet hash, prompt hash, frozen gold, gaf setting, model and effort) and counts the completed `CLEAN` runs that carry your verdict: *Lands on a frozen fingerprint* is a wrong run, *Matches the frozen gold* a correct one, and *Unclear* is counted apart and left out. It shows wrong and correct of the total; the correct verdicts in a row, by end time, with the stop rule *Three correct in a row: stop testing this design*; whether the frozen ship bar is met (at least N runs, and wrong of total at least W of N); a projected batch mean range; and the chance that a ten-run batch averages 0.60 or lower. The projection uses instrument constants measured on the writer's own earlier tasks (a correct run scores 0.82 to 0.90, a wrong run 0.13 to 0.32): the range runs from (correct × 0.82 + wrong × 0.13) to (correct × 0.90 + wrong × 0.32), divided by the total, and the chance is P(C ≤ 5) where C, the correct runs in a batch of ten, is beta-binomial(10, correct + 1, wrong + 1). It says that the platform's gate is at least six completed runs averaging 0.60 or lower and that the instrument matched a platform batch once and is untested elsewhere. Numbers are decimals; it shows only *Waiting for the round to end.* while any round runs.

## Pipeline

The **Pipeline** page (top of the sidebar, Local agents edition only) runs a whole design loop from one task link or one task folder. You approve it once, with a total spending cap, and it stops by itself.

It has two modes. **New task from the world files** is the default: the designer starts from the world files and builds a task of its own, and it never sees the prompt, guideline or golden answer of an earlier task. **Harden the existing task** is the older mode: the designer takes the task as it is and makes it harder. The steps below describe the older mode; [the new mode](#a-new-task-from-the-world-files) differs in the design step, the checks before the pilots and the rule for passing.

1. **Import.** Paste the task link, or the full path of a folder that holds the task's files. The [link loader](#the-link-loader) opens the page in its own Chrome window, waits for you to sign in, turns on the option that shows all files, and downloads every file on the page: the world files as well as the files added for the task. Any file it could not download is listed as skipped. When the download ends, the run waits on a *Check the files* card. It shows the file list, the skipped files and any notes about what the loader could not cover, such as pages it did not follow or frames it could not read. Press Continue if every file is there; otherwise stop and import from a folder. A folder import skips this step.
2. **Classify.** One tool-less run sorts the import into the prompt, the grader guideline, the golden answer, the world files and the task files. Classification fails closed:
   - A file whose name, group or label names an answer, a solution, a rubric, a guideline or grading is withheld from the pilots, whatever the model said.
   - A file that holds a long passage of the guideline or the golden answer is withheld too.
   - The run stops before any design when a world or task file would be withheld. Tick *Start even if a world or task file has to be withheld* only if the pilots can do without it.
3. **Design.** The trap designer (an agent in its own working folder) writes the hardest traps it can find, a revised prompt, a revised guideline and a golden answer. It is told to prefer new files and to edit an existing world file only when a trap cannot work without the edit; originals are never changed, and an edit that removes more than a fifth of a file is refused. Before any pilot runs, the design must pass these checks:
   - The golden answer must score at least 0.90 against its own guideline.
   - A fairness review must find no guideline item that a solver could not know from the prompt and the files.
   - No figure or decision from the golden answer may appear in the prompt or in a new file's name.
   - The new and edited files are scanned for passages of the guideline and the golden answer.

   A design that fails gets one repair turn, then counts as a redesign.
4. **Screen.** Two blind pilots run on the design, and each is graded as soon as its run ends. The screen passes only if both score below **0.40** with the simulated grader. As soon as one pilot has a usable score of 0.40 or more, the other pilot is cancelled, the screen fails and the designer is sent back to harden the task.
5. **Test.** Five blind pilots, which run **only when both screen pilots scored below 0.40**. The test passes if at least four of the five score below 0.45. It ends as soon as the result is decided: when four pilots are below 0.45 (passed), or when two are at or above it (four of five can no longer be reached). Pilots that have not ended are cancelled and not graded, are marked *stopped early* and get no replacement, and what they spent so far is still counted.

   A score close to a bar is graded twice and averaged before it counts toward a decision: from 0.35 to 0.45 in the screen, from 0.40 to 0.50 in the test. A pilot with no usable score gets one replacement round, unless the result is already decided.
6. **Redesign.** A failed screen, a failed test or a rejected design sends the designer back with the results, up to three redesigns.

The run ends when a design passes the test, after the third redesign, when the next step would pass the total cap, or when you press *Stop*. Before each step it reserves that step's worst case plus 15% headroom. The total cap defaults to USD 60 and may be up to USD 200. The page shows what one full attempt (design, screen and test) can cost at most with the caps you chose. A lower total cap is allowed; the run then may stop at the cap before the test. While a pipeline runs, the Agents page cannot launch a round or use the simulated grader or the author review.

While any round runs, the page withholds the prompt, the guideline, the golden answer, the trap titles and the edited files' names, sizes and hashes. *Export* (refused while a round runs) downloads `<label>_pipeline_PRIVATE.zip` with the exported design. Keep it private: it holds the guideline and the golden answer. The pipeline's working files stay under `private/pipelines/`. The pilots' packet is the only copy under the system temporary folder, and it is removed when the run ends.

### A new task from the world files

Choose **New task from the world files** on the start form. It differs from the older mode in what the designer gets, how the task is described, how it is checked and how it passes.

**What the designer gets.** The world files and the task files the pilots would get, the idea catalog, and your reference documents when you have some. It gets no prompt, guideline or golden answer from an earlier task, and none is needed. Files that look like answers, rubrics or guidelines stay withheld from the designer and the pilots whatever the classifier said. If one of them is real evidence (a parent answer file, say), list its name in *Keep these files as world inputs*. The Check the files card then shows it with a warning, and it goes to the designer and the pilots as a world file. Nothing else overrides the withholding; ticking *Start even if a world or task file has to be withheld* only silences the warning that a file is missing.

**Reference documents.** Put them in `private/references/` (it is ignored by git and never committed) or name another folder. Markdown, text, PDF, Word, Excel, CSV and JSON files are accepted: at most 20 files and 8 MB in all, regular files only, no links. The start form shows how many were found and their names, never what is in them. When the folder breaks a rule, the form lists each problem as a short plain sentence (the file or the folder and the reason, up to 20) next to the count. Only the designer reads them (it can open PDFs). They are sent to Anthropic like the rest of the task, and the fourth acknowledgement says so. No passage of them may appear in a file the pilots get: the same 80-character check that guards the guideline runs over the prompt and over every new or edited file of any kind (text, Word, Excel, slides, RTF, a file with no extension), and it covers the whole 8 MB of the folder. A byte for byte copy of a reference document is refused as well, so a PDF cannot be slipped in under another name; a world or task file of your own that is byte for byte a reference is withheld with a warning at the start, before anything is paid for (name it under *Keep these files as world files (optional)* to keep it). Text that a world file and a reference share is not a leak when the designer edits that world file: only a passage that no original file holds is. What the check cannot look at is listed as unscanned: a file with no readable text (a PDF) and any file or tail of a file that the scan did not reach. Pilots, the blind reviewer and the graders never see the references. Without any reference documents the designer still works from its idea catalog.

**The brief.** Besides the task, the designer writes `brief.json`: the kind of workflow it picked and why, the decision the task asks for, which file is the authority, and for each trap (at most three, one primary) the rule it rests on, the right path and the tempting wrong one, why the wrong one is tempting, what it would cost, and the strongest alternative answer with the clause that rules it out. The harness checks the brief without a model. The wrong path has to change a required conclusion or a required calculation, so a different action counts, and arithmetic that moves while the action stays the same does not. With more than one trap there must be controls for the baseline, each wrong path alone and all of them together, each different from the baseline. The governing clause and the clause against the strongest alternative must appear word for word in the packet or the prompt, and a quote of a clause must be a whole sentence or at least 40 characters, held to the file it names (a wrong file name fails the quote; the rest of the packet is not searched). The brief may also give the day the decision is taken (`decision.decisionDate`, an ISO date); the application check then holds the reviewers to that day. A failure goes through the repair turn and then rejects the attempt.

**Fairness and difficulty are two results.** Fairness is decided first, and a pilot's score never decides it. Difficulty is the screen and the test.

Before any pilot runs, every design faces these checks, all mandatory:

1. **The answer set.** The golden answer and every permitted alternative are graded against the guideline. The golden answer needs 0.90 and each alternative 0.85. Each answer is graded twice; if the two grades fall on either side of the threshold a third grade is taken and the majority decides, and the answer is shown as unstable with all its grades. A grade that comes back empty is asked for once more, and a second empty one fails the check. An answer below its threshold rejects the attempt as a defect of the guideline or the golden answer.
2. **The blind review.** A reader gets a copy of the pilot packet and the revised prompt, with the Read, Glob and Grep tools, and nothing else: no guideline, golden answer, brief or reference. It says which answer the files support, which document governs and why, the strongest different answer, and any words in any file that say a document is withdrawn or replaced. Its Read tool refuses Word, Excel, slide and RTF files, so the harness writes a plain text rendering of each into a folder next to the packet copy (never into the pilots' packet) and tells the reader which they are; PDFs and pictures it opens itself. A rendering shows the file as it says it: a tracked deletion as `[deleted: ...]`, a comment, a header, a footer, a note or a master slide labelled, every sheet of a workbook under `Sheet: <name>` with its cells in columns (an empty cell kept, a date as a date, a formula with no stored value as `[formula: ...]`), the dashes, quotes and cells of an RTF file as the characters they stand for. A rendering that is not the whole file (a formula with no value, a file that was cut) is marked partial. The reader's own record is looked at: a review in which it opened no file of the packet, or did not open a PDF or a picture, is marked partial and says which. Every other review is given the text the harness takes from the files (the parts of an Office file where a status is written too: headers and footers, comments, notes, sheet names and properties). A PDF or a picture has no text for those reviews: it is listed as not scanned, and a notice that the blind reader quotes from one is a passage the application check must answer. Because the harness has no text of a PDF, a clause cannot be quoted from one: a task whose governing document exists only as a PDF cannot pass (the brief's quotes are not found), so give the governing document as text, Word or Excel as well. A file nobody can read (an old binary Office file, an archive) stops the start before anything is paid for; with *Start even if a world or task file has to be withheld* ticked the review goes on, names the file, and its result is marked partial.
3. **The reveal.** A tool-less call compares that reading with the guideline, the golden answer and the brief. It names the strongest alternative, quotes the file for it and against it, and says what kind of objection it is and what to do about it. The harness looks for each quote itself.
4. **The application check.** Finding a quoted clause in a file only shows that it exists. For every alternative that a clause is said to exclude, and for the rule and the strongest alternative of every trap in the brief (not only the primary one), a tool-less call must show that the clause covers this decision, is in force on the decision date, has not been superseded, and rules the alternative out by its words. The harness compares the dates itself, and each date has to stand in a quote of the file (the decision date is the brief's own when it gives one). A document that sits under a higher one needs a known relation, the higher document has to be another file of the packet, and a sentence that links the two by name has to say so, or the check fails. The decision date has to stand in a quote of the files even when the brief states it, and a quote that holds several dates gives as the effective date only the one the sentence says takes effect. The harness looks for supersession language near the clause (replaced, amended, withdrawn, revoked, expired and the like, beside the clause's file name or title, its section or first words, or the heading above it, and anywhere in a file whose name carries the clause file's name) and lists every passage, whole; a file it could not read at all is listed as not scanned and disclosed to you. A passage nobody addressed, or one that changes the clause, fails the check, and so does an answer of "yes" and of "no" for the same passage. At most 40 passages are listed, the strongest wording first, and the weaker ones are not dropped: one entry for each file that has some is put to the reviewer with their number and the first of them, and has to be answered too. Words that the blind reader quoted as a notice from any file are put to the reviewer as well, in a file with text as in a PDF. The effective date has to stand in a quote of the clause's own document, in a sentence that says it takes effect (the cue nearest the date counts, "in force until" and "ineffective" do not), and a quote that stops in the middle of a number or a word is not a quote. The reviewers see the packet whole when it fits; otherwise the clause's file, the authority file, the task's prompt, the evidence files and the files that hold supersession wording come first and in full, the other files share a fifth of the room whatever their number, a file that is cut says so, and a quote from the part that was not shown does not count.

What the reviews find decides what happens next. An alternative the packet allows is not a rejection, but saying that the guideline covers it settles nothing either: it is settled only when the design has a written answer for that very alternative and the guideline grades that answer at 0.85 or more; a graded answer for some other alternative does not count. The reviewer names the declared alternative by its id (the name of its answer file without the folder and the extension: `alt-1`), and the harness holds the two to each other: the figures of the reviewer's alternative and of the declared one agree, with their units, and so do the kinds of their first verbs, so "postpone by thirty days" is "delay by 30 days" and neither is "delay by sixty days" or "do not delay". Otherwise one repair turn adds the alternative to the guideline's acceptable variation and writes its answer under `answers/`; the harness checks that what was written is the alternative the review reported, that the guideline line is there, the fixed answers are graded again against the revised guideline (the old and new grades are kept side by side), and the reveal runs once more. If the second review reports the same alternative and the revised guideline now covers it, that resolves it; if not, the attempt is rejected. A different method with the same conclusion is accepted, with a line added to the guideline when it lacks one; if that repair changes the packet, or the golden answer, the brief or the answer files, the reviews run again on what changed, and the clauses of the brief are checked again. When the blind reader reached a different answer, the alternative has to state the action or the figures of the right path. A missing requirement, a conflict between documents or evidence the pilots cannot reach is never passed as settled, whatever the review called it. When the blind reader reached a different answer, "no alternative" cannot pass and "equivalent" needs a quote; only a clause that rules the answer out, shown to apply, settles it. Anything unsettled gets one repair turn; if the packet changed, the blind review and the answer set run again. If it is still unsettled, the attempt is rejected. An answer from a review that cannot be read is asked for once more and then rejects the attempt.

**The pass rule.** A low score counts only when the harness can explain it. After each pilot is graded, every pilot below its bar gets one adjudication call with its answer, the grader's reason, the guideline, the brief and the packet text. Matching a number of the wrong path is only a hint. The call must name a class:

- **intended**: the answer adopts the intended wrong action and gives the wrong reasoning, and both are quoted from the answer; the harness finds the quotes;
- **other valid error**: the answer breaks a clause of the packet, quoted from the packet, and the action it took is quoted from the answer, word for word; the application check then asks whether the clause rules out that action;
- **permitted alternative** or **grader defect**: the answer is in fact acceptable, so the fault is in the guideline or the golden answer;
- **ambiguous**, **unsupported**: no explanation was shown;
- **tool failure**: the pilot could not read or open what it needed. It is treated as a missing pilot and gets the usual replacement, but only when the pilot's own record shows a tool call that failed (a result marked as an error) on the exact path of a file of its packet: a Read of it, or a command that names it and whose error says it could not be opened. A name that merely appears in a call, or a search that found nothing, proves nothing. The adjudicator is shown the failed calls the harness found; its word alone makes it an unsupported low.

Only the first two count. The screen passes when both pilots count, and the test when at least four of five count. A stage still ends as soon as its result is decided, and only pilots that count are counted. If a stage fails because of a permitted alternative or a grader defect, the designer gets one repair turn that may change only the guideline and the golden answer. The saved answers are then graded again, with no new pilots, and the stage is counted again. This happens once per attempt. If anything else changed, or nothing did, nothing is run again. A failure from ambiguous or unsupported lows goes to a redesign, with the answers and the graders' reasons in the feedback and a note that the traps may not be what is making the pilots fail.

**The freeze record.** Before the pilots run, and again after a guideline repair, the pipeline records what was tested: the packet, prompt, guideline, golden answer and answer set hashes, the pilots' model and effort, the grader's model and effort, and the run budget. The export lists the same, with the hash of every file it ships, so the packet that was tested can be compared byte for byte with the files you take away.

**What the isolation means.** A pilot or a reviewer is given none of the designer's information: its conversation and logs, the references, the brief, the guideline, the golden answer, the answer set and any project memory all stay out. It still gets the instructions it needs, which for a pilot are the fixed pilot text, the prompt and the packet. The Studio checks the options, the environment and the working folder of each such run (the folder is under the temporary folder, never under the project or your home folder). The check names a folder only when a value holds it as a path, so `private-notes` beside `private` is not `private`. The variables a shell sets to remember where it was (`PWD`, `OLDPWD`, `INIT_CWD`, which name the folder you started the companion from, often the private folder) are not given to the Studio's own runs, and the environment is looked at once, before anything is paid for, so a variable of yours that does name a private folder stops the start with its name, and a reader that touches a file outside its folder is discarded after the fact. What it cannot do: the audit works after the fact and is not a sandbox, every run shares your sign-in, and a process of your own account can in principle open another's files; the audit flags it when a run does.

**What it costs.** Every attempt reserves its mandatory checks before it starts: the designer and its repair turn, the blind review and the reveal twice each (a retry, or a rerun after a repair), the application checks of one review (the reveal's clause and, for each of up to three traps, its rule and its strongest alternative), two repair turns, up to three grades of each fixed answer, and one adjudication for every pilot. That is a typical worst case and not the last one: a run in which every review is retried and rerun after each of two repairs, with the answer set graded again each time, would cost more than any usable cap, so what goes beyond the reserve is paid call by call. Each call is reserved against the cap before it starts, a call the cap cannot pay for ends the run as incomplete, and nothing passes without its checks. A fault of the Studio itself in a check (a file it cannot write, say) is not reported as an internal error after the designer was paid: the attempt is rejected as incomplete, with a plain reason, and the next attempt goes on. At the default caps that is USD 23.50, or USD 27.03 with the usual headroom on top, and the total cap has to hold that before the first attempt starts. A full attempt that reaches the test at the default pilot cap of USD 3.00 needs a total cap of USD 59.80, which the default total cap of USD 60 pays for with USD 0.20 to spare (the older mode needs USD 41.40). The page shows the figure for the mode you choose. If the cap cannot pay for the checks of the first attempt, or the cap or a Stop falls inside a guideline repair before the saved answers are counted again, the run ends as incomplete, and a design whose checks did not finish is never reported as passed. A redesign that the cap cannot pay for, after an attempt whose checks finished, is a plain budget stop. Amounts are shown to the cent with half a cent rounded up. The optional switch *Also grade six diagnostic answers* adds up to USD 3.00 per attempt: the designer writes six sample answers, three that should score high and three low, and the guideline must grade each into its band. With it the least total cap is USD 63.25.

### The link loader

The link loader is part of the companion and calls no model. It drives a dedicated Chrome profile in `private/link-profile/` (Chrome or Chromium must be installed; set `FINANCE_STUDIO_CHROME` to its path if it is not found). Your everyday Chrome profile is never used.

- **Sign in.** You sign in through a plain Chrome window that the loader does not control, so the platform sees an ordinary browser. Press *Continue* on the Pipeline page once you are signed in. The loader closes that window, reopens the page under its own control and carries on. If the page still asks for a sign-in, it tries once more, then stops and suggests importing from a folder.
- **All files.** The loader looks for the option that shows all files and turns it on. If it cannot find the option, it asks you to turn it on in the Chrome window and press *Continue*. The option's label is remembered per site in `private/link-mappings.json`, so the next load turns it on by itself.
- **The whole page.** Before it lists the files, it opens collapsed sections, expanders and every tab, presses *Load more* in each tab, scrolls long lists and reads same-origin frames. It does this again after turning on the all-files option. When a time limit cuts a step short, the result says so.
- **Downloads.** The loader presses or requests only what is clearly a download: a link to a file, or a control named *Download*. It also uses tabs, expanders, *Load more* and pagers to expose content. Anything else that names a file is listed as skipped with the reason, never clicked. While the loader presses anything (a tab, *Load more*, a pager, the all-files option or a download), the browser blocks any request that could save a change. The control is noted and not pressed again. Files are saved to `private/links/<id>/files/` and the page text to `page.json`. When some files fail, the loader lists them and waits: download them yourself and use the folder import, or press *Continue* to go on without them.
- **Privacy.** The link, its query and any token are never written to a command line, a log or a stored state, and the profile's history is cleared when the load ends.

Keep the Chrome window open until the load finishes. On macOS the loader warns when the project folder is in iCloud Drive or another synced folder, because the profile holds a sign-in.

## Workflow

1. **Load the task package.** Drop the task ZIP or source files on Overview. Files are inventoried and extracted locally (formulas with saved values; PDFs stay unparsed). *Run local checks* reports saved formula errors, missing caches, hidden sheets, version clues, and prompt-wording cues, all labeled structural or heuristic.
2. **Generate candidate roots.** Three source-linked hypotheses are ranked by evidence, arithmetic, and causal independence. Same-root duplicates and non-binding variants are rejected; a candidate without a source-resolved answer is held. Ranking is not a difficulty prediction.
3. **Record the traps (Trap ledger page).** A new project is a trap ledger. Enter the task context, add one trap per root with *Add trap* (or promote a candidate root or a Mode ideas card), and write the task thesis: how the traps make one required conclusion turn on reading the documents. The *Trap-design gate* card on that page lists the rules a trap has to meet. The *Framework* select switches a project between the trap ledger and the failure-mode set; it never resets author reviews.
   *Failure-mode set (earlier projects).* Enter the task context from the task pull. Import the saved JSON of the failure-mode library pull; the app never calls the endpoint and the shared task key never enters it. The shortlist is deterministic: approved, uses above zero, numeric average score; lowest average first, then most uses, then not overused, then lowest usage share, then Mode ID. Exactly ten are shown; fewer is reported, never padded. Select exactly three by Mode ID. Add exactly two net-new modes from work you did or reviewed, or promote a candidate root or a Mode ideas card with *Add as net-new mode*; record the duplicate check against the shortlist for each. Write the thesis that ties the five together.
4. **Instantiate each trap or mode (Root design).** In a trap ledger, also name the confident decoy, any superseded version and the room at the bright line; the audit asks for a decoy, flags a decoy note that names the deciding rule (a decoy that cites the rule turns the trap into a lookup), and asks for the margin when an output has a decision threshold. Complete the record contract: triggering condition, plausible wrong approach, detection method, corrective action, expected model behavior (solve, reconcile, push back), classification (strict error or judgment-call divergence), governing rule, facts, anchors, acceptable variations, and tolerance rationale. *Scaffold blanks from mechanism* fills empty fields from the research catalog, marked as hypotheses the audit keeps flagging until edited. One causal group per root: several changed outputs are one failure.
5. **Recompute both branches (Economics).** Enter correct and wrong outputs with units, tolerances, and an optional decision threshold. The helpers (cash bridge, whole-cent ceiling, record-date dividend capacity, affine fixed point) show their equation and limits.
6. **Draft, lint, export (Review and export).** *Draft from traps* (*Draft from failure modes* in an earlier project) writes deterministic grader guidance from the records; rewrite it in your own words. The lint flags what gets guidance returned (see *Lint limits* below). Blockers are exact tokens; the rest are labeled heuristics. Exports: solver JSON/text (prompt and file manifest only), evaluator JSON/text, grader guidance text, the trap ledger (or failure-mode records), and the working document. The **Upload pack** card builds `<title>_upload_pack_PRIVATE.zip` (the title with every run of other characters made `_`) in the card layout of the platform's task form: `1.2_prompt.txt`, `1.3_new_input_files/`, `1.4_answer_file_ResponseFiles/`, `1.4_grader_guidelines_ResponseText.txt` (the cleaned guidance), `README_UPLOAD.txt` with card-by-card steps, and `manifest_sha256.txt`. Choose the new input files and the answer files last, because re-rendering the page clears the pickers. Files are copied byte for byte and their properties are not rewritten, so scrub properties first and pilot on the same bytes. It refuses a missing prompt, guidance or answer file, a space in a file name, a non-Office answer file, a gaf file and duplicate names, and lists warnings (answer-file naming, guidance that does not name the answer file, a file name in the prompt). It runs in the browser in both editions. The zip holds the answer file: keep it private.
7. **Test the design (Agents page, Local agents edition).** Freeze the gold with a ship bar, run a blind pilot round on the solver package (the approved files and your prompt, which every pilot reads after a short fixed text), classify the answers against the frozen gold, read the *Pilot gate*, and add the evidence to the project's experiments. Calibrate the guidance first with the simulated grader on the reference answer.
8. **Record actual runs.** Observed results need a run ID, exact versions, score scale, evidence location, and the modes actually observed. Planned modes are never reused as observed evidence.

## Mode ideas

**Mode ideas** (Package analysis, after the candidate roots page) suggests failure-mode ideas for a derivative task. They come from a catalog of 44 generic mechanisms (written for this tool, with no task or workbook content) and a pure local model. The page makes no request of any kind and calls no model, so it works in both editions.

- **A new task.** Enter the workflow and a short description, then *Generate ideas*. Each card says why the correct reading is unique and the wrong one tempting, and how to build the idea into a task in a few concrete moves. With no package files to point at, an idea is held for missing evidence unless your description already uses the wording it needs.
- **An existing task.** With a package loaded, the page reads only the solver-visible files (source, template and proposal roles; never evaluator, run-evidence or audit files) and cites the document, locator and quote where an idea could attach, each re-checked against the package. It compares every idea with the modes already in the project: an idea that shares a causal group or wording with a current mode is marked as overlapping a current mode or as already covered, and listed last.
- **A precedent workbook (optional).** *Load precedent workbook* reads a CSV you export from your own records, one row per earlier failure mode: workflow, name, what was built, how a solver went wrong, and a recorded score (header names are matched loosely; see `docs/local-agents.md` section 17; up to 5 MB and 5,000 rows). It is read in this browser from the file you pick and kept in the page's memory for the session. It is never fetched, stored, sent anywhere, or written into the project JSON, a workspace or any export; removing the workbook, or a reload, forgets it. Each idea then shows its closest precedents, at most three, with the recorded score exactly as written in your file. Keep the file outside the repository, or under `private/`.
- **Order.** Ideas are grouped by status (reviewable hypotheses, then holds, then overlaps and ideas already covered). With a workbook loaded, each group is ordered by the lowest recorded score among an idea's closest precedents first; an idea with no readable score follows those with one; ties go to the idea with more precedents, then lead ideas, then a stable id. The page says so once, in a footnote: "Ordered by the lowest recorded score among each idea's closest precedents, as recorded in your workbook (lower is the more complex task, in your workbook's reading). Finance Task Studio did not compute these scores and they do not predict a result on this task." Scores are used for this order only. None is rounded, rescaled, averaged, shown as a percentage or turned into a rate or a prediction, and an idea carries no score of its own.
- **Add as trap.** In a trap ledger the card offers *Add as trap*; the confirmation says the trap arrives pending, with its failure point, trigger, wrong approach, correct treatment, detection and consequence written, and that the decoy, superseded version, margin, expected behaviour, classification, acceptable variations, tolerance rationale, right headline and outputs stay yours to supply. There is no slot count and no duplicate-check note, the package line counts traps, and the overlap sentences speak of a current trap (the card's status tag still reads *Overlaps a current mode*). The page follows the framework of the project in the task editor.
- **Add as net-new mode (failure-mode set).** An idea joins the project through the same function as *Add as net-new mode* on the candidate roots page (`FinanceAuthoring.addCandidate`), after a confirmation that states the five-mode rule (three historical, two net-new) and how many net-new slots are open. The page warns at the cap and does not block; the task editor then flags the set for review. The new root arrives pending, with its failure point, trigger, wrong approach, correct treatment, detection method and consequence written and with no recorded score or precedent text. The expected behavior, classification, acceptable variations, tolerance rationale, correct headline and outputs stay yours to supply.
- **A hypothesis, not a result.** Every card reads "Hypothesis for review. No claim about how a solver will perform." Nothing is run, and a precedent's recorded score says nothing certain about your task. *Copy as text* leaves the precedents out.

## Lint limits

The lint follows the project guide and the format that actually ships, not a stricter one. Page numbers in lint messages refer to the project guide.

- **Business prompt: no word limit.** The guide asks only for a concise prompt, and shipped prompts ran 71 to 91 words, so length is a review cue above 120 words and never blocks (`lintPrompt` in `core.js`). Only an empty prompt blocks the solver export. The 44-word `exportPolicy` exception from earlier projects still imports and validates as before, but never lowers the cue: the effective value is the larger of 120 and the policy value. The draft generator still writes prompts of 40 words or fewer.
- **Prompt blockers (exact tokens).** A file name or extension (`Register_Sep2026.xlsx`), a build or platform term (GAF, SAF, golden answer, grader, rubric, trajectory, a model name, and any `lintTerms` of a loaded private module), and a word-count request (`under 200 words`, `a 300-word note`).
- **Prompt review cues (heuristics).** No operative date; wording that names the mechanism, the basis or the right figure (`not a limit`, `on a USD basis`, `takes precedence`, `the correct rate`); role-play, greetings and sign-offs; `do not fabricate` and similar; tabs, columns, cells, fonts or steps; the words task, activity, workflow, world and AI; and curly quotes, long dashes or non-breaking spaces.
- **Grader guidance: review above 650 words; blocker at 800 or more.**
- **Titled sections.** The five block headings are accepted (exact match, with or without the leading number and period): `Context`, `Golden Response`, `1. Must-haves`, `2. Common Failures`, `3. Acceptable Variation`. So are the three headings of the A/B/C template: `A) MUST BE PRESENT AND CORRECT`, `B) PENALIZE FOR`, `C) NEUTRAL`. Any other titled section, markdown heading, or bold title is still flagged.
- **The A/B/C template.** Its three headings and the fixed sentence under each are recognised whole and are not linted, because their wording (`PENALIZE`, `golden answer`, two long dashes) is the template's own. Everything the writer adds around them is linted as before. *Clean guidance* and the guidance export leave these lines exactly as they are. A guideline in this layout gets one review cue: if the named-section check flags it, add a `Context` heading line above the first paragraph and a `Golden Response` heading line above the benchmark paragraph.
- **Layout (review cues).** The five named sections (or the A/B/C template), the answer file named with its extension, the sentence `The file type and file names of a submission are not graded.`, at least one must-have with a value, at most ten common failures, a figure in each common failure (the error, the wrong figure and the right figure), and no severity wording (`critical error`, `minor issue`). These run on a whole guideline only: the generated draft and Mode ideas cards are linted as fragments (`lintGuidance(text, {fragment: true})`).
- **Scoring words.** `You are grading` and `You are grading a` are not flagged. Every other use of `grading`, `score`, `scoring`, and `points` keeps its behavior, and the scoring-language blockers (for example `penalise`, `partial credit`, `weighting`) are unchanged.
- **Internal jargon.** The built-in list is generic and names no platform or company. A private evidence module may carry a `lintTerms` array of strings; when such a module is loaded, the editor passes those terms to the guidance and prompt lint as extra case-insensitive jargon terms, and *Run local checks* uses them for the upload checks below, so platform-specific terms stay on your machine.
- Unchanged: the cell-reference check, the dash and unicode check, the check for mentions of models or prompts, and the vague-failure heuristic.

## Upload checks

*Run local checks* on Overview also checks the files that will be uploaded: solver files (source and proposal roles) and answer files (evaluator-role Office or PDF files). The `gaf/` template is the parent's, is never changed, and is never checked.

- **File names with spaces** (error): the platform refuses the upload.
- **Answer file names** (review): GAF, SAF, a version (`v2`), Final, Untitled, Copy, Draft or a task id in the name.
- **Build or platform words** (review): GAF, SAF, golden, grader, grading, rubric, trap, decoy, variant, pilot, fingerprint, reference answer, answer file, derivative task, hardened, trajectory, model names and any private `lintTerms`, in the extracted text, Word comments, Excel notes and threaded comments, and the title, subject, keywords and description properties of solver and prompt files. An ordinary word can match (a pilot scheme, a value trap), so each finding cites where.
- **Document properties to scrub** (review): a creator, last-modified-by, company, manager, non-default template or comment author that names a generator (python-docx, openpyxl and the like), a default account, a path, an e-mail address, or a private term. Other property values are listed once (info) to confirm that none is a real person. A file shipped with its properties removed shows nothing.
- **Lookalike punctuation** (info): curly quotes, long dashes and non-breaking spaces. Normal in a document typed in Word; a tell in text from a rewriting pass.
- **A prompt file that names a file** (review). The earlier 40-word cue for prompt files is gone.

Word footnotes and endnotes are now extracted as records (`Footnote 2`), so a rule that sits in a footnote is searchable like the body text.

## Privacy

- **`private/` is git ignored.** It holds evidence modules, their builders, and every agent round: `private/agent-rounds/<round id>/` has `round.json`, `freeze.json`, `packet.sha256`, and for each pilot `runs/<n>/` with `transcript.jsonl`, `stderr.txt`, `run.json`, and `outputs/`. Transcripts are written as they arrive and never edited. The agent features write only to `private/agent-rounds/`, the pilot folders in the temporary directory (kept until you delete them), and `LOCAL_SERVER.json` and `LOCAL_SERVER.lock` at the project root (both ignored by git; the companion removes them when it shuts down), plus the files your browser downloads when you ask it to. They read the packet folder you choose, and the `claude` program reads its own configuration. The round JSON that the page downloads (`Finance_Agent_Round_<id>_PRIVATE.json`) holds the frozen gold and the prompt: keep it outside the repository. `*_PRIVATE.*` and `*-PRIVATE.*` are ignored by git as a safety net, and so are the app's project download (`*-project.json`), task packages, documents, archives and data files in any letter case (`xlsx`, `xlsm`, `xlsb`, `xls`, `xltx`, `xltm`, `docx`, `docm`, `doc`, `dotx`, `pdf`, `zip`, `pptx`, `pptm`, `ppt`, `odt`, `ods`, `odp`, `rtf`, `numbers`, `pages`, `key`, `7z`, `rar`, `gz` and `csv`; `tests/fixtures` is the exception), `/tmp/`, `/.claude/settings.local.json` and `FILEBASE_MANIFEST.json`.
- **The public tree carries no task content.** Code, tests, fixtures, comments, and docs use synthetic data only.
- **A precedent workbook is never kept.** The CSV you pick on the Mode ideas page stays in that page's memory for the session. It is not written to `localStorage`, the project JSON, a workspace, an export or the companion, and the page makes no request (see *Mode ideas*).
- **Privacy scan.** `scripts/privacy-scan.cjs`, run with `npm run privacy`, is generic: the term list is not in the repository. It reads one term per line from `private/privacy-terms.txt` (lines starting with `#` are ignored; a term written as `/.../i` is a regular expression; anything else is a case-insensitive literal). In a linked worktree without `private/privacy-terms.txt` it uses the main checkout's list. It scans every tracked file and every untracked file that git does not ignore. Text files are scanned. A binary file cannot be scanned, so it blocks the scan unless its exact path is a line of `scripts/binary-allowlist.txt` (no wildcards; lines starting with `#` are comments; a path may be followed by `sha256=<hex>` to pin its content). Binary means a NUL in the first 8 KB, content starting with `%PDF-`, `PK\x03\x04` or `\xD0\xCF\x11\xE0`, or content that is not valid UTF-8. An allowlisted `.png` must really be a PNG, and `tests/fixtures/package.zip` is pinned by its hash. This covers tracked files, untracked files that git does not ignore, and, with `--range`, files that a commit in the range adds or changes; the range check classifies every added or changed blob by its own content. Task packages (xlsx, docx, pdf, zip) and the app's exports must never be listed. The scan also blocks tracked files that `.gitignore` ignores and, with `--range`, a push that adds or changes an ignored path. `--range <base>..<head>` also scans the added lines of the commits about to be pushed, and `--terms <file>` uses another list. It prints `file:line` and the number of the matching term, never the line itself, prints `BINARY <path>` for each blocked binary file and `IGNORED <path>` for each ignored path (fix it with `git rm --cached <path>`), and exits 1 on any hit or blocked file. The summary line counts `binary allowed`, `binary blocked` and `ignored blocked`.
- **It fails closed.** If the term list is missing or empty, it exits non-zero with `no privacy term list: refusing to pass`.
- **Block pushes locally.** A `pre-push` hook is recommended. The repository carries it as the shim `.githooks/pre-push`. Hooks are not versioned, so run this once in each clone:

  ```sh
  npm run setup
  ```

  It runs `scripts/setup-hooks.cjs`, which copies the shim into the common hooks folder (`$(git rev-parse --git-common-dir)/hooks/pre-push`), so every branch and worktree of the clone uses it. It sets no `core.hooksPath` (it unsets one that is `.githooks`) and refuses to overwrite a different pre-push hook unless you run `npm run setup -- --force`, which keeps the old one as `pre-push.replaced`. The shim blocks the push if `node` or `scripts/pre-push.cjs` is missing. The manual hook still works. From the top of the work tree:

  ```sh
  printf '#!/bin/sh\nexec node scripts/pre-push.cjs "$@"\n' > .git/hooks/pre-push && chmod +x .git/hooks/pre-push
  ```

  The launcher warns when no pre-push hook is where git looks, and only when its folder is the top of a git checkout. `scripts/pre-push.cjs` reads the refs that git is about to push and runs the scan with `--range` over exactly the commits the push would publish (`<remote sha>..<local sha>`; for a new branch, from its first commit that is not on the remote). A term that one commit adds and the next removes is therefore still caught, which a scan of the work tree alone would miss. It scans the work tree as well, ignores deletions, and blocks the push on any hit, on any failure to scan, and on any binary file that the push adds or changes (or that the work tree holds) whose path is not on `scripts/binary-allowlist.txt`, and on any path that `.gitignore` ignores which the push adds or changes. The push check reads that allowlist from the commit being pushed, so add the line in the same push as the file. Push to a named remote (`git push origin ...`) so the hook knows which remote's history to leave out. Set `FINANCE_PRIVACY_TERMS=/path/to/terms.txt` to use another term list; the default is `private/privacy-terms.txt`. Without the hook, run `npm run privacy -- --range <remote>/main..HEAD` before every push.
- **A test for the whole tree.** `FINANCE_PRIVACY_TERMS=private/privacy-terms.txt npm test` also runs the scan over every tracked and untracked file as part of `tests/core.test.cjs`. The list is never in the repository, and the test is skipped without the variable.

## Data and export contract

- Project schema `finance-task-design` version 2; version 1 projects import with defaults. A project carries `framework`: `trap-ledger` (new projects) or `failure-mode-set` (a file without the field, and the illustrations). Each root also carries `decoy`, `superseded` and `margin` (empty in older files). In a trap ledger the evaluator draft carries `trapLedger` (each trap's deciding rule, decoy, superseded version, margin and headlines) in place of `failureModeSet`, and the failure-mode records and working document speak of traps. Evaluator export adds the failure-mode set, root records, source excerpts, guidance with lint, review findings, gates, runs, and calculator state. Official human-only analysis fields and attestations are never generated.

They carry no score.
- Generated text passes a deterministic cleanup (dashes, curly quotes, zero-width characters, repeated spaces); the working document keeps its indentation.
- Package schema `finance-task-package` version 1 and workspace schema `finance-analysis-workspace` version 2 are unchanged. Archive limits: 50 MB per file, 100 MB expanded, 1,500 entries, 150 documents, three nesting levels.

## Boundaries

Structural checks and lint are not semantic verification, a difficulty score, or a grading decision. Pilot results are directional: a few runs of one model cannot establish how hard a task is, and a simulated grader is not the evaluation's grading. The app does not recalculate workbooks, authenticate run IDs, or submit anything. The Offline edition calls no model. The Local agents edition calls a model only through the `claude` CLI, and only after an approval for that round or that single run. A qualified reviewer and a matched actual run are still required before any claim about a task's difficulty.
