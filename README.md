# Finance Task Studio

A workspace for building the **failure-mode set** of a derivative finance task: three historical modes from a failure-mode library plus two net-new modes from your own practice, each anchored to source evidence and recomputed economics, then carried into lint-checked grader guidance. It reads task packages (ZIP, XLSX, DOCX, CSV, text) in the browser, proposes source-linked candidate roots, and exports the solver draft, the private evaluator draft, the failure-mode records, and the persistent working document separately.

It comes in two editions:

| Edition | How you run it | Agents | Network |
|---|---|---|---|
| **Local agents** (primary) | `npm start`, or `Start Finance Task Studio.command` on macOS. A companion server listens on `127.0.0.1`. | Yes, after you approve each round. | The page talks only to its own companion on `127.0.0.1`. The agent runtime (the `claude` CLI) talks to Anthropic. |
| **Offline** | Open `Finance_Task_Studio.html` from disk. | No. The Agents page says so. | None. The page's content security policy is `connect-src 'none'`, and no model is called. |

Private task evidence never ships with the app. A bundled task audit is kept locally as a *private evidence module* (see below), loaded through a file picker, and ignored by git.

## What the agents do

The Agents page runs the loop used to harden a task by hand, on your machine, with Claude Code (`claude -p`):

- **Blind pilots.** Up to 5 agents per round solve the task from the solver files you approve and the prompt you write, after a short fixed text that the companion puts in front of the prompt (the approval dialog shows it word for word). Each runs in its own folder. No grader file, gold, fingerprint, evidence module, log, or earlier output is copied into that folder.
- **Audit.** Every tool call a pilot makes is checked. Any read or write to a path outside the pilot's folder, any search of the whole computer for files (`mdfind`, `locate` and the like), any reach for this computer over the network, and any start of the agent runtime (`claude`) marks the run `DISCARDED`: it stays on disk and visible, and is excluded from classification and export counts. The audit reads commands as text and does not run anything; see *What the audit cannot see* below.
- **Classification.** Answers are compared with a gold and with fingerprints of expected wrong answers that you freeze **before** launch. The app suggests a verdict by matching figures (with your tolerances) and tokens in the final answer. Output files are only searched to say where a figure also appears, and a decision keyword within three words after *not*, *no*, *never*, *avoid*, *cannot* or a word ending in *n't* does not count. A single-digit gold figure is weak evidence and cannot make a match alone, and a reason sentence explains anything left uncounted. That suggestion is a heuristic. The verdict you record is the one stored and exported.
- **Simulated grader.** A tool-less agent reads the guidance text and one answer and returns a verdict and a reason. It is a simulation and a single sample, not the evaluation's grading.
- **Author review.** A tool-less agent reads an extract of the task package loaded on Overview and writes one analysis. The dialog leaves out, by default, loaded files marked evaluator-only, run evidence or author review (one *Leave out* box covers all three) and says how many files are left out.

## Safety model

- **Approval per round.** Nothing starts without an explicit approval click for that round. The approval dialog shows the model, effort, number of pilots, how many run at once, the spending cap per pilot and for the round, tool list, working folder, packet hash, the fixed text pilots see before your prompt, and the isolation statement, and asks for three acknowledgements: shell access as you, network use by the agent runtime, and isolation by audit only. The simulated grader and the author review each ask for their own approval of a single run.
- **Cap of 5 pilots per round.** The cap is a constant in `backend/agents/constants.cjs` and is enforced on the server as well as in the page. A new round needs a new approval. By default every pilot of a round starts at once, so a round ends within one 50 minute limit; you can choose fewer at a time.
- **Spending cap per pilot.** Every agent process the Studio starts gets `--max-budget-usd`: USD 3.00 per pilot by default (0.05 to 20.00, chosen per round), 0.50 for a simulated grader or an author review. The runtime stops a pilot that reaches it, and the run details say so. **The cap is not a ceiling on everything a pilot can start.** A pilot has a shell, and the `claude` program and your sign-in stay reachable from it (they must, for the pilot itself to run). A `claude` process that a pilot starts from its shell has no cap, and its tool calls are not audited. The audit discards a run whose tool calls start the runtime (kind `runtime`: `claude` as a command or argument, `claude -p` in code or in a file the pilot writes, the runtime's own path), but only after the fact, and it cannot see a start under a name built while a command runs. The approval dialog, the settings card and the approval summary say so.
- **Pre-flight before anything starts.** Before approval (and again at launch, and before a simulated grader or author review) the companion checks that `claude --help` lists every option it will pass, reads the pilot token if you stored one, refuses an environment that would send a pilot through a gateway or rename its models (`ANTHROPIC_BASE_URL` at any host but Anthropic's, `ANTHROPIC_AUTH_TOKEN`, Bedrock, Vertex or Foundry switches, model overrides) unless the pilot token is there to replace them, and checks that `claude auth status` says it is signed in under the exact pilot environment. No check runs a model. A problem is named, by variable name and never by value, and nothing starts.
- **Pilot sign-in.** Pilots can run under a dedicated token of your own Claude subscription instead of your everyday sign-in (see "Pilot sign-in" below). The token is read from the macOS Keychain item `finance-studio-pilot-token` (or `FINANCE_STUDIO_PILOT_TOKEN`) at each pre-flight, handed only to the processes the Studio starts as `CLAUDE_CODE_OAUTH_TOKEN`, and kept out of the record: the companion blanks it out of the runtime's output before anything is parsed or written, discards a run whose tool calls read the environment (`env`, `printenv`, `/proc/*/environ`, `os.environ`, the variable names, and so on; kind `environ`) or show the token anywhere (kind `secret`), and after each run scans the whole pilot folder and the evidence copy and blanks the token out of any file that holds it. Seen live in two runs (macOS, Claude Code 2.1.287): the environment of a pilot's Bash tool did not contain the variable (`printenv` printed nothing), so a pilot's commands did not see it; the Studio does not rely on that, because the same user's processes can still read the `claude` process's environment (`ps -E`, `/proc/<pid>/environ`; the audit flags those) and a future runtime may behave differently. It cannot stop a pilot that does obtain the token from sending it away while it runs; a token that was sent away is compromised, so make a new one with `claude setup-token` and store it again.
- **Gold frozen before launch.** The server refuses to launch a round without a freeze record (hash and timestamp). Edits after launch create a new version labelled post-hoc and never overwrite the original.
- **Shell access as you.** A pilot is a Claude Code agent with Bash, Read, Write, Edit, Glob, and Grep, running with your user permissions.
- **Isolation by instruction and audit, not by an operating system sandbox.** The pilot folder is created in the operating system's temporary directory (`finance-studio-pilots/<run id>`), outside the project. It holds only the approved solver files, an empty `outputs/`, and an empty `.tmp/` that is the agent's `TMPDIR`. The runtime's own configuration folder is moved to `.tmp/claude-config` inside it (`CLAUDE_CONFIG_DIR`), so files the runtime saves for the agent stay inside the folder; your sign-in is still read where it always is, and nothing is copied. (Checked live on macOS with Claude Code 2.1.287 by `npm run smoke` stages S0 to S2: the runtime reports the moved folder, signs in there with the pilot token, and a real pilot's large tool output landed under it; see `VERIFICATION.md`.) Memory and `CLAUDE.md` files are switched off for pilots. Nothing at the operating system level stops a command from touching other files or the network. The audit finds path violations afterward and discards those runs. There is no allowance for harness paths and no setting that relaxes it. **Pilot folders are kept**: they hold copies of the packet files and the pilot's work, and they stay in the temporary directory until you delete them (the approval dialog says so). The companion checks that the folder holding them is a real directory that your account owns, makes it private (mode 0700) if it is open, and refuses a link.
- **Blind while a round runs.** A pilot can reach the companion like any program on your machine, so while any round runs the companion leaves the gold, fingerprints, prompt, approval summary, source folder, final answers and classification details out of every round answer (the page says what is hidden; the answer to a freeze keeps that round's approval summary, which elides the prompt), refuses a simulated grader or author review (their text would be on a command line a pilot can read), and the audit discards any pilot whose tool calls reach for this machine over the network (`localhost`, `127.x.y.z`, `::1`, or the companion's port). When a pilot finishes normally, anything it left running in its process group is stopped before the audit and the output snapshot, and a note says so. Known gaps, not closed yet (`docs/local-agents.md` section 16): the export answer is not withheld (fingerprint ids and your classification notes, no gold), `GET /api/status` still carries the archived adapter's state, and the routes that change a round still accept a request that carries the nonce (their answers are withheld).

### What the audit cannot see

The audit works on the text of the tool calls. It follows `cd`, variables the command sets, quoting, command substitution, here documents, `eval`, `bash -c`, `${IFS}` splitting and brace words, and it resolves symbolic links that exist. It does not execute anything, so these are **not** seen, and a run that used one can still be `CLEAN`:

- a path assembled while a command runs (a variable or command output the audit cannot see, a script that builds a path, encoded text passed to `eval` or a shell, a program started from a name built at run time);
- a directory change whose target cannot be resolved (`cd "$SOMEWHERE"`): later relative paths are then not checked, and only `..` paths are still flagged;
- anything done by a program the pilot started that the text of the call does not name;
- a `claude` process started under a name assembled while a command runs, or from a copy whose name the call does not show. Such a process runs with your sign-in and without the spending cap until it ends;
- a connection to this machine through a host name assembled at run time, the machine's own host name or LAN address, or a bare `localhost` on a line that names no network client.

Where the text shows that one of these happened, the run gets a **note** (`cwd-unresolved`, `unverifiable-command`, `unverifiable-code`, `unverifiable-input`, `unverifiable-path`). A note never discards a run. Read the notes in the run details. The audit is told the environment the pilot received, so a path held in an inherited variable (for example one that `npm start` sets) is checked when a command uses that variable by name. The environment is still passed on whole, as the design says. `npm start` adds variables that name the project folder (`INIT_CWD`, `npm_config_local_prefix`, and others), and your shell may export `OLDPWD`; if you do not want a pilot to be able to read them, start the companion with `node backend/server.cjs --open` from a shell where they are unset. `cd -` is only trusted after a `cd` in the same command, because its target is otherwise whatever the shell inherited. The work per call is capped and timed; a call that exceeds a cap fails closed and discards the run.
- **The agent runtime talks to Anthropic; the page talks only to localhost.** The solver files and prompt you approve are sent to Anthropic by the `claude` program, as are the guidance text and one answer for a simulated grader, and an extract of the loaded package text for an author review. The page itself makes requests only to `127.0.0.1`.
- **Nothing starts on launch.** Starting the companion, with `npm start` or the launcher, never starts a model. The launcher only asks `claude --version`.
- **No workarounds.** If `claude` cannot start (not found, not signed in, blocked by a permission policy), the run is marked `failed` with the real error text. Run the command from your own terminal instead.
- **Directional results only.** With fewer than 20 runs every count is shown as "directional only, n = k". The app computes no pass rate, no difficulty score, and no works/fails label. Scores in a precedent workbook you load on the Mode ideas page are values you recorded: they are shown as written and only order ideas.

## Quick start

Requires Node 22 or newer and the `claude` CLI, installed and signed in (run `claude` once in a terminal). There is nothing to install with npm.

Your first pilot:

1. `npm run setup`, once per clone. It turns on the privacy check for pushes (see *Privacy*).
2. Store the pilot token ([Pilot sign-in](#pilot-sign-in)).
3. `npm start` (below). Keep that window open and use a second terminal for the next two steps.
4. `npm run smoke`. This is stage S0 and calls no model.
5. Once, run S3 and S4: `npm run smoke -- --stage S3 --i-approve-model-calls`, then the same with `--stage S4`. Each calls a model under a small spending cap (USD 0.25 and 0.50); [Pilot sign-in](#pilot-sign-in) says what they check.
6. On the Agents page, run a first round with 1 pilot before you scale up ([The Agents page](#the-agents-page)).
7. Classify the answers, then export them.

```sh
npm start
```

This runs `node backend/server.cjs --open`. The companion listens on `127.0.0.1:47321`, prints its address, writes `LOCAL_SERVER.json` (ignored by git), and asks the system to open the page (`open` on macOS; elsewhere use the printed address). Open the **Agents** view in the sidebar. The browser keeps its saved work (the project and the Agents draft) per address, so the fixed port brings it back at the next start.

If `FINANCE_STUDIO_PORT` is unset or empty and 47321 is busy, the companion takes a free port and prints `The usual port 47321 is busy, so this start uses another address. Work saved in the browser by earlier sessions (the project and the Agents draft) will not show at this address.` A `FINANCE_STUDIO_PORT` you set, `0` included, is used as given, and if that port is busy the start fails with exit code 1. Only one companion runs per project folder. A second start prints `Finance Task Studio is already running at <url>`, opens that address when it was started with `--open` (`npm start` and the launcher do), and exits with code 0. A `LOCAL_SERVER.json` whose process is gone, or whose address does not answer `/api/status` within 1.5 seconds, counts as stale and is replaced.

The companion prints `Keep this window open while a round runs; closing it stops the companion and its pilots.` Ctrl-C, closing the window, `SIGTERM` and `SIGQUIT` cancel the running round and remove `LOCAL_SERVER.json`. When the process exits for any reason, it also sends `SIGKILL` to the process groups of pilots, simulated graders and author reviews that are still running. A `kill -9` cannot be caught, so a pilot can outlive it. The next start stops a leftover pilot only if `ps` shows the runtime binary recorded for it and the process leads its own group, adds `A pilot process left over from the previous companion was stopped at startup.` to that run's stderr tail, and the run still ends `failed` with the reason `interrupted`.

To use a specific `claude` binary: `CLAUDE_BIN=/path/to/claude npm start`. Detection order is `CLAUDE_BIN`, then `claude` on `PATH`, then `/opt/homebrew/bin/claude`, `/usr/local/bin/claude`, `~/.claude/local/claude`, and `~/.local/bin/claude`. Detection runs `claude --version` with a 5 second limit and nothing else.

### Pilot sign-in

Pilots load no settings (`--setting-sources ""`), so a sign-in that lives in your `~/.claude/settings.json` (for example a gateway reached through `ANTHROPIC_BASE_URL` and `ANTHROPIC_AUTH_TOKEN`) never reaches them, and the companion refuses to send a pilot through a gateway it cannot see through. Give pilots a token of your own Claude subscription instead. On macOS, store it in the Keychain from the clipboard, so that nothing is typed or pasted into the terminal. Run the commands one at a time:

```sh
claude setup-token
```

It prints the token on your screen once. Select only the `sk-ant-oat01-…` line and copy it. Then:

```sh
security add-generic-password -U -a "$USER" -s finance-studio-pilot-token -w "$(pbpaste | grep -o 'sk-ant-oat01-[A-Za-z0-9_-]*' | head -1)"
security find-generic-password -s finance-studio-pilot-token -w | tr -d '\n' | wc -c
pbcopy < /dev/null
clear
```

The second command prints a number only. It was 108 for the tokens made in testing; a very different number (0, or a few characters) means the copy did not take, so repeat from `claude setup-token`. Do not use the bare `-w` password prompt: pasted text reached it with the wrong content twice in testing, and the pre-flight cannot tell, because `claude auth status` accepts any value of the right shape (only a model call, smoke S1, proves the token). The last two commands empty the clipboard and the screen. The `-U` replaces an existing Keychain item in place.

On other systems, or to override the Keychain, start the companion with `FINANCE_STUDIO_PILOT_TOKEN` set in its environment. `FINANCE_STUDIO_KEYCHAIN=off` makes the companion ignore the Keychain altogether (the tests set it). The companion prints `Pilot sign-in: …` when it starts, and the pre-flight notice in the page says where pilots sign in from. Without a token, pilots use whatever sign-in `claude` finds on its own, as before.

The token is on your screen after `claude setup-token`, so never paste terminal output into a chat, an issue or a file in this repository or `private/`. If the token was shown anywhere, run `claude setup-token` again and store the new one; making a new token does not revoke the old one, so also look for a sign-out-everywhere option in your Claude account settings.

Before your first round, `npm run smoke` checks the installed `claude` without starting a model: its version, that `claude --help` lists every option the Studio passes, where the pilot token comes from (its length, never its text), which gateway variables a pilot would inherit, and that `claude auth status` says it is signed in in the pilot environment (with the configuration folder moved into a scratch folder and the token, if any). Four further stages call a model and run only when you add `--i-approve-model-calls` (`--stage all` runs S0 to S4, with S4 after S3); see `scripts/live-smoke.cjs`: S1 (one tool-less call), S2 (one pilot through a round), S3 (one pilot told to print its token, which must end `DISCARDED` with the token in no kept file) and S4 (one pilot on `claude-haiku-5-5` at effort low, spending cap USD 0.50, that uses its Read, Write, Edit, Glob and Grep tools inside its folder and makes one Read of a canary file outside it). S4 checks that each tool call was seen in the live stream, that the calls inside the folder are clean, and that the outside read is flagged and the run `DISCARDED` (reported as INFO if the pilot declines to read the canary). It saves the stream, with the token redacted and your home folder shown as `~`, under `private/live-smoke/`. On macOS with Claude Code 2.1.287 and the token in the Keychain, S0, S1 (USD 0.0059) and S2 (USD 0.0271) passed on their first run. S3 first ended with two FAIL rows (USD 0.0252) because the stage expected a leak this runtime does not allow; after the stage was corrected it passed (USD 0.0199). Its rows were rewritten again since, so run S3 once more after updating. Not yet seen live: a pilot that reaches its spending cap, a prompt delivered on stdin, and a live Read, Write, Edit, Glob or Grep call (S4 was written for the last and has not been run).

On macOS you can double-click **Start Finance Task Studio.command** instead. It looks for Node in `/opt/homebrew/bin`, `/usr/local/bin`, and on `PATH` (the runtime bundled with the archived harness app is the last candidate), prints the Node version and whether `claude` was found, then starts the same server. It prints `Privacy hook not installed: run npm run setup once` when the clone has neither `core.hooksPath` set to `.githooks` nor a `.git/hooks/pre-push`.

## Open it

- **Finance_Task_Studio.html** is the single-file Offline edition: download it and open it in a current desktop browser. No installation, account, server, or internet connection is needed. It never runs agents.
- **index.html** is the source-folder edition for development; keep every file beside it. Served by the companion, its Agents page can run agents; opened from disk it behaves like the Offline edition.
- **Start Finance Task Studio.command** (macOS) starts the companion as described above.

## The Agents page

Six cards, top to bottom, under a status strip that shows the selected round, how many pilots are done, running, waiting, failed or cancelled, the elapsed time, and any other running round (the browser tab title shows `(ended/total)` too). Launch stays disabled until the earlier steps are done. The form is kept as a draft in the browser while you work (never while a round runs; *Clear draft* empties it; a launch removes it).

A step rail on the left (a stepper across the top on narrow screens) marks each of the six cards as done, needing attention or running, says what to do next, and jumps to the card.

1. **Runtime.** Whether Claude Code was found, its version and path, and a *Check again* button.
2. **Packet.** Enter the folder that holds the solver files and press *Inspect*. Unzip the task ZIP outside the project, then paste the full path of its `filesystem` folder (in Finder, select it and press Option-Command-C). The path may carry surrounding quotes, Terminal backslash escapes or a leading `~`; your home folder itself is refused. Pilots see the ticked files under `./filesystem/` with their folder structure kept, so choose the folder that is the production `filesystem` folder itself (the page warns when the folder you chose already contains one). Regular files only (no symlinks, depth up to 4, up to 150 files, up to 100 MB; a file name with a control character is listed but cannot be used). Files that look like grading material are excluded by default, with the reason shown: anything under a `grader(s)`, `grading`, `evaluator(s)`, `reference(s)`, `answer(s)` or `private` folder (also inside `gaf/`), and, outside a `gaf/` folder, paths with a whole grading word in a folder or file name (guideline, guidance, grading, grader, rubric, solution, expected, answer, golden, gold, reference, memo, evaluator, fingerprint, attestation, private, and their plurals; two-part run-together names such as `answerkey` too, but not longer ones such as `answerkeyfinal`). Evidence of earlier runs (`trajectory`, `run 03`, `run_log`, `pilot run`) and review or audit notes (`review`, `audit`, `candidate`, but not `audit committee` or `credit review`) are excluded too. Words count only whole, so `Goldman_Comps.xlsx` and `Cash_Runway_Model.xlsx` are sources. Some ordinary finance names are withheld by this rule on purpose (for example `Revenue_Guidance.pdf` or `Expected_Returns.xlsx`); each shows its reason and can be overridden. **Inside a `gaf/` folder only the folder names above withhold a file; grading words in the file name do not**, because `gaf/` is what the production solver sees, so `gaf/Golden_Response.docx` is included by default and goes to every pilot while the gaf toggle is on. The packet table marks such a file *Check: grading word in a gaf/ file*; untick it, or turn the gaf toggle off, if pilots should not see it. Including an excluded file needs an explicit per-file override, which is recorded in the round. The page and the companion use the same rule (`classifyPath` in `package-engine.js`). Folders inside the project or under `private/` are refused. Write the pilot prompt in the box (word count shown against the project limit). Pilots also see a short fixed text before it: it says the materials are in `./filesystem`, that files go to `./outputs`, that the answer goes in the final message, and that a missing file is to be reported in the answer, not searched for elsewhere on the computer. The Round card and the approval dialog show it word for word under *Pilots also see this fixed text before your prompt*. The `gaf/` toggle (on by default) records whether that folder is part of what the solver sees; it matches production only if the production solver sees it. A file counts as a gaf file when `gaf` is a word in its path with a slash, an underscore, a space or a dash (or the start) before it and one of those, a dot (or the end) after it: `gaf/x.csv`, `gaf-hedge.csv`, `GAF_notes.txt` count; `gafHedge.csv`, `gaf2024.xlsx` and `x.gaf.csv` do not, and are sources. The role column, the toggle, the page and the companion all use this one rule (`GAF_PATTERN` in `package-engine.js`), so every file shown as a gaf template is hidden when the toggle is off. The choice is shown in the approval dialog and recorded in the round and in every exported record.
3. **Settings.** Model, effort, the number of pilots (1 to 5, default 5), how many run at once (all by default), and the spending cap per pilot, with the round maximum for the pilot processes the Studio starts (the card says what the cap does not cover, see *Safety model*). Changing one after freezing marks the freeze stale.
4. **Freeze.** Enter the gold decision phrase, the gold figures with tolerances, and the fingerprints of expected wrong answers (id, label, tokens or figures). A figure takes the same forms as the companion reads: `12450`, `12,450`, `$12,450`, `(1,200)` for -1,200, `3.2x` or `12%` (kept as 12, not 0.12). The tolerance field is labelled "Tolerance (absolute, same unit as the value)". *Freeze gold* shows the hash, a content hash of the gold and fingerprints alone, and the timestamp.
5. **Round.** The round's settings, the fixed text pilots see before your prompt, and the shell-access and isolation statements. *Review and approve* first runs the pre-flight (a problem shows "Fix this before you approve." and *Check again*), then opens the approval dialog. It shows that fixed text word for word, the prompt and its hash, the files delivered and the files withheld, the command line with the prompt elided, and the exact text that the approval hash covers (that text includes a `Fixed prompt prefix sha256:` line, so the approval covers the fixed text too). *Approve and launch* stays disabled until all three acknowledgements are ticked. If the launch is refused after the approval (another round is running, or Claude Code is missing), the round stays approved and the same dialog launches it once the cause is gone. *Review and approve* is disabled while Claude Code is not found.
6. **Runs.** One row per pilot with state, turns, tool calls, resolved model, audit badge, and elapsed time. *Details* opens the final answer, outputs, and any violations with the offending call. A failed run explains itself: the reason in words, the runtime's own message, and the command (prompt elided) to run from your terminal. Classify each `CLEAN` run (suggested verdict, your verdict, fingerprint chips, note). The chips include fingerprints that a post-hoc freeze added. Under the table: *Start next round from this round* (for a frozen round that is running or has ended: finished, failed or cancelled; disabled while any round runs) makes a new draft with the same files, prompt, settings, gold and fingerprints, to edit, freeze and approve again; the freeze then says whether gold and fingerprints changed. Then *Simulated grader* and *Author review* (both disabled while any round runs), and **Export**, which adds run-evidence records to the project's experiments (after a confirmation) or downloads the round JSON. `DISCARDED` runs are exported only in a separate list.

## Workflow

1. **Load the task package.** Drop the task ZIP or source files on Overview. Files are inventoried and extracted locally (formulas with saved values; PDFs stay unparsed). *Run local checks* reports saved formula errors, missing caches, hidden sheets, version clues, and prompt-wording cues, all labeled structural or heuristic.
2. **Generate candidate roots.** Three source-linked hypotheses are ranked by evidence, arithmetic, and causal independence. Same-root duplicates and non-binding variants are rejected; a candidate without a source-resolved answer is held. Ranking is not a difficulty prediction.
3. **Lock the set (Failure modes page).** Enter the task context from the task pull. Import the saved JSON of the failure-mode library pull; the app never calls the endpoint and the shared task key never enters it. The shortlist is deterministic: approved, uses above zero, numeric average score; lowest average first, then most uses, then not overused, then lowest usage share, then Mode ID. Exactly ten are shown; fewer is reported, never padded. Select exactly three by Mode ID. Add exactly two net-new modes from work you did or reviewed, or promote a candidate root or a Mode ideas card with *Add as net-new mode*; record the duplicate check against the shortlist for each. Write the thesis that ties the five together.
4. **Instantiate each mode (Root design).** Complete the record contract: triggering condition, plausible wrong approach, detection method, corrective action, expected model behavior (solve, reconcile, push back), classification (strict error or judgment-call divergence), governing rule, facts, anchors, acceptable variations, and tolerance rationale. *Scaffold blanks from mechanism* fills empty fields from the research catalog, marked as hypotheses the audit keeps flagging until edited. One causal group per root: several changed outputs are one failure.
5. **Recompute both branches (Economics).** Enter correct and wrong outputs with units, tolerances, and an optional decision threshold. The helpers (cash bridge, whole-cent ceiling, record-date dividend capacity, affine fixed point) show their equation and limits.
6. **Draft, lint, export (Review and export).** *Draft from failure modes* writes deterministic grader guidance from the records; rewrite it in your own words. The lint flags what gets guidance returned (see *Lint limits* below). Blockers are exact tokens; the rest are labeled heuristics. Exports: solver JSON/text (prompt and file manifest only), evaluator JSON/text, grader guidance text, failure-mode records, and the working document.
7. **Test the design (Agents page, Local agents edition).** Run a blind pilot round on the solver package (the approved files and your prompt, which every pilot reads after a short fixed text), classify the answers against the frozen gold, and add the evidence to the project's experiments.
8. **Record actual runs.** Observed results need a run ID, exact versions, score scale, evidence location, and the modes actually observed. Planned modes are never reused as observed evidence.

## Mode ideas

**Mode ideas** (Package analysis, after the candidate roots page) suggests failure-mode ideas for a derivative task. They come from a catalog of 44 generic mechanisms (written for this tool, with no task or workbook content) and a pure local model. The page makes no request of any kind and calls no model, so it works in both editions.

- **A new task.** Enter the workflow and a short description, then *Generate ideas*. Each card says why the correct reading is unique and the wrong one tempting, and how to build the idea into a task in a few concrete moves. With no package files to point at, an idea is held for missing evidence unless your description already uses the wording it needs.
- **An existing task.** With a package loaded, the page reads only the solver-visible files (source, template and proposal roles; never evaluator, run-evidence or audit files) and cites the document, locator and quote where an idea could attach, each re-checked against the package. It compares every idea with the modes already in the project: an idea that shares a causal group or wording with a current mode is marked as overlapping a current mode or as already covered, and listed last.
- **A precedent workbook (optional).** *Load precedent workbook* reads a CSV you export from your own records, one row per earlier failure mode: workflow, name, what was built, how a solver went wrong, and a recorded score (header names are matched loosely; see `docs/local-agents.md` section 17; up to 5 MB and 5,000 rows). It is read in this browser from the file you pick and kept in the page's memory for the session. It is never fetched, stored, sent anywhere, or written into the project JSON, a workspace or any export; removing the workbook, or a reload, forgets it. Each idea then shows its closest precedents, at most three, with the recorded score exactly as written in your file. Keep the file outside the repository, or under `private/`.
- **Order.** Ideas are grouped by status (reviewable hypotheses, then holds, then overlaps and ideas already covered). With a workbook loaded, each group is ordered by the lowest recorded score among an idea's closest precedents first; an idea with no readable score follows those with one; ties go to the idea with more precedents, then lead ideas, then a stable id. The page says so once, in a footnote: "Ordered by the lowest recorded score among each idea's closest precedents, as recorded in your workbook (lower is the more complex task, in your workbook's reading). Finance Task Studio did not compute these scores and they do not predict a result on this task." Scores are used for this order only. None is rounded, rescaled, averaged, shown as a percentage or turned into a rate or a prediction, and an idea carries no score of its own.
- **Add as net-new mode.** An idea joins the project through the same function as *Add as net-new mode* on the candidate roots page (`FinanceAuthoring.addCandidate`), after a confirmation that states the five-mode rule (three historical, two net-new) and how many net-new slots are open. The page warns at the cap and does not block; the task editor then flags the set for review. The new root arrives pending, with its failure point, trigger, wrong approach, correct treatment, detection method and consequence written and with no recorded score or precedent text. The expected behavior, classification, acceptable variations, tolerance rationale, correct headline and outputs stay yours to supply.
- **A hypothesis, not a result.** Every card reads "Hypothesis for review. No claim about how a solver will perform." Nothing is run, and a precedent's recorded score says nothing certain about your task. *Copy as text* leaves the precedents out.

## Lint limits

The lint follows the format that actually ships, not a stricter one.

- **Business prompt: 60 words.** The 44-word `exportPolicy` exception from earlier projects still imports and validates as before, but never lowers the limit: the effective limit is the larger of 60 and the policy value. The draft generator still writes prompts of 40 words or fewer; a writer may keep to 40.
- **Grader guidance: review above 650 words; blocker at 800 or more.**
- **Titled sections.** The five block headings are accepted (exact match, with or without the leading number and period): `Context`, `Golden Response`, `1. Must-haves`, `2. Common Failures`, `3. Acceptable Variation`. Any other titled section, markdown heading, or bold title is still flagged.
- **Scoring words.** `You are grading` and `You are grading a` are not flagged. Every other use of `grading`, `score`, `scoring`, and `points` keeps its behavior, and the scoring-language blockers (for example `penalise`, `partial credit`, `weighting`) are unchanged.
- **Internal jargon.** The built-in list is generic and names no platform or company. A private evidence module may carry a `lintTerms` array of strings; when such a module is loaded, the editor passes those terms to the lint as extra case-insensitive jargon terms, so platform-specific terms stay on your machine.
- Unchanged: the cell-reference check, the dash and unicode check, the check for mentions of models or prompts, and the vague-failure heuristic.

## Private evidence modules

A bundled task audit (`kind: "bundled-task-audit"`) carries a task's extracted source records, the candidate and screening projects, the review text, and paired calculation rows. Keep such files under `private/` (ignored by git, never bundled by the build) as `private/evidence-module.js` or any `*-audit.js`, and load them with *Load private evidence module*; the saved script form (`window.X = {...};`) and plain JSON both load. The audit views render from the module's own projects and rows, so no task-specific text lives in the code. A saved workspace embeds the loaded module so the analysis round-trips locally. Task-specific module builders also live under `private/` (for example `private/scripts/build-evidence-module.py`, which reads a completed audit package named by environment variables and writes the module next to it); they are not part of the public tree. An evidence module is never copied into a pilot folder. The optional `lintTerms` array is described under *Lint limits*.

## Privacy

- **`private/` is git ignored.** It holds evidence modules, their builders, and every agent round: `private/agent-rounds/<round id>/` has `round.json`, `freeze.json`, `packet.sha256`, and for each pilot `runs/<n>/` with `transcript.jsonl`, `stderr.txt`, `run.json`, and `outputs/`. Transcripts are written as they arrive and never edited. The agent features write only to `private/agent-rounds/`, the pilot folders in the temporary directory (kept until you delete them), and `LOCAL_SERVER.json` at the project root (ignored by git; the companion removes it when it shuts down), plus the files your browser downloads when you ask it to. They read the packet folder you choose, and the `claude` program reads its own configuration. The round JSON that the page downloads (`Finance_Agent_Round_<id>_PRIVATE.json`) holds the frozen gold and the prompt: keep it outside the repository. `*_PRIVATE.*` and `*-PRIVATE.*` are ignored by git as a safety net, and so are the app's project download (`*-project.json`), task packages and documents (`xlsx`, `xlsm`, `xls`, `docx`, `doc`, `pdf`, `zip`, `pptx`; `tests/fixtures` is the exception), `/tmp/`, `/.claude/settings.local.json` and `FILEBASE_MANIFEST.json`.
- **The public tree carries no task content.** Code, tests, fixtures, comments, and docs use synthetic data only.
- **A precedent workbook is never kept.** The CSV you pick on the Mode ideas page stays in that page's memory for the session. It is not written to `localStorage`, the project JSON, a workspace, an export or the companion, and the page makes no request (see *Mode ideas*).
- **Privacy scan.** `scripts/privacy-scan.cjs`, run with `npm run privacy`, is generic: the term list is not in the repository. It reads one term per line from `private/privacy-terms.txt` (lines starting with `#` are ignored; a term written as `/.../i` is a regular expression; anything else is a case-insensitive literal). It scans every tracked file and every untracked file that git does not ignore. Text files are scanned. A binary file cannot be scanned, so it blocks the scan unless its exact path is a line of `scripts/binary-allowlist.txt` (no wildcards; lines starting with `#` are comments). This covers tracked files, untracked files that git does not ignore, and, with `--range`, files that a commit in the range adds or changes. Task packages (xlsx, docx, pdf, zip) and the app's exports must never be listed. `--range <base>..<head>` also scans the added lines of the commits about to be pushed, and `--terms <file>` uses another list. It prints `file:line` and the number of the matching term, never the line itself, prints `BINARY <path>` for each blocked binary file, and exits 1 on any hit or blocked binary file. The summary line counts `binary allowed` and `binary blocked`.
- **It fails closed.** If the term list is missing or empty, it exits non-zero with `no privacy term list: refusing to pass`.
- **Block pushes locally.** A `pre-push` hook is recommended. The repository carries it as `.githooks/pre-push`. Git config is not versioned, so run this once in each clone:

  ```sh
  npm run setup
  ```

  It sets `core.hooksPath` to `.githooks`. The manual hook still works. From the top of the work tree:

  ```sh
  printf '#!/bin/sh\nexec node scripts/pre-push.cjs "$@"\n' > .git/hooks/pre-push && chmod +x .git/hooks/pre-push
  ```

  The launcher warns when a clone has neither of these. `scripts/pre-push.cjs` reads the refs that git is about to push and runs the scan with `--range` over exactly the commits the push would publish (`<remote sha>..<local sha>`; for a new branch, from its first commit that is not on the remote). A term that one commit adds and the next removes is therefore still caught, which a scan of the work tree alone would miss. It scans the work tree as well, ignores deletions, and blocks the push on any hit, on any failure to scan, and on any binary file that the push adds or changes (or that the work tree holds) whose path is not on `scripts/binary-allowlist.txt`. The push check reads that allowlist from the commit being pushed, so add the line in the same push as the file. Push to a named remote (`git push origin ...`) so the hook knows which remote's history to leave out. Set `FINANCE_PRIVACY_TERMS=/path/to/terms.txt` to use another term list; the default is `private/privacy-terms.txt`. Without the hook, run `npm run privacy -- --range <remote>/main..HEAD` before every push.
- **A test for the whole tree.** `FINANCE_PRIVACY_TERMS=private/privacy-terms.txt npm test` also runs the scan over every tracked and untracked file as part of `tests/core.test.cjs`. The list is never in the repository, and the test is skipped without the variable.

## Data and export contract

- Project schema `finance-task-design` version 2; version 1 projects import with defaults. Each root carries lane, Mode ID, the record-contract fields, and the returned library record; the project carries task context, thesis, grader guidance, and the imported library. Unknown fields are discarded, unsafe keys rejected, calculator results recomputed.
- Library import accepts the endpoint shape `{activity, count, modes: [{mode_id, name, mechanism, grader_detection_guidance, status, uses, avg_task_score, usage_share, overused}]}` (up to 500 modes) or a previously saved normalized library; every returned record is kept.
- Solver export is an allowlist: the authored prompt, word count, prompt and workbook versions, and supplied filenames with versions. Evaluator export adds the failure-mode set, root records, source excerpts, guidance with lint, review findings, gates, runs, and calculator state. Official human-only analysis fields and attestations are never generated.
- Agent round export (Agents page) produces run-evidence records of kind `local-blind-pilot` that pass the project's experiment validation: resolved model, audit status, the root failures the writer recorded, the evidence location under `private/agent-rounds/`, and a note stating "directional", the number of runs, whether `gaf/` was visible, and the freeze hash. They carry no score.
- Generated text passes a deterministic cleanup (dashes, curly quotes, zero-width characters, repeated spaces); the working document keeps its indentation.
- Package schema `finance-task-package` version 1 and workspace schema `finance-analysis-workspace` version 2 are unchanged. Archive limits: 50 MB per file, 100 MB expanded, 1,500 entries, 150 documents, three nesting levels.

## Research and playbook provenance

The research catalog incorporates a primary-source review dated 2026-10-07: 20 source records, 14 mechanism hypotheses, and 16 acceptance gates; the ten playbook gates adapt a user-provided playbook. Complete JSON is in `research/`; `scripts/build-catalog.cjs` rebuilds the browser projection. ## Boundaries

Structural checks and lint are not semantic verification, a difficulty score, or a grading decision. Pilot results are directional: a few runs of one model cannot establish how hard a task is, and a simulated grader is not the evaluation's grading. The app does not recalculate workbooks, authenticate run IDs, or submit anything. The Offline edition calls no model. The Local agents edition calls a model only through the `claude` CLI, and only after an approval for that round or that single run. A qualified reviewer and a matched actual run are still required before any claim about a task's difficulty.
