# Local agents: design and contract

Status: design for Finance Task Studio 3.0. This file is the contract the implementation and its tests follow.

## 1. Why

Studio 2.x was an offline authoring workspace. It could not test a design. Testing a design means running a blind solver on the package a writer plans to ship, and reading what it does. A pilot gets the approved solver files and the writer's prompt, and the companion puts a short fixed text in front of the prompt (section 3.2). The workflow that works is the one used to harden tasks by hand: build a frozen solver packet, run a few blind Claude Code agents on it, audit every tool call, and classify the answers against a gold and fingerprints written **before** any output was seen.

3.0 moves that loop into the app. The Studio, when served by the local companion, starts Claude Code agents (`claude -p`) on the writer's machine.

Two editions remain:

| Edition | How it runs | Agents |
|---|---|---|
| **Local agents** (primary) | `npm start`, or `Start Finance Task Studio.command`. Companion on `127.0.0.1`. | Yes |
| **Offline** | `Finance_Task_Studio.html` opened from disk. CSP `connect-src 'none'`. | No. The Agents page says so. |

The page never talks to anything except its own companion. The **agent runtime** (the `claude` CLI) makes network calls to Anthropic. That is disclosed in the approval dialog and the README.

## 2. Non-negotiables

1. **Nothing starts without an explicit approval click** for that round. The approval dialog shows model, effort, number of pilots, how many run at once, the spending cap per pilot and the round maximum, tool list, working folder, packet hash, the fixed text that precedes the prompt and the isolation statement. Starting the companion never starts a model.
2. **At most 5 pilots per round.** The cap is a constant in `backend/agents/constants.cjs` and is enforced on the server, not only in the UI. A new round needs a new approval.
3. **Gold is frozen before launch.** The server refuses to launch a pilot round without a freeze record (hash and timestamp). Edits after launch create a new freeze version labelled post-hoc and never overwrite the original.
4. **Blind means blind.** Each pilot runs in its own folder outside the project root (`<os tmpdir>/finance-studio-pilots/<runId>/`). The folder holds only the approved solver files, an empty `outputs/` and an empty `.tmp/` that is the agent's `TMPDIR`. No grader file, gold, fingerprint, evidence module, log or earlier output is ever copied in. The runner refuses to build a folder if a selected file is under `private/`, or the shared path rule (`classifyPath` in `package-engine.js`, section 9) gives it the evaluator role, unless the writer overrides that file by name in the UI (recorded in the round).
5. **Every tool call is audited, strictly.** Any read or write to a path outside the pilot folder (the folder includes its own `.tmp/`) marks the run `DISCARDED`. It is kept on disk, shown in the UI, and excluded from classification and export counts. There is no allowance for harness owned paths and no toggle that weakens this. See section 6.
6. **Isolation is by instruction and audit, not by an operating system sandbox.** The UI says this in plain words at approval time. A pilot is a Claude Code agent with shell access running as the writer. The server must not claim otherwise anywhere.
7. **Results are directional.** With fewer than 20 runs the UI shows "directional only, n = k" next to every count. No pass rate, difficulty score, or "works / fails" label is generated. This matches `README.md` and `VERIFICATION.md`.
8. **Private task content stays local.** Round state lives in `private/agent-rounds/` (git ignored). Nothing task specific is hard coded in code, tests or docs. Fixtures are synthetic.
9. **The browser never supplies a command, a binary path or an argument list.** It supplies a folder path to read from, file names to include, text, and choices from allowlists. The server builds every argument.
10. **Denials are not worked around.** If `claude` refuses to start (not found, not signed in, permission policy), the run is `failed` with the real stderr tail. The UI tells the writer to run it from their own terminal and offers the exact command.

## 3. Runtime: Claude Code CLI

### 3.1 Detection

`detectClaude({env, exists, execFile})` returns `{found, path, version, source}`:

1. `CLAUDE_BIN` if set and executable.
2. `claude` on `PATH`.
3. Known locations: `/opt/homebrew/bin/claude`, `/usr/local/bin/claude`, `~/.claude/local/claude`, `~/.local/bin/claude`.

It runs `claude --version` with a 5 second timeout. It never runs a model. Reading the status (`GET /api/status`) runs only this.

**Pre-flight.** Before anything starts (a launch, a simulated grader, an author review) and when the page asks for it before approval (`POST /api/agents/rounds/:id/preflight`), the server detects the runtime again and makes four checks. None runs a model; a failure is a 409 that names the problem and says nothing was started.

1. `claude --help` must list every option in the argument lists about to run (`REQUIRED_FLAGS` in `claude-runner.cjs` is exactly what `buildArgs` can produce). An older or newer CLI that lacks one, for example `--max-budget-usd`, is refused by name. The parsed option list is cached per binary path and version; a failure is never cached.
2. The pilot token is read (section 3.4): `FINANCE_STUDIO_PILOT_TOKEN` in the companion's environment, else on macOS the Keychain item `finance-studio-pilot-token` (never when `FINANCE_STUDIO_KEYCHAIN=off`). No token is fine (pilots use the writer's own sign-in). A token that is there but cannot be used or read is refused, naming its place and never its text.
3. The companion's environment must not route a pilot elsewhere (`gatewayFindings` in `pilot-token.cjs`): `ANTHROPIC_BASE_URL` at any host but `https://api.anthropic.com`, `ANTHROPIC_AUTH_TOKEN`, `ANTHROPIC_CUSTOM_HEADERS`, `CLAUDE_CODE_USE_BEDROCK|VERTEX|FOUNDRY`, or a model override (`ANTHROPIC_MODEL`, `ANTHROPIC_DEFAULT_*_MODEL`, `ANTHROPIC_SMALL_FAST_MODEL`, `CLAUDE_CODE_SUBAGENT_MODEL`). With the pilot token such a variable is simply left out of the pilot environment and the answer says so; without it the pre-flight is refused by variable name (host names and the word "set", never a value), because the Studio could not tell what such a pilot tests.
4. `claude auth status --json` must exit 0 and say `loggedIn: true`, run with exactly the pilot environment (section 3.2, pilot token included) in a throwaway `<tmpdir>/finance-studio-preflight-*` folder that is removed afterwards. Email and organisation fields are dropped. For a launch it runs after the packet hash check, and the round state is checked again after the wait. With the token the refusal says so and points at `claude setup-token`. Checked live (2.1.296): with `CLAUDE_CODE_OAUTH_TOKEN` set the command answers `loggedIn: true, authMethod: oauth_token` for any value of the right shape, so this check proves the runtime accepts the token, not that Anthropic does; the first model call does that (smoke S1).

The pre-flight returns `{token, source, dropped}` to its caller; the token lives in memory for that launch (`live.token`) and is never written.

### 3.2 Argument list (fixed, built by the server)

```
claude -p <prompt-text>
  --model <allowlisted id> --effort <allowlisted level>
  --output-format stream-json --verbose
  --tools "Bash,Read,Write,Edit,Glob,Grep" --allowedTools "Bash,Read,Write,Edit,Glob,Grep"
  --permission-mode acceptEdits
  --disable-slash-commands --strict-mcp-config --setting-sources ""
  --no-session-persistence
  --max-budget-usd <x.xx>
```

- `cwd` is the pilot folder. `stdin` is closed. Timeout 50 minutes (`timeout` semantics: SIGTERM, then SIGKILL after 5 s).
- **Spending cap.** `--max-budget-usd` is the last argument of every round's list; with `promptVia: 'stdin'` (next item), `--input-format text` follows it. A pilot round chooses the cap per round (`config.maxBudgetUsd`, USD 0.05 to 20.00 in whole cents, default 3.00); tool-less runs use 0.50. A run the runtime stops at the cap ends with a `result` event of subtype `error_max_budget_usd` (the name the 2.1.296 CLI uses for this case, read from its text, not yet seen in a live run; the stub sends that shape); it is `failed` with `failureReason: "budget"`.
- **What the cap covers.** The cap applies to each pilot process the Studio starts. It is not a ceiling on everything a pilot's shell can start: the pilot environment keeps `PATH`, `CLAUDE_BIN` and the sign-in reachable (below), the runtime has no environment variable for a budget, so a `claude` process that a pilot starts itself runs under the writer's sign-in with no cap, and its tool calls appear only inside the outer pilot's tool output, unaudited. The audit discards such a run after the fact (violation kind `runtime`, section 6); it cannot stop the process or see a start under a name built at run time. The approval summary states the cap per pilot, pilots × cap "for the pilot processes the Studio starts", and this limit in words; the settings card and the approval dialog repeat it.
- **Prompt on stdin (available, not used by rounds).** `buildArgs({promptVia: 'stdin'})` leaves the prompt out and appends `--input-format text`; `ClaudeRun` then writes the prompt to stdin and closes it. Rounds keep the prompt as the argument after `-p` until a live run confirms stdin delivery (`scripts/live-smoke.cjs --stage S1 --prompt-via stdin`). The 120 KiB prompt limit applies either way.
- **Environment** (`pilotEnv` in `claude-runner.cjs`): the parent environment plus
  - `TMPDIR` and `CLAUDE_CODE_TMPDIR` = `<folder>/.tmp`, so scratch space and temporary files are inside the folder;
  - `CLAUDE_CONFIG_DIR` = `<folder>/.tmp/claude-config`, created before the process starts, so the runtime's own files (for example a large tool output it saves under `projects/<cwd key>/<session>/tool-results/` and points the agent at) stay inside the folder;
  - `CLAUDE_SECURESTORAGE_CONFIG_DIR`, so the runtime still finds the writer's sign-in where it always is: a value the writer already set is kept, else the writer's `CLAUDE_CONFIG_DIR`, else the empty string (Claude Code 2.1.x reads empty as `~/.claude` for the credentials file and as "no suffix" for the macOS Keychain item name, exactly as when neither variable is set). Nothing is copied into the pilot folder; no credentials file is ever written there;
  - `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1` and `CLAUDE_CODE_DISABLE_CLAUDE_MDS=1`, so no memory or `CLAUDE.md` file reaches a blind pilot;
  - with the dedicated pilot token (section 3.4): `CLAUDE_CODE_OAUTH_TOKEN` = the token, and none of `ANTHROPIC_BASE_URL`, `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`, `ANTHROPIC_CUSTOM_HEADERS`, `CLAUDE_CODE_USE_BEDROCK|VERTEX|FOUNDRY`, `ANTHROPIC_MODEL`, `ANTHROPIC_DEFAULT_*_MODEL`, `ANTHROPIC_SMALL_FAST_MODEL`, `CLAUDE_CODE_SUBAGENT_MODEL` or the writer's own `CLAUDE_CODE_OAUTH_TOKEN` (`DROPPED_WITH_TOKEN` in `pilot-token.cjs`), so the pilot reaches Anthropic directly with the token and nothing else.

  `FINANCE_STUDIO_PILOT_TOKEN`, the companion's own source of the token, is always left out. Nothing else is added or removed. No API key is read, logged or forwarded explicitly. The child environment is otherwise not scrubbed; the audit is given the same environment so inherited path variables are resolved. The runtime writes its own `.claude.json` into `<folder>/.tmp/claude-config`. It can hold account metadata (in a test container: account and organisation ids and the email address; no tokens). A pilot can read it without a violation, and it stays with the private (0700) pilot folder. Tool-less runs and the sign-in check use the same environment.
- **What has been checked against the real CLI.** Stages S0 to S3 of `scripts/live-smoke.cjs` (section 11) on the writer's Mac with Claude Code 2.1.287 (2026-10-11), the pilot token from the Keychain: `claude --help` lists every option above; `claude auth status` in the pilot environment says signed in and reports the moved folder as its configuration folder; a tool-less haiku call under the token completed with the model asked for (S1); a pilot through the round flow saved its large tool output under `<folder>/.tmp/claude-config/projects/<cwd key>/<session>/tool-results/` (the key is built from the physical path, `/private/var/...` on macOS, and the file has a short random name, not the tool id the stub uses), ended with a CLEAN audit, and left no `sleep 900` behind (S2); and a pilot told to print `CLAUDE_CODE_OAUTH_TOKEN` found the variable unset, in two runs (S3, section 3.4). Still unconfirmed against a live run: that `--max-budget-usd` stops a pilot (no run has reached its cap; the stub's shape of that result is read from the CLI's text), that a prompt on stdin arrives intact, and the redaction against a runtime that does pass the token to the pilot's shell (shown only with the stub). A file-based sign-in (Linux) under the moved folder has not been checked on a real machine. Live Read, Write, Edit, Glob and Grep calls were inspected by stage S4 (section 11) on 2026-10-23: the parser extracted all six, and the Read outside the folder discarded the run.
- Prompt text for a pilot (`PILOT_PROMPT_PREFIX` in `rounds.cjs`): `The task materials are in ./filesystem. Save any files you produce to ./outputs. When you finish, give your answer in your final message. If a file you need is not in ./filesystem, say so in your answer; do not search elsewhere on this computer.\n\n` followed by the writer's prompt. The prefix is fixed by the companion. The prompt hash covers the writer's prompt only, and the approval summary has a line `Fixed prompt prefix sha256: ...`, so the approval hash covers the prefix as well. The approval record also stores `promptPrefixSha256`, the hash of the fixed text alone. If the Studio is updated and the text changes after a round was approved, the launch is refused with `APPROVAL MISMATCH: The Studio's fixed pilot text changed after this round was approved. Cancel this round, then freeze and approve it again. Nothing was started`. The approval summary view carries the text as `promptPrefix`, and the page shows it word for word under "Pilots also see this fixed text before your prompt", in the approval dialog and in the round facts on the Round card.
- Allowlists: models `claude-opus-5-5` (default), `claude-sonnet-5-5`, `claude-fable-5-1`, `claude-haiku-5-5`; efforts `low`, `medium` (default), `high`, `xhigh`, `max`.
- Other agent kinds use the same runner with `tools: []` (`--tools ""`), no folder content, and a prompt built by the server:
  - `grader-sim`: a **simulated** grader. Input is the guideline text and one answer. It returns JSON with `verdict`, `reason`. Always labelled "simulated grader, not Studio grading".
  - `author-review`: one tool-less analysis of the package text the page extracts (replaces the archived DeepSeek run, which stays in the tree, unlinked and unchanged). It returns text for the author to read, is never stored or classified, and never enters an export. Labelled "author review of the loaded package, not a blind pilot and not a score".

### 3.3 Stream parsing

`claude-runner.cjs` parses newline-delimited JSON. It records:

- the `system/init` event: resolved `model`, `tools`, `skills`, `mcp_servers`;
- every assistant `tool_use` block (name and input) for the audit;
- `tool_result` text only for the leak check (not stored in the summary);
- the final `result` event: `result` text, `num_turns`, `total_cost_usd`, `terminal_reason`, `subtype`, `is_error`, `modelUsage` keys;
- a stderr tail (last 4 KB).

A run is `completed` only if exit code is 0 **and** there is a `result` event with non-empty text. Otherwise it is `failed` (or `cancelled`) and carries a `failureReason`: `cancelled`, `spawn-error`, `timeout`, `budget` (the result subtype is `error_max_budget_usd`, whatever the exit code), `signal`, `no-exit-code`, `exit-code`, `no-result`, `error-result`, `empty-result`; the rounds add `setup-error` and `interrupted`. The page explains each in words. A cancelled run is `cancelled`. Requested versus resolved model is reported separately; a mismatch is an audit note (`model-mismatch`), never silently corrected.

**Redaction at the source.** `ClaudeRun` takes `redact` (the pilot token). Every stdout line is passed through it before it is written to the transcript, parsed or emitted, and so is the stderr tail; `[pilot-token redacted]` stands where the token stood. The summary counts the lines it changed (`redactions`), and the rounds turn a count above zero into a `secret` violation, because the token was in the runtime's output whatever the stored events show (a tool result is kept to 2000 characters).

### 3.4 Pilot sign-in: the dedicated token

A pilot does not have to run under the writer's own sign-in, and when the writer's own Claude Code goes through a gateway (settings that set `ANTHROPIC_BASE_URL` and `ANTHROPIC_AUTH_TOKEN`) it cannot: pilots load no settings (`--setting-sources ""`), so they would have no sign-in at all, and a pilot that did go through the gateway would test whatever the gateway serves, which the Studio cannot tell. The answer is a token of the writer's own Claude subscription, made with `claude setup-token`, that only pilots use (`backend/agents/pilot-token.cjs`).

- **Where it lives.** On macOS, the Keychain item `finance-studio-pilot-token` (`security add-generic-password -U -a "$USER" -s finance-studio-pilot-token -w`; the token is typed at the prompt, so it is in no shell history). On any system, `FINANCE_STUDIO_PILOT_TOKEN` in the companion's own environment, which wins over the Keychain because it is an explicit choice of whoever started the companion. `FINANCE_STUDIO_KEYCHAIN=off` makes the companion skip the Keychain (the tests set it through `tests/fixtures/clean-env.cjs`, so a token stored on a developer's Mac never reaches a test). Never in the repository, in `private/`, in a settings file or in a round record. The README stores it from the clipboard with a length check; the bare `-w` password prompt is not recommended, because pasted text arrived with the wrong content twice in testing (4 and 202 characters) and the sign-in check cannot tell.
- **How it is read.** `readPilotToken` runs `security find-generic-password -s finance-studio-pilot-token -w` (10 second limit; exit 44 means no item) at every pre-flight, and the companion reads it once more at start-up for one terminal line (`Pilot sign-in: …`). A token must be printable ASCII of 16 to 4096 characters. Errors name the place the token came from and never its text or any output of `security`.
- **Who gets it.** Only the processes the Studio starts: pilots, the sign-in check, simulated graders and author reviews, as `CLAUDE_CODE_OAUTH_TOKEN` (section 3.2), with the gateway, provider, model and other sign-in variables left out of their environment.
- **What keeps it out of the record.** The runner blanks it out of the stream before anything is parsed or written (section 3.3). The audit is given the value (`secretValues`) and discards a run that reads the environment (`environ`) or shows the token anywhere (`secret`, section 6); its report says "(the pilot token)" and every text it shows passes through the same redaction. After a run, the whole pilot folder (outputs, scratch space, the runtime's own files under `.tmp/claude-config`, the copied inputs) and the evidence copy under `private/agent-rounds/<round>/runs/<n>/outputs` are scanned, and the token is blanked out of any file that holds it and out of any file or folder name that holds it (the entry is renamed, a taken name gets " (2)", and the stored output list is redacted the same way; a link is reported and left alone); such a run is `DISCARDED` with the entries named as they are after the change (note `secret-redacted`). The output snapshot hashes are taken before that scan, so they describe the files as the pilot left them.
- **What it does not do, stated plainly.** The token is in the environment of the `claude` process. Seen live (macOS, Claude Code 2.1.287, smoke S3, in two runs): the environment of the shell the Bash tool starts did **not** contain `CLAUDE_CODE_OAUTH_TOKEN` (`printenv` printed nothing and exited 1), so a pilot's commands did not see the token in their own environment. That is the runtime's behaviour, not the Studio's doing, it was seen for one runtime version, and it leaves other paths: a process of the same user can read the `claude` process's environment (`ps -E` on macOS, `/proc/<pid>/environ` on Linux; the `environ` rule flags those), and a future runtime may pass the variable through. So the redaction and the audit stay as the Studio's own guarantee, and a pilot with network access that does obtain the token can still send it somewhere before the run ends. The audit discards such a run afterwards; it cannot stop it. A token that is sent away is compromised: make a new one with `claude setup-token` and store it again. A pilot can also use the token to start another `claude` process (section 3.2, "What the cap covers"), which the `runtime` rule discards after the fact. The sign-in check proves the runtime accepts the token, not that Anthropic does (section 3.1); the first model call does that. On a system that is not macOS and has no `FINANCE_STUDIO_PILOT_TOKEN`, pilots use the writer's own sign-in as before.

## 4. Data model (all JSON, schema `finance-agent-round` version 1)

```
Round {
  id: "rnd-<12 hex>", createdAt, label,
  packet: { sourceDir, files:[{path, sha256, bytes, role, include, overridden}], promptText, promptSha256, packetSha256, gafVisible:boolean },
  freeze: null | { version:1, frozenAt, sha256, contentSha256, gold:{ decision, figures:[{label, value, tolerance}] , notes }, fingerprints:[{ id, label, tokens:[string], figures:[{label,value,tolerance}] }], postHoc:false },
  config: { kind:"pilot", model, effort, count:1..5, tools:[...], maxBudgetUsd:0.05..20, concurrency:1..count },
  carriedFrom: null | "<earlier round id>",
  carried: null | { roundId, freezeVersion, postHoc, freezeSha256, contentSha256, packetSha256, promptSha256, gafVisible, config, content:{gold, fingerprints} },
  approval: null | { approvedAt, summarySha256, promptPrefixSha256, acknowledgements:["shell-access","network","isolation-by-audit"] },
  runs: [ Run ],
  status: "draft"|"frozen"|"approved"|"running"|"finished"|"cancelled"|"failed"
}
Run {
  id: "<roundId>-<n>", n, folder, state:"queued"|"running"|"completed"|"failed"|"cancelled",
  startedAt, endedAt, exitCode, signal, failureReason (null | section 3.3), requestedModel, requestedEffort, resolvedModel,
  numTurns, costUsd, terminalReason, stderrTail,
  toolCalls:{total,bash,file},
  audit:{ status:"CLEAN"|"DISCARDED", violations:[{tool,kind,path,call}], inputsModified:[string], notes:[string] },
  final:{ text, chars }, outputs:[{name,bytes,sha256}],
  classification: null | { suggested:{verdict,matches,fingerprints}, human:{verdict, fingerprintIds:[string], note, at} }
}
```

`contentSha256` hashes the gold and fingerprints only (no time stamp), so two freezes of the same content compare equal; `sha256` covers it as well as `frozenAt`. Freezes stored before this field are hashed on demand. `config.concurrency` is how many pilots run at once (default: all of them). A round stored before `maxBudgetUsd` and `concurrency` existed and not launched yet (draft, frozen or approved) gets them when the companion loads it: USD 3.00 per pilot and every pilot at once, the values its approval summary already showed, so it can be frozen again, approved and launched as it is. A launched round keeps the config it ran with. Approval refuses a round whose stored config `parseConfig` would change, because the launch refuses it (409, "Freeze again from the form, which creates a new round"). An approved round that no longer matches its approval (for example one approved by an earlier version over a different summary text) can never launch: cancel it, then freeze a new round from the form or start the next round from it; the launch refusal says so, and when the cause is a change to the fixed pilot text (section 3.2) it says that. Round views also carry `carryChanges` (`packet`, `prompt`, `gafVisible`, `settings`, `freezeContent`: what differs from the round it was carried from).

Persisted files per round under `private/agent-rounds/<roundId>/`: `round.json`, `freeze.json`, `packet.sha256`, and per run `runs/<n>/{transcript.jsonl, stderr.txt, run.json, outputs/}`. Transcripts are written as they arrive and never edited.

## 5. HTTP API (companion, `127.0.0.1` only)

All routes require `Host == 127.0.0.1:<port>`. All non-GET routes also require `Origin == http://<host>`, `Content-Type: application/json`, and header `x-finance-local == nonce` (the nonce comes from `GET /api/status`). Bodies are capped at 1 MB (packet inspection and round creation: 256 KB; they carry paths, not bytes). IDs match `^[a-z0-9-]{4,64}$`; any other value is a 400. No route echoes a filesystem path the client did not already send.

| Method and path | Purpose |
|---|---|
| `GET /api/status` | Existing fields plus `agents: { runtime: detectClaude(), maxPilotsPerRound, models, efforts }`, `nonce` and `pid` (this companion's process id). `GET /api/status?probe=1` answers `{ companion: 'finance-task-studio', pid }` at once; the full answer waits for runtime detection, which can run `claude --version` for up to 5 seconds. A later start asks with the probe (section 16, "Start"). |
| `POST /api/agents/packet/inspect` `{sourceDir}` | Lists regular files (no symlinks, depth ≤ 4, ≤ 150 files, ≤ 100 MB) with `{path, bytes, sha256, inferredRole, defaultInclude, reason}`. Rejects paths under the project root, under `private/`, that are not directories, or that are the home folder itself. The path may be pasted as a person copies it: surrounding quotes, Terminal backslash escapes and a leading `~` are undone first (`cleanSourcePath` in `pilot-folder.cjs`); a relative path is refused with a message that says to paste the full path of the unzipped task's `filesystem` folder. The text is cleaned once (`resolveSourceDir`), and every refusal, here and when a round is created, runs on the real folder it resolves to, which is the folder the round stores. |
| `POST /api/agents/rounds` `{label, sourceDir, include:[path], overrides:[path], promptText, gafVisible, config, carriedFrom?}` | Creates a round in `draft`. Computes hashes. `carriedFrom` (optional) is the id of an earlier round whose latest gold and fingerprints are recorded in `carried`, as `/next` does: 400 if it is not a round id, 404 if that round is unknown, 409 if it has no freeze. Nothing is frozen or approved by it. The page sends it when a form filled by **Start next round** is frozen. |
| `POST /api/agents/rounds/:id/freeze` `{gold, fingerprints}` | Writes `freeze.json`; status `frozen`. Refused after launch (use `/refreeze` for a post-hoc version). |
| `POST /api/agents/rounds/:id/approve` `{summarySha256, acknowledgements}` | `summarySha256` must equal the server's hash of the approval summary (so the writer approves exactly what will run). |
| `POST /api/agents/rounds/:id/preflight` | The launch pre-flight (section 3.1) without approving or starting anything. 200 `{ok, roundId, version, checkedAt, signIn, checks}` (`signIn` is one sentence on where pilots sign in from; `checks` has four lines) or 409 with the reason. |
| `POST /api/agents/rounds/:id/launch` | Requires `approved`. Verifies packet hashes again, runs the pre-flight, builds folders, starts runs (all pilots of the round at once by default; `config.concurrency` can ask for fewer, never above 5). Returns immediately. 409 while a simulated grader or author review is running. |
| `POST /api/agents/rounds/:id/next` | Start the next round from a frozen round: a new `draft` with the same source folder (listed again, so hashes are current), selection and overrides, prompt, gaf setting, config and label, and `carried` holding the earlier round's latest gold and fingerprints. Nothing is frozen or approved. The body carries nothing. 409 for a round without a freeze or a packet that can no longer be built as it was. |
| `GET /api/agents/rounds` / `GET /api/agents/rounds/:id` | Round state. Polled every 1.5 s. No transcript bodies. |
| `GET /api/agents/rounds/:id/runs/:n` | Run detail incl. final text and output list. |
| `POST /api/agents/rounds/:id/runs/:n/classify` `{verdict, fingerprintIds, note}` | Human classification. Allowed only if audit is `CLEAN`. |
| `POST /api/agents/rounds/:id/cancel` | SIGTERM all runs; state `cancelled`. |
| `POST /api/agents/rounds/:id/export` | Returns run-evidence JSON (section 8). |

| `POST /api/agents/grader-sim` `{guidelineText, answerText, model}` | One tool-less simulated grader run. Counts toward a separate cap of 5 per call batch. 409 while any round runs or is being launched (section 16). |

Errors: `{error: "<message>"}` with 400, 403, 404, 405, 409, 413, 415 or 500. A launch refusal for a changed packet is 409 with `PACKET HASH MISMATCH`. A wrong `Content-Type` is 415. An error the server did not expect is a generic 500 and the cause goes only to the terminal log; server folder paths are redacted from every message.

## 6. Audit (port of the field-tested checker)

`auditToolCalls(events, {folder, claudeConfigDir, env, companionPort, runtimeBin, secretValues})` is pure and always strict. For each assistant `tool_use` it inspects the tool input strings (for `Bash`: the command; for others: every string value) and reports `violations`:

- `abs`: an absolute path that is not inside the pilot folder and not allowlisted (`/dev/null`, `/dev/stdout`, `/dev/stderr`, and files directly under `/usr/bin`, `/bin`, `/usr/local/bin`, `/usr/sbin`, `/sbin`; these directories may be read and run, never written). A program directly in `/opt/homebrew/bin` or `/opt/homebrew/sbin`, or inside a macOS application bundle, `/Applications/<Name>.app/Contents/MacOS/<program>`, may be run as the command word of a shell command (for example Homebrew's `python3` or LibreOffice's `soffice`) and nothing else. As an operand (`cat`, `cp`, `rm`, `tee`), a redirect target, the path of a file tool or part of code text, the same path is an `abs` violation like any other, and so is any other use of a path in a bundle. URLs are stripped first. Symlinks are resolved with `fs.realpathSync` when the path exists.
- `bare-root`: `ls /`, `find / ...`, `cd /` and similar commands that take bare `/` as an argument. In code text (see "Code text" below) it is also `find /` written in a code string, a quoted glob that starts at the root with a wildcard (for example `'/**/*.xlsx'`), and `os.walk`, `os.listdir`, `os.scandir`, `glob` and the like given `os.sep`, `os.path.sep` or `'/'`.
- `dotdot`: `..` segments are resolved against a **tracked working directory**. The tracker starts at the folder and follows `cd` in each Bash command. Only a resolved path outside the folder is a violation. In code text, a quoted `'..'` or `".."` counts only as a positional argument, or a path keyword argument (`path=`, `dir=`, `top=`, `directory=`, `folder=`, `file=`, `filename=`, `root=`, `cwd=`), of a call that takes a path: `listdir`, `chdir`, `scandir`, `walk`, `setwd`, `readdir`, `opendir`, `glob`, `abspath`, `realpath`, `normpath`, `Path`, `open`, `list.files`, `file.path`, `Dir.entries`, and `join` or `resolve` of `path` or `os.path` (with close variants such as `readdirSync` and `rglob`). It then counts as `..` from the tracked working directory. As a data value (`na_values='..'`, a cell value, `split('..')`) it is not flagged. When that call also uses `__file__` or `__dirname`, the base is the script's folder and not the working directory, so the run gets an `unverifiable-path` note (second wording, below) and no violation. `os.pardir`, `os.path.pardir` and `from os import pardir` count; the bare word `pardir` does not. `Path.cwd().parent` and `dirname(os.getcwd())` count as `..` from the tracked working directory, and `Path.cwd().parents` is always a `dotdot`. In a shell command, `$(dirname $PWD)` and `$(dirname "$PWD")` are the parent of the tracked working directory, and `$PWD/..` is resolved from it; when the working directory is not known, `$PWD/..` is a `dotdot`.
- `home`: `~`, `$HOME`, `${HOME}`, `$OLDPWD`.
- `harness-spill`: an absolute path under the writer's own Claude configuration directory (`claudeConfigDir`: the writer's `CLAUDE_CONFIG_DIR`, else `$HOME/.claude`; never the pilot's moved one), for example the large-output files the runtime would point an agent at if its configuration were not moved. It is a violation like any other path outside the folder; the kind only explains the cause so the writer can read the report. The pilot's own `<folder>/.tmp/claude-config` is inside the folder, so with the moved configuration (section 3.2) such spills are clean.
- `loopback`: a tool input that reaches for this machine over the network. The companion answers every local process and its rounds hold the gold, so this discards the run. Loopback is `127.0.0.0/8`, `localhost` (and `*.localhost`, `localhost.localdomain`, `ip6-localhost`), `::1`, `[::1]`, `::ffff:127.x.y.z` and `0.0.0.0`; the companion's own port (`companionPort`, handed over by the server after it listens) counts with any host. Flagged: a URL with a loopback host (any scheme but `file:`; in a URL host also `127.1`, `2130706433`, `0x7f000001`, `0`), `host:port` with a loopback host (also a port built at run time), a quoted loopback host string, `127.a.b.c` or `0.0.0.0` written out, `/dev/tcp` and `/dev/udp` to a loopback host or the companion port, a line naming a network client together with `localhost`, a shell word that is only a loopback host (`curl localhost`, `H=localhost`), and the companion port as `:<port>`, `port=<port>`, `port: <port>` or a URL port. Not flagged, by decision: the bare word `localhost` in prose (a sentence in a written file, an echo of a sentence, a here-document line that names no network client), remote URLs, other ports, and the companion port as a plain figure. `companionPort` must be a whole number from 1 to 65535 or null; anything else throws, and a throwing audit discards the run. At most 50 loopback findings are examined per text and per call.
- `bare-cd`: `cd` with no argument.
- `machine-search`: a tool input that searches the whole computer for files, which a pilot that is missing a file might try. Flagged in a shell command: `mdfind`, `locate`, `plocate`, `slocate` or `mlocate` as a command, at the top level, behind a wrapper (`sudo`, `time`, `nohup`, `env`), after `xargs`, `watch` or `find -exec`, inside `$( )` or backticks, in `bash -c`, in `eval` and in here documents. Flagged in code text: the same names as a program (a quoted `'locate'`, a quoted command that starts with one and an option, the command string given to `system`, `popen`, `subprocess`, `exec` or `spawn`, `$(locate ...)`, `xargs locate`). Not flagged: the word in a sentence, `command -v locate`, `which locate`, `grep locate x.txt`, `echo mdfind` and a quoted "locate the totals".
- `runtime`: a tool input that starts the agent runtime again. Such a process runs under the writer's sign-in with no `--max-budget-usd` cap (only the process the Studio starts gets one) and its tool calls are never audited. `auditToolCalls` takes `runtimeBin` (the runtime the round started, `live.bin` in the store; an absolute path or null, anything else throws). Flagged: in a shell command, any word whose value after expansion is the runtime, that is a last path segment `claude` (any case, also `claude.exe`), or the `runtimeBin` path, its real path or, as a bare name, its file name. Any word counts, not only the command name, because `xargs`, `find -exec`, `watch` and the like start their arguments (so `which claude` is flagged too); `$CLAUDE_BIN -p` and `C=claude; $C` are seen through expansion. In any text of any tool (the command, inline code, a file a pilot writes, a description): `claude` followed by an option (`claude -p`, `/usr/local/bin/claude --print`), a quoted `'claude'` or quoted path ending in `/claude` (how code names a program for `subprocess`, `spawn` or `execFile`), `@anthropic-ai/claude-code`, and the `runtimeBin` path. Not flagged: `claude` in a sentence ("prepared with Claude"), names that only contain it (`claude-config`, `claude_notes.txt`, `.claude`). Not seen: a start under a name built at run time or through a copy whose name the call does not show. The Studio does not put a `claude` that refuses to start first on the pilot's `PATH`: the pilot could change `PATH` back, and such a shim could not be checked against the live runtime here; the audit is the check.
- `environ`: a tool input that reads the process environment, which holds the pilot's sign-in (section 3.4) and whatever the writer's shell exported, and which no finance task needs. Flagged in a shell command: `env` with nothing to run after it (only options, their values and `NAME=value` words; also behind `nohup`, `time`, `timeout 5`), `printenv` anywhere in the command (also after `xargs`, `find -exec`, `watch`), a bare `export` or `export -p`, `declare`/`typeset` with no name (bare, `-p`, `-x`), a bare `set`, `compgen -e|-v|-A export|-A variable`, `ps` with an `e` in a BSD style option word (`ps e`, `ps axeww`; only when no dash option precedes it), `ps -E`, a `ps` format naming `env`, and `launchctl getenv|export`. Flagged in any text of any tool: `/proc/<pid>/environ`, the names `CLAUDE_CODE_OAUTH_TOKEN`, `FINANCE_STUDIO_PILOT_TOKEN`, `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`, code that reads the environment (`os.environ`, `process.env`, `getenv(`, `System.getenv`, `%ENV`, `$ENV{`, Ruby `ENV[`/`ENV.fetch`, `os.Environ(`, `std::env::`, `Sys.getenv`, `Environment.GetEnvironmentVariable`) and `${!name}`. Not flagged: `env python3 x.py`, `export NAME=value`, `set -e`, `ps aux`, `ps -ef`, `ps -C sleep`, and the words env or environment in prose.
- `secret`: the pilot token itself (`secretValues`: strings of at least 8 characters, anything else throws), in plain or JSON-escaped form, or the runner's marker `[pilot-token redacted]`, in any tool input, tool result, assistant text or final answer; and a read of a credential store: `security find-generic-password|find-internet-password|dump-keychain|export|find-key`, or the names `finance-studio-pilot-token`, `Claude Code-credentials`, `.credentials.json` in any text. The report says "(the pilot token)", or "(the pilot token in a tool result | the final answer | the assistant text)", and every path and call text in the report passes through the same redaction, so the report never holds the value. The rounds add two more sources of this kind: the runner's own redaction count (the token was in the output whatever the kept events show) and the files scan after the run (`(the pilot token in a file)`, the files named in `call`).

**Code text.** The rules above marked "in code text" run only on text that is a program: a Bash code string (`python -c`, `node -e`, `Rscript -e`), a here document fed to an interpreter or written to a file with a code extension, and what a file tool writes to a file with a code extension (`.py`, `.sh`, `.R`, `.js`, `.ts`, `.rb`, `.pl`, `.ps1` and the like) or that starts with a `#!` line. What `echo` or `printf` prints is code too when it goes into an interpreter (`echo "..." | python3 -`) or to a file with a code extension (`echo "..." > outputs/s.py`, `| tee outputs/s.sh`), and so is a here document piped into an interpreter (`cat <<'EOF' | python3 -`); an interpreter given a script file or an inline program (`-c`, `-e`) reads its piped input as data. What is written to any other file (`.csv`, `.json`, `.txt`, `.md` and the like) is data and keeps only the checks it had before: a statistical table can hold a quoted `".."` for "not available", and that is not the parent folder. A `'..'` that resolves to a folder inside the pilot folder (after `cd filesystem`) is not flagged.

**Implementation notes (as built).** The audit tokenises shell commands (quotes, substitutions, here-documents, subshells, redirects, `bash -c`, `eval`), splits on unquoted `$IFS`, expands brace words such as `{cat,/etc/x}`, and tracks `cd`, `cd -`, `pushd`/`popd` and `$PWD`. A word is a URL only when it has a real host and nothing left to expand; `x://../..` is a relative path. It accepts `env` (the environment the pilot actually received, so `$VAR/path` is checked for inherited variables), `budgetMs` and `clock`. Work is bounded and **fails closed**: a call that cannot be analysed is a violation, not a pass. Notes that never discard a run: `unverifiable-command`, `unverifiable-code`, `unverifiable-input`, `unverifiable-path` (an argument or a redirect target built wholly from a variable the command did not set, or from command output, so the audit cannot check it; not noted for the arguments of `echo`, `printf` and the other commands that only print their words, `grep`, `sed` and `awk` patterns, the variable of a `for` loop, a process substitution, `$?` `$#` `$$` `$!`, an arithmetic expansion, and the arguments of `[`, `test`, `sleep`, `exit` and the like; the second wording is for code that builds a path from `__file__` or `__dirname` and a `..`, whose target depends on where the script is), `cwd-unresolved` (relative paths after an unresolvable `cd` are not checked). The audit remains a heuristic: paths built at run time, shell functions and aliases, and encoded text passed to a shell can evade it. The UI and README say so.

Must **not** be flagged: `sed -n '/a/,/b/p'` style address ranges, division such as `a / b`, `x/y` inside Python, remote URLs, `/dev/null`, `localhost` in prose, `find / replace` in prose, a quoted `".."` in a data file, and a quoted `".."` used as a data value in code (`na_values='..'`).

The folder's own `.tmp/` is inside the folder, so it needs no special case. A run whose only violations are `harness-spill` is still `DISCARDED`; the UI explains the cause and the writer can re-run it.

Additional audit notes: `inputs-modified` (a solver file's sha256 changed at the end), `model-mismatch`, `leak-in-results` (a tool result mentioning the project root or `private/`), `secret-redacted` (the pilot token was blanked out of named files after the run) and `secret-scan-skipped` (a file too large or unreadable to scan for it).

Fixtures for the tests use these patterns: `cd ../../other` from a folder two levels deep is a violation; `cd /tmp/x/filesystem; ... > ../out.txt` is **not** a violation when `/tmp/x` is the folder; a Read of a file under `claudeConfigDir` is a `harness-spill` violation; a write to `<folder>/.tmp/a.txt` is clean; a Read of a spill file under `<folder>/.tmp/claude-config` is clean; `curl http://127.0.0.1:<port>/api/status` is a `loopback` violation; `claude -p x`, in a Bash call or in a script a pilot writes, is a `runtime` violation. The audit cannot see a host assembled at run time, the machine's own host name or LAN address, or an unquoted bare `localhost` on a line that names no network client.

## 7. Classification (assistive, never final)

`classify.suggest(freeze, finalText, outputsText)` returns tokens found and `verdict` in `matches-frozen-gold | fingerprint | unclear`. The verdict is decided from the final answer only (figures, decision keywords, fingerprints). The output files are searched too, but only to say where a gold figure appeared (`where` is `final`, `outputs` or null): a figure, a decision keyword or a fingerprint that is found only in the output files does not count. Numbers match with the freeze tolerance after stripping thousands separators, currency signs and a trailing `%` or `x`; `(1,200)` reads as -1,200. A verdict of `matches-frozen-gold` requires every gold figure in the final answer, plus at least one keyword when the writer supplied `gold.decision`. A decision keyword does not count when `not`, `no`, `never`, `cannot` or a word ending in `n't` stands within the three words before it in the same clause, or when `avoid` stands directly before it (further back it opens a purpose clause, as in "To avoid default, refinance"). A comma, colon, semicolon, full stop, `!`, `?`, a dash with spaces around it or a new line ends the clause, so "No, reject the proposal." is an answer and not a negation. A gold figure written as a bare single digit (`3`, `-4`; not `3.0`, `2.0x` or `5%`) is weak evidence; it is judged by how it is written, not by its value. Its entry carries `weak: true`, and when every gold figure is weak and no decision keyword confirms them the answer is not a match. A fingerprint hit requires all of that fingerprint's tokens or figures in the final answer. A `reason` sentence explains anything that was seen and left uncounted. The result is labelled "heuristic" in the UI. The human verdict is the one stored and exported.

## 8. Evidence export

`export` returns an array of records accepted by `candidate-engine.js` `logs()` and by `core.js` `validateExperiment`:

```
{ runId, date, model (resolved), versions:{prompt,workbook,evaluator}, sourceFingerprint, score:null, scoreMax:null,
  kind:"local-blind-pilot", audit:"CLEAN", classification:"no-root-failure"|"model-error", rootFailures:[fingerprint ids],
  evidence:"private/agent-rounds/<id>/runs/<n>", notes:"Local blind pilot, directional, n=<k>, GAF visible=<bool>, freeze <sha>" }
```

`DISCARDED` runs are exported only in a separate `discarded` array. The experiment's `snapshot` equals `core.snapshot(project)` at export time.

## 14. Privacy scan: block pushes that carry task content

`scripts/privacy-scan.cjs` is generic. Its term list is **not** in the repository: it reads one term per line from `private/privacy-terms.txt` (lines starting with `#` ignored; a term wrapped in `/.../i` is a regular expression, anything else is a case-insensitive literal). It fails closed: if the file is missing or empty it exits non-zero with the message `no privacy term list: refusing to pass`.

- It scans every tracked file and every untracked file that git does not ignore (text files only), and with `--range <base>..<head>` also the added lines of the commits about to be pushed. In a linked worktree that has no `private/privacy-terms.txt`, it uses the main checkout's term list (the directory above the git common dir).
- **Binary files are blocked unless allowed.** A binary file cannot be scanned for terms. A tracked file, an untracked file that git does not ignore, or (with `--range`) a file that any commit in the range adds or changes, is blocked when the scan sees its content as binary and its exact repo path is not a line of `scripts/binary-allowlist.txt`. Binary means a NUL byte in the first 8 KB, content that starts with `%PDF-`, `PK\x03\x04` or `\xD0\xCF\x11\xE0`, or content that is not valid UTF-8; the range check classifies every blob that a commit adds or changes itself. In the allowlist, blank lines and lines starting with `#` are ignored, there are no wildcards, and a line is an exact path, optionally followed by `sha256=<hex>` to pin the content. An allowlisted `.png` must really be a PNG, and `tests/fixtures/package.zip` is pinned by its hash, so a path cannot be reused for another kind of file. The work tree check reads the file from the work tree; the range check reads it from the head commit of the range, so a push can only allow what it publishes, and the line has to be committed in the same push as the file.
- **Ignored files are blocked.** A tracked file that `.gitignore` ignores is blocked, and with `--range` so is any path that a commit in the range adds or changes and that `.gitignore` ignores. The scan prints `IGNORED <path>`; the fix is `git rm --cached <path>`, and the summary counts `ignored blocked`. Task packages (xlsx, docx, pdf, zip) and the app's exports must never be listed. A file over 5 MB is binary when its first 8 KB hold a NUL byte; any other file over 5 MB is reported as skipped.
- It prints `file:line` and the matched term index, never the full line, and exits 1 on any hit. For each blocked binary file it prints `BINARY <path> (<why>) is not on scripts/binary-allowlist.txt` and also exits 1. The summary line says `binary allowed` and `binary blocked`.
- `npm run privacy` runs it. The pre-push hook runs it through `scripts/pre-push.cjs` and blocks the push. The hook is versioned as the shim `.githooks/pre-push`; a clone turns it on with `npm run setup` (`scripts/setup-hooks.cjs`), because hooks themselves are not versioned. Setup copies the shim to the common hooks folder, `$(git rev-parse --git-common-dir)/hooks/pre-push`, so every branch and worktree uses it; the shim runs the `scripts/pre-push.cjs` of the checkout being pushed from and blocks the push if `node` or that script is missing. Setup sets no `core.hooksPath` (it unsets one that is `.githooks`), and refuses to overwrite a different pre-push hook unless `npm run setup -- --force` is used, which keeps the old one as `pre-push.replaced`. The manual hook (a `.git/hooks/pre-push` that runs `node scripts/pre-push.cjs "$@"`) still works. `Start Finance Task Studio.command` prints `Privacy hook not installed: run npm run setup once` when no pre-push hook is where git looks for this checkout's hooks, and only when its folder is the top of a git checkout.
- `.gitignore` also keeps the app's own exports and task documents out of git: `*[_-]PRIVATE.*` (so `*_PRIVATE.*` and `*-PRIVATE.*`), `*-project.json`, `/LOCAL_SERVER.json`, `/LOCAL_SERVER.lock*`, and these document, archive and data extensions in any letter case: `xlsx`, `xlsm`, `xlsb`, `xls`, `xltx`, `xltm`, `docx`, `docm`, `doc`, `dotx`, `pdf`, `zip`, `pptx`, `pptm`, `ppt`, `odt`, `ods`, `odp`, `rtf`, `numbers`, `pages`, `key`, `7z`, `rar`, `gz` and `csv` (all but the synthetic files under `tests/fixtures`), `/tmp/`, `/.claude/settings.local.json` and `/FILEBASE_MANIFEST.json`. `npm run package` (`python3 scripts/package-filebase.py`) writes the manifest and two ZIPs next to the repository, from tracked files only, under the `finance-task-studio/` prefix; it refuses symlinks, needs a git checkout (and says so otherwise) and warns when the work tree is dirty. `npm run build` no longer needs python3.
- Tests use a synthetic term list passed with `--terms <file>`; they never read `private/`.

## 16. As built: response shapes and behaviour the contract left open

These are the shapes the page and the tests rely on. A change to any of them needs a change to `agents.js` and `tests/agents-server.test.cjs`.

- **Lists and rounds.** `GET /api/agents/rounds` returns `{rounds: [row]}`, newest first, where a row has `id, createdAt, label, status, carriedFrom, config, packetSha256, freezeSha256, gafVisible, runCount, counts`. A round view (every round route) has the section 4 fields plus `postHocFreezes`, `carryChanges`, `counts` and `directional`. Its `runs` are rows: `audit` is `{status, violationCount, inputsModified, notes}`, `final` is `{chars}`, `classification` is `{suggestedVerdict, humanVerdict}`, and a failed run has its `failureReason` (section 3.3). The full record (final text, violations, outputs, `classification: {suggested, human}`) comes only from `GET .../runs/:n`.
- **Approval.** While a round is `frozen` or `approved`, its view also carries `summarySha256` and `approvalSummary` (`text, summarySha256, commandLine, workingFolder, promptPrefix, model, effort, count, tools, maxBudgetUsd, concurrency, packetSha256, freezeSha256, gafVisible, overrides`; the last two settings are null when the stored round lacks them; a round that has not been launched gets them when it is loaded, section 4). The page approves by sending that hash back, so the server checks it against a hash of the summary it computes again. The command line is built by the server and has the prompt elided. `promptPrefix` is the fixed text of section 3.2, which the page prints word for word (null from a service that does not send it); the summary text itself carries its hash.
- **Suggestion.** `classification.suggested` is `{verdict, matches: [{label, value, found, where, weak?, reason?}], fingerprints: [{id, label, hit, tokensFound, figuresFound}], decision, reason?, label: "heuristic", freezeVersion, freezeSha256}`. Only fingerprints with `hit: true` are candidates. `reason` is present only when something was seen and left uncounted (section 7).
- **Export.** `POST .../export` returns `{schema: "finance-agent-round-export", roundId, records, discarded, excluded, notes, freeze, directional, gafVisible}`. The page stamps each record with the project snapshot before it validates it with `core.validateExperiment`.
- **Client keys.** Keys such as `bin`, `args`, `folder` and `env` in any body are ignored. A tool list that differs from the fixed one is refused with 400.
- **Extra HTTP rules.** A GET with a foreign `Origin` header is 403. Every response carries `X-Frame-Options: DENY`. While the server shuts down, new requests get 503.
- **Start.** `runCompanion` in `server.cjs`. The default address is `127.0.0.1:47321` (`DEFAULT_PORT`), so the browser's per-origin work (the project and the Agents draft) comes back at the next start. If `FINANCE_STUDIO_PORT` is unset or empty and that port is busy (EADDRINUSE), the server listens once more on a free port and prints "The usual port 47321 is busy, so this start uses another address. Work saved in the browser by earlier sessions (the project and the Agents draft) will not show at this address." A `FINANCE_STUDIO_PORT` that is set, `0` included, is used as given; if it is busy, as with any other listen error, the start prints "Finance Task Studio could not start: ..." and exits 1. One companion runs per folder. Before anything is loaded, and before the agent service exists (creating it recovers the rounds of a dead companion and stops the pilots it left, which must never happen to a companion that is still running), `claimStart` claims the folder and `findRunningCompanion` reads `LOCAL_SERVER.json`. The claim is `LOCAL_SERVER.lock` (gitignored), created exclusively (flag `wx`) and holding the pid, so two starts at the same moment give one companion. A lock whose pid is dead, or that holds no pid and is more than 2 seconds old, is taken over. The lock is removed when the companion exits and when a start gives up; delete it by hand only if no companion runs. A start that finds the lock held waits up to 10 seconds (`LOCK_WAIT_MS`) for the other start to come up, then refuses with exit 1. The record is stale, and the new start overwrites it, only when it has no usable pid or names this process, its pid is dead (signal 0; EPERM counts as existing), the connection to its url is refused, or its url answers `GET /api/status?probe=1` as a companion with a different pid. If the url answers as a companion with the recorded pid, the second start prints "Finance Task Studio is already running at <url>", opens that url when `--open` is given (`npm start` and the launcher give it), starts nothing and exits 0. Anything else with a live pid (no answer within 5 seconds, `STATUS_TIMEOUT_MS`; another connection error; an error status; something that is not a companion) refuses the start with exit 1, because a slow companion must not be taken for a dead one: a start that went on would recover its rounds and kill its pilots. The message names the process and the url and gives two ways out: close that companion (Control-C in its window), or delete `LOCAL_SERVER.json` if none is running. After listening the server writes `LOCAL_SERVER.json` (`url`, `pid`, `startedAt`, `modelCallsOnLaunch`) and prints the address, the fallback line when there is one, `Pilot sign-in: ...` and "Keep this window open while a round runs; closing it stops the companion and its pilots."
- **Shutdown.** On SIGINT, SIGTERM, SIGHUP (the Terminal window was closed) or SIGQUIT the server cancels the archived adapter and every running round, waits for the processes to stop, removes `LOCAL_SERVER.json` if it still records this pid and gives back `LOCAL_SERVER.lock`, then exits 0. A second signal exits at once (128 plus the signal number); a shutdown still unfinished after 20 seconds exits 1. Pilots run in their own process group, so Ctrl-C reaches them only through this handler. A hook on the process `exit` event is the last resort: whatever ends the process (an uncaught exception, the forced exit), it sends SIGKILL to the process group of every pilot, simulated grader and author review that is still running (`killPilots`, `RoundStore.killPilotsNow`; synchronous, nothing awaited) and removes `LOCAL_SERVER.json` if it still records this pid and `LOCAL_SERVER.lock`. A SIGKILL of the server cannot be caught, so running pilots keep running until the next start (see Launch).
- **Launch.** A launch with no `claude` found, or a failed pre-flight, is refused with 409 and the round stays `approved`. Only one round runs at a time. A round that was running when the server stopped is marked interrupted on the next start. While a pilot runs, `run.json` holds a `pilot` record (pid, whether it leads its own process group, spawn time, runtime binary); it is removed when the run ends and is in no view. At the next start a run that is still `running` with such a record has its pilot stopped with SIGKILL (the whole group when it led one), but only if `ps` shows that pid alive and, for a group, a process group id equal to the pid; a whole word of its command line (split at white space) is the recorded runtime binary or has exactly its file name; and `ps etime` puts its start within 10 seconds (`BINARY_MATCH_SLACK_MS`) of the spawn time recorded with the pid. The number can be handed to an unrelated program once the pilot has ended, so when any of these cannot be established, nothing is killed. The run then gets "A pilot process left over from the previous companion was stopped at startup." on its stderr tail. Either way the run ends `failed` with `failureReason: "interrupted"`.
- **Blindness while a round runs.** A pilot has a shell on this machine and can reach the companion like any local process (the nonce is in `GET /api/status`). While any round is `running`, every route that answers with round data (the list, a round, a run, and the POST answers of create, freeze, `/next`, refreeze, approve, launch, cancel and classify) is passed through `redactRoundData` in `server.cjs`. Each freeze record shrinks to `{sha256, frozenAt}`. `gold`, `fingerprints`, `promptText`, `approvalSummary`, `summarySha256` and `sourceDir` are removed wherever they appear. A run's `final` becomes `{chars}`. `classification.suggested` keeps `verdict, label, freezeVersion, freezeSha256` and `classification.human` keeps `verdict, at, freezeVersion, freezeSha256`. The answer carries `redacted: true`. The freeze answer alone keeps the approval summary and its hash, so the next round can be frozen and approved while another runs. If the round list cannot be read, the server redacts. The full view returns when the round ends. Known gaps, not closed yet: `GET /api/status` still returns the archived adapter's state (including its result text), because `dashboard.js` keeps the polled snapshot; the export is not redacted (it carries fingerprint ids and the writer's classification notes, no gold); and the write routes (cancel, freeze, refreeze, classify) still accept a request carrying the nonce. Their answers are redacted, and the audit discards a pilot that reaches the companion.
- **Overlap.** `POST /api/agents/grader-sim` and `/author-review` answer 409 while any round runs or a launch is in flight, because their text would be on a command line a pilot can read; a launch answers 409 while one of them is in flight. Each side counts itself in before it checks the other. The service applies the same rule again.
- **Companion port.** After `listen()` the server calls `service.setCompanionPort(port)` when the service has it (anything but 1..65535 is a 400). The store passes it to the audit as `companionPort`.
- **Pilot sign-in.** `createAgentService` takes `pilotToken` (use this token) and `readPilotToken` (replace the Keychain and variable read) for tests; otherwise the store reads the token at every pre-flight (section 3.4). The pre-flight answer carries `signIn`, which the page appends to its "Claude Code is ready" notice. `runCompanion` prints one `Pilot sign-in:` line at start-up (`describePilotSignIn` in `server.cjs`): where the token comes from and which gateway variables are left out, that a stored token cannot be used, or that pilots will be refused because the environment sets a gateway variable and no token is stored. A run's `audit.violations` can carry `tool: "(runtime output)"` (the runner's redaction count) and `tool: "(files)"` (the files scan) with kind `secret`.
- **Test isolation.** The browser test copies the files it needs to a temporary folder and runs the companion from there, so round state is written under that copy and the project's own `private/` folder is neither read nor written.
- **Archived adapter.** `--run-approved-once` still starts the archived one-run analysis, and nothing else does. `LOCAL_SERVER.json` records `modelCallsOnLaunch: 0` unless that flag was given. The companion removes the file when it shuts down (see Shutdown).

## 17. Mode ideas: the failure-mode idea generator

### 17.2 The catalog

`idea-archetypes.js` sets `FinanceIdeaArchetypes = {version: 1, archetypes, kinds}`: 44 archetypes, `ia-01` to `ia-44`, in six kinds (`base-or-definition`, `timing-or-date`, `scope-or-classification`, `source-conflict`, `arithmetic-or-structure`, `instruction-or-presentation`). An archetype has `id`, `name`, `kind`, `mechanism` (one of the 14 research-catalog ids; the research catalog and its 20, 14 and 16 counts are not changed), `summary`, `whyItHolds` (written so that it can fill a governing rule), `buildMoves` (a few imperative sentences), `wrongApproach`, `correctTreatment`, `detection` and `consequence` (phrases spliced after "A tempting mistake is to ", "The correct treatment is to ", "To check it, " and "If missed, ", as `FinanceCore.generateGuidance` splices them), `howSolversGoWrong`, `needs` (what a task must contain for the idea to be buildable), `signals`, `workflowHints`, `lead`, `supporting` and `causalGroup` (`cg-` plus the id, so two ideas from one archetype count as one causal root).

The catalog is authored for this tool in generic finance vocabulary. It carries no workbook content, no figure, no statistic and no proper noun, and a check kept outside the repository compares its text with the private precedent rows for shared wording (`VERIFICATION.md`). The only guidance beyond the text is qualitative: `lead` marks the recipes the catalog lists first (the authority-gate recipes and those that let one wrong figure feed the whole headline) and `supporting` marks secondary layers. Every sentence passes `lintIdea`, and the signals compile, are lowercase and stay fast on 200 KB of text (`tests/idea-archetypes.test.cjs`). `signals` is `{terms, regex, needsAll?, negative?}`: a term is a lowercase stem or phrase that matches at the start of a word of the normalised text (`supersed` finds `superseded`), `regex` holds sources compiled case-insensitively, `needsAll` terms must all be found before the archetype can be proposed and a `negative` term rules it out. The same signals serve twice: to find where an archetype could attach in a package, and to label rows of a precedent workbook.

### 17.3 The precedent workbook (library CSV)

`parseLibraryCsv(text, {maxBytes = 5e6, maxRows = 5000})` reads RFC 4180 text: quoted fields with commas, doubled quotes and any newline inside quotes, LF, CRLF or CR between rows, a UTF-8 byte order mark stripped, blank rows skipped. It throws only on a non-string or a text over `maxBytes` (UTF-8 bytes); anything else is reported. It returns `{rows, rejected, hash, columns, warnings}`:

- `rows` is `[{id, workflow, trap, built, fell, score, scoreText}]`. `id` is `p-0001`, `p-0002` and so on in file order among the rows kept. `scoreText` is the score cell trimmed and otherwise exactly as written; `score` is its number when it is a plain decimal (an optional sign, digits, an optional fraction) and `null` otherwise, and the row is kept. Cells are cut at 4,000 characters (counted in a warning); reading stops at `maxRows` data rows (a warning says so).
- `rejected` is `[{line, reason}]`: a row with no trap title, and a quote that is never closed (the rest of the file was read as one cell, which the reason says). At most 500 are listed; the rest are counted in a warning.
- `warnings` (at most 50) name a missing column, a score that is not a plain number (the first 20 by line, then a count), cut cells and the row cap.
- `columns` is `{workflow, trap, built, fell, score, count}`: the index of the cell each field was read from. `hash` is the SHA-256 of the text as passed in, from a synchronous implementation inside the model because `FinancePackageEngine.sha256` is asynchronous. It tells the page whether the workbook changed since the ideas were made.

Headers are compared after lowercasing and turning every run of other characters into one space; the first matching header cell wins for each field, the order of the columns is free and other columns are ignored. The aliases for `workflow` and `trap` must match the whole header: `workflow`, `task workflow`, `workflow name`, `workflow label`; `trap` (required, since no row is read without it), `trap name`, `trap title`, `failure mode`, `failure mode name`, `failure mode title`. The other three match the beginning of the header, so words after the alias (a parenthetical, for example) are allowed: `built` (`what the writer built`, `what writer built`, `writer built`, `built`, `writer`, `description`); `fell` (`how the model fell`, `how model fell`, `how new model fell`, `how it fell`, `fell`, `grader`; a header that names a score or a mean is not `fell`); `score` (`score`, `mean`, `model mean`, `new model mean`, `the model mean`, `avg score`, `average score`, `avg mean`, `average mean`). A missing optional column is a warning and an empty text.

### 17.4 Labels and retrieval

`labelRows(rows, archetypes)` returns `{labels: {rowId: {archetypeId | null, matched, runnerUp?}}, coverage: {labelled, unlabelled}}`. For each row it finds the signals of every archetype in the trap (weight 3), what was built (1) and how it went (1); every distinct term found in a field adds that field's weight and so does every regex hit. An archetype is ruled out by a `negative` term or an unmet `needsAll`. A row gets the top archetype only when that archetype scores at least 3 and beats the runner-up by at least 2; otherwise it gets `archetypeId: null`. Unlabelled is an accepted answer: the labels only help retrieval and are not shown anywhere, so a wrong or missing label costs a worse choice of precedents, never a wrong claim.

`retrieve(rows, query, options)` ranks rows by TF-IDF cosine over the trap (counted twice), the workflow and what was built, using lowercase ASCII words, stop words and bare numbers removed and light stemming (plural, `ies`, `ing`, `ed`, a final `e`). `buildIdeas` builds the query from the archetype (name, summary, why it holds, wrong approach, workflow hints) and the task (workflow and the first 1,000 characters of the description). A row whose label equals the archetype is boosted and kept even without shared words, and a row in the same workflow gets a smaller boost. It keeps the three nearest; ties go to the lower row id. The similarity and the reason it returns are internal and never printed.

### 17.5 Ideas: status, order and the display of recorded scores

- **Call.** `buildIdeas({mode: 'new' | 'existing', task: {workflow, description}, pkg, project, library, archetypes, now, limit})` returns `{ideas, inputs, notes, ordering, generatedAt}`. `inputs` is `{packageFingerprint, projectKey, libraryHash, archetypesVersion, mode}`, a record of what the ideas were made from. The page keeps a matching signature (mode, package fingerprint, workbook hash, project snapshot, workflow and description) and says when any of them has changed since; it never regenerates by itself. The page asks for every catalog idea (up to 100) and shows six at a time.
- **Existing task.** `detectApplicability` reads only solver-visible documents (roles `source`, `template`, `proposal`; the `prompt` document is read only to note wording the request already uses, never as evidence) in one pass over the records. It lists, per archetype with evidence, up to 3 items (at most 2 from one document) of `{documentName, locator, quote (300 characters at most), term, label}` and a strength, `signal` when two different cues matched and `weak` for one. Every anchor is checked again with `FinancePackageEngine.resolveClause` (the exact locator, one record, the quote present) before it is shown. The card shows the exact locator; a build move names a spreadsheet by its sheet and never by a cell reference, because the guidance lint forbids those.
- **Coverage.** `coverage(project, archetypes)` compares an idea with the current roots: the same causal group, or at least three signal hits in one root (the archetype's whole name in a root counts as two), is `covered`; two hits, or one hit with the same mechanism, is `overlap`; the same mechanism alone is `mechanism`, which is weak (the default `period_alignment` never counts) and does not change a status. It also returns `openNetNewSlots` (`SET.netNew` minus the net-new roots; negative when over the limit).
- **Status.** `anchored` (reviewable hypothesis): the package has evidence, or, in a new task, the description itself uses the wording the archetype needs. `needs-evidence` (hold: missing evidence): nothing yet shows the task can hold it. `overlap` and `covered` (overlaps a current mode, already covered) come from the coverage above and also set `overlapWith`. An idea added to the project becomes `covered` by its causal group.
- **An idea** is `{id, archetypeId, title, mechanism, kind, status, statusWords, summary, whyItHolds, buildMoves, wrongApproach, correctTreatment, detection, consequence, applicability, precedents, lowestScoreText, overlapWith, causalGroup, honesty, lead, needs, anchored, strength, described}`. `id` is `idea-` plus a hash of the archetype and the inputs. In an existing task `buildMoves` name the document or sheet the move would touch, only when the whole sentence passes the lint.
- **Order.** Status first (`anchored`, then `needs-evidence`, then `overlap` and `covered` together). With a library: then the lowest recorded score among the idea's displayed precedents, ascending (an idea with no precedent that has a number follows those that have one), then more precedents, then `lead`, then id. Without a library: `lead`, then catalog order. So a recorded score never lifts an idea over a better status, and with a library loaded it outranks `lead`.
- **Precedents on an idea.** At most 3, the three closest by similarity, displayed sorted by recorded score ascending (a row without a number last, ties by id). Each is `{id, workflow, trap, scoreText}`: the score is `scoreText` as recorded, printed after the label "recorded score" (capitalised on the page; a row without one says "not given"). `lowestScoreText` is the `scoreText` of the first displayed precedent that has a number; it orders ideas and is not printed on its own.
- **Never derived.** No mean, median, range, minimum as a headline, share, percentile, band, rescaling, rate or prediction is computed from any score, in the model, the page, a tooltip or a copy. An idea carries no score of its own. `ordering` is three counts (`rows`, `unreadable`, `ordered`), so the page can say when no score could order the ideas; when `ordered` is zero it prints "No closest precedent has a score that is a plain number, so these ideas are not ordered by recorded score." in place of the footnote, and it counts the rows without a readable score.
- **Words of the workbook.** The trap and workflow are shown as a quote. The only changes: a percent sign becomes the word "percent", and the phrases "pass rate", "success rate", "failure rate", "likely to" and "caught" become three dots (`displayText`). The score cell is never touched. All other text on the page (catalog and interface) contains no percent sign and none of those phrases, which the tests sweep.
- **Note on the order.** The ordering footnote prints once per page, only when a recorded score ordered at least one idea, followed by one plain line saying that ideas are grouped by status first.
- **Hand-off.** `toAuthoringProject(idea, {pkg, project})` returns a single-root project that `FinanceCore.parseProject` accepts unchanged, for `FinanceAuthoring.addCandidate(pkg, {id, title, authoringProject})`, the function behind *Add as net-new mode* on the candidate roots page. The root is `lane: 'net-new'` and `reviewStatus: 'pending'`, with `mechanism` and `causalGroup` from the idea, `governingRule` from `whyItHolds`, `facts` (the anchor lines `file locator: quote`, then a labelled paragraph "Build: " plus the build moves), `triggeringCondition` (the first build move), `correctInterpretation`, `wrongInterpretation`, `detectionMethod`, `correctiveAction` and `headlineWrong` from the idea, and `duplicateCheck` as "To confirm: nearest current modes: <Mode IDs and titles>." (a draft, never a claim that the comparison was done). `expectedBehavior`, `classification` and `ambiguity` are left empty, `outputs` is empty (no number is invented), and `sources` holds only anchors that resolve again to one solver-visible record holding the quote, with version `sha256:<document hash>` and `suppliedToSolver: true`. For an idea with anchors, the audit then keeps only the items the author must supply: expected behavior, classification, acceptable variations, tolerance rationale, the correct headline, outputs, the source dates and the reviews. `addCandidate` does not check the five-mode rule or run a duplicate check and resets "addressed" review gates, so the page asks first: the dialog states the five-mode rule (three historical, two net-new), the open net-new slots, any overlap, and the gate reset when there is one. The cap warns; it does not block, and the task editor flags a set of more than five.

### 17.6 Privacy

- The workbook is read with the browser's file input (a hidden `<input type="file" accept=".csv,text/csv">` made with `document.createElement`) and `File.text()`. The parsed rows, labels and hash live in one module variable of `ideas.js`; the module exports only `render`, `afterRender` and `handleEvent`. They are never written to `localStorage`, `sessionStorage` or IndexedDB, to the project JSON or `project.library` (which has a 500-mode cap and is exported), to dashboard state (which is exported in the workspace JSON), to an export, or to any companion route. The page makes no request, so nothing leaves the browser. Reloading, or *Remove workbook*, forgets it; removal also clears the precedents held by the ideas on the page, which stay but are marked as made with a workbook that is gone.
- What reaches the project when an idea is added is the catalog's own text, anchors from the package and mode titles in `duplicateCheck`. No recorded score, no precedent text, no row id and no library hash is written (`tests/ideas-model.test.cjs` sweeps the converted project for each). *Copy as text* leaves the precedents out.
- No file of the workbook, no real row and no recorded score is in the repository, in a test, in a fixture or in a screenshot: every test builds its CSV from invented rows (Atlas, Meridian, Borealis; the browser suite writes it to a temporary folder that it removes afterwards). Keep the person's own file outside the repository, or under `private/`, which is ignored (as is any `*_PRIVATE.*`).

## 20. Pipeline: from a task link to a tested design

The Pipeline page (`pipeline.js`, `pipeline.css`) and the orchestrator (`backend/pipeline/`) chain the steps of sections 3 to 9 into one approved run. The README's *Pipeline* section describes it for the writer. This section is the contract.

1. **Approval.** One `POST /api/pipeline/start` approves the whole run. The answer is `{id}`, `pln-` followed by 12 hex characters.
   - Before it opens a link or makes a folder, start() refuses with 409 when Claude Code is not found. The worst case of one full attempt is the ceiling to the cent of `headroom × (fixedUsd + pilots × (pilotCapUsd + perPilotUsd))`. `GET /api/pipeline` reports the parts of the default mode as `config.minCap` and both modes as `config.minCapByMode` (`new`: `fixedUsd` 20.50, `perPilotUsd` 1.50; `harden`: 8.00 and 1.00, at the default designer cap), and the page shows the figure by the cap field. In the new mode the optional diagnostic suite adds `config.minCapFairnessSetUsd` (3.00) to `fixedUsd`. A lower `capUsd` is accepted, with a warning on the page, and the run ends in `budget` when its next step would not fit. The service option `minCapCheck: true` turns this into a 400 refusal.
   - `capUsd` defaults to 60 and may be up to 200. Only one pipeline runs at a time.
2. **Stages.** `import`, `classify`, `design`, `screen`, `grade-screen`, (`redesign`), `test`, `grade-test`, then `done`, `failed`, `stopped` or `budget`. Every stage is stored in `private/pipelines/<id>/state.json`. After a companion restart, an attempt that was running is marked `failed` with a note.
3. **Import.** From a link through the link loader (section 21), or from a folder outside the project. Both are copied to `private/pipelines/<id>/original/` with a streamed hash. The view's `import` holds the count, the files (name, group, label, size, hash), `groups` (files per group), `skipped` (every file that was not kept, with the reason, including files the loader could not download), `toggle`, `page` and `notes`.
   - `import.notes` are the loader's own notes (from its done state and from `page.json`): a cap it hit, pagination it did not follow, requests still pending, frames it could not read, and so on. Any address in them is replaced by `<link>`; there are at most 50, of at most 500 characters each. A folder's `page.json` may carry the same list.
   - **Confirm the files.** The loader cannot be perfect on a page it has not seen, so after a link import finishes and before any model run (and before any money is spent) the pipeline waits. It stays in the stage `import` with `waiting: {kind: 'confirm-files', message: 'Check the file list against the task page. Press Continue if every file is there, or Stop and use Import from folder.', since}`. `POST /api/pipeline/<id>/continue` ends this wait itself, without calling the loader, and the run goes on to the classifier. Stop ends the pipeline as usual. The wait does not count against the import time limit. A folder import has no such wait, because the owner chose those files by hand. The service option `confirmFiles` (default true) turns the wait off; only the tests use it.
4. **Classify.** One tool-less run returns the prompt, the guideline, the golden answer, the world files, the task files and the files to withhold. The rules after it fail closed:
   - A file whose name, group or label names a golden, reference, model or gold answer, a solution, an answer key, an answer or response file, a rubric, grading or a grader is withheld whatever the model said. A guideline is withheld under the narrower rule of section 19.3.
   - A file is also withheld when its text holds an 80-character window (step 30) of the original guideline or golden answer. Plain text and the text of docx, xlsx and pptx are scanned. Files that cannot be read are listed in `classification.unscanned`.
   - The run stops before the designer in three cases: no golden answer was identified but a file looks like one (the `harden` mode only: a new task has none to name, and such a file is withheld); a world or task file would be withheld (unless `acceptMissing`); or the packet would pass the agent limits (150 files, 100 MB, depth 4).
   - In the new mode the prompt, the guideline and the golden answer may each be `null`; whatever the classifier names is used only to withhold material and to guard its passages, and it is never given to the designer. A withheld file's text joins those passages too. `keepAsWorld` (item 11) is the only exception to the name rules.
5. **Design (the `harden` mode; items 11 to 19 describe the new mode).** The designer is an agent with the pilots' tools, working in `private/pipelines/<id>/designer/`. It reads `task/`, `prompt.txt`, `guideline.md`, `golden-answer.md` and `ideas.txt`, and writes `out/`:
   - new files go under `out/new/`, which is preferred;
   - edited copies of world or task files go under `out/edited/`, each listed with a reason;
   - it also writes `prompt.txt`, `guideline.md`, `golden-answer.md` and `traps.json`.
   `out/`, `out/new` and `out/edited` must be real folders with regular files only. Originals are never changed. The edited copy replaces the original only in the pilots' packet.
   `readDesign` refuses:
   - an edit that shrinks a file by more than a fifth;
   - a guideline more than 1.5 times the original's length without `rubricChanges`;
   - a gold figure missing from the guideline or the golden answer;
   - a figure or decision phrase of the golden answer in the prompt or in a new file's name (when it is not in the original prompt or packet);
   - a trap that lists a file the pilots do not get;
   - a new or edited file that holds a guideline or golden-answer passage.

   Two gates follow:
   - **Calibration.** The golden answer is graded against its guideline and must score at least 0.90.
   - **Fairness.** A tool-less review must list no guideline item that a solver could not know from the prompt and the files. A missing or unreadable answer counts as a failure.

   A failed check gets one repair turn (cap USD 1.00), then rejects the attempt (`outcome: 'rejected'`, `rejection.reasons`), which uses a redesign. A public reason never names a file, a trap or a fingerprint, because a name the designer chose can carry a figure. The exact detail reaches only the repair prompt, `attempts/<n>/feedback.md` and, on a safety stop, the private `error.log`.
6. **Screen and test.** Rounds are made through the agent service with `gafVisible: true`. The pilots' packet is the only copy under `<tmpRoot>/finance-studio-pipelines/<id>/work/filesystem`, and it is checked by sha256 and name before every round. The screen runs first, the test runs only if the screen passed, and each pilot is graded as soon as its run ends, while the others go on.
   - **Bars.** The screen bar is 0.40 (`SCREEN_BAR`): the screen passes only when both pilots score below it. The test bar is 0.45 (`TEST_BAR`; `PASS_BAR` is its old name): the test passes when at least 4 of 5 score below it. `GET /api/pipeline` `config` and each pipeline's `config` carry `screenBar`, `testBar` and, as before, `passBar` (the test's). The designer is aimed at the screen's bar.
   - **Stop as soon as the result is decided.** After each grade the stage asks whether its result is decided, using usable scores only. The screen fails with one score at or above 0.40. The test passes with 4 scores below 0.45 and fails with 2 at or above it. A decided stage cancels the round's pilots that have not ended (`cancelRound`) and does not grade the ones that ended after the decision. Such a pilot is marked `stoppedEarly: true` with a `stoppedReason`. It is not missing, so it gets no replacement. The stage result carries `stoppedEarly: {afterPilot, score}` (`null` when every pilot ran to its end, also when the last score decided it). A cancelled pilot's spend is counted in the ledger: its cost when the run reported one, else its cap, marked `estimated`.
   - **Regrade bands.** A score inside the band around the stage's bar is graded a second time, and the two are averaged and both recorded, before it counts toward a decision: [0.35, 0.45] in the screen (`SCREEN_REGRADE_BAND`) and [0.40, 0.50] in the test (`TEST_REGRADE_BAND`). `regradeBand(stage)` checks a band: two finite numbers inside [0, 1], the first below the second, holding the stage's own bar. An invalid band falls back to the single `REGRADE_BAND`, and a fallback that is not valid for a stage throws when the service is made. `config` carries `screenRegradeBand`, `testRegradeBand` and `regradeBand` (the fallback).
   - **The grader.** The grader reads the final message plus the text of the run's output files (xlsx and docx extracted), up to 59,000 characters, and its effort is at least medium. Pilots are graded while other pilots still run, so the pipeline's grader call (the agent service's grader prompt, one answer per call) sends the prompt on stdin and not on a command line: the agent service's own `graderSim` refuses to run beside a round because its text would be on a command line a pilot could read. The check of the golden answer, before any round, still uses `graderSim`.
   - A pilot without a usable score (discarded, failed, or not gradable) gets a replacement round, unless the result is already decided or a replacement could not change it (`replacementSkipped`). The replacement round is graded and decided the same way.
   - A failed screen or test, or a rejected design, goes to `redesign`, at most 3 times; `feedback.md` says when a stage was stopped early.
7. **Budget.** Before each step, the run reserves the step's worst case times 1.15 and ends in `budget` if spent plus reserved would pass `capUsd`. The fixed caps are: classifier 0.50, designer 5.00, repair 1.00, fairness review 0.25 (`harden`), each grader call 0.50, and, in the new mode, blind review 1.50, reveal 0.50, application check 0.50, adjudication 0.50. A pilot round reserves `count x (pilotCapUsd + 2 x 0.50)` (plus one adjudication, 0.50, in the new mode), so that a round that is stopped early spends less than it reserved. Item 18 gives the reservations of the new mode.
8. **Locks.** While a pipeline runs, `POST /api/agents/rounds/:id/launch`, `/api/agents/grader-sim` and `/api/agents/author-review` answer 409 "A pipeline is running". A grader call refused for its input leaves that pilot without a score; if every call of a step is refused, the step fails.
9. **Redaction.** While any round runs, every pipeline answer passes through `redactPipelineData`. The following become `{withheld: true}` and the answer carries `redacted: true`:
   - the prompt, the guideline, the golden answer, the gold and the fingerprints;
   - each trap's title, files, mechanism, decoy and values;
   - the edited files' names, reasons, diffs, hashes and sizes, and the hashes and sizes of every imported and packet file;
   - the calibration, the fairness review, the guideline diff, `rubricChanges` and every grader reason;
   - in the new mode: the brief and the task type, the answer set and its grades, the permitted alternatives, both review stages (they sit in `fairness`), every adjudication, the counts by class (`lows`), the list of unexplained lows, the guideline repair and the recount, the diagnostic answers, the replaced pilot values (`previous`), and the names and file records of the reference documents (their count stays).
   - every rejection reason, and the stage message, summary and error when they quote one (`quotesRejection: true`).

   `POST /api/pipeline/:id/export` answers 409 while a round runs. Otherwise it returns `<label>_pipeline_PRIVATE.zip` with the exported design and a README that names its attempt.
10. **Cleanup.** Every end removes `<tmpRoot>/finance-studio-pipelines/<id>/`. At startup, leftover folders of known pipelines are removed and unknown folders are left alone. Stop and the import timeout wait up to 10 s for the link loader to close its browser before the stage ends.

11. **A new task (`designMode: 'new'`): inputs.** The designer's folder holds `task/` (the world and task files the pilots would get), `ideas.txt`, `reference/` when there are reference documents, and, on a redesign, `feedback.md` and `previous/` (its own last design). It holds no `prompt.txt`, `guideline.md` or `golden-answer.md` of an earlier task. Everything answer-like, rubric-like or guideline-like stays withheld from the designer and the pilots (fail closed), whatever the classifier said.
   - **`keepAsWorld`** is a list of up to 50 file names from the owner. A listed file is a world file: it goes to the designer and the pilots, the agent service is told to override its name rule for it, the packet check lets its name through (its bytes are still compared with every withheld hash), and the view records it (`config.keepAsWorld`, `import.keepAsWorld[]` with `present` and a `warning`, `classification.keptAsWorld[]`). A file that holds a long passage of the withheld material is withheld whatever the owner said. `acceptMissing` still only silences the missing-file stop.
   - **`referencesDir`** names a folder of reference documents. When it is left out, `<root>/private/references` is used if it exists (`private/` is ignored by git, so the documents are never committed), and `false` means none. The folder is checked at start: `.md .txt .pdf .docx .xlsx .csv .json`, at most 20 files and 8 MB in all, at most two levels deep, regular files only, no links, nothing hidden or outside the folder, or the start is refused with 400. The files are copied once (streamed, hashed) to `private/pipelines/<id>/references/` and from there to `designer/reference/` for each attempt. `GET /api/pipeline` reports the default folder as `config.references.default` (`exists`, `found`, `names`, `bytes`, `problems`, `problemList`) and the limits. `problems` stays a count; `problemList` is an array of at most 20 short plain sentences, each naming the file or the folder and the reason (for example `The reference folder holds 21 files; the limit is 20`), cut to 200 characters and never holding a word of a file. The view's `references` holds `source` (`default`, `folder` or `none`), `found`, `names`, `bytes`, `files` (name, size, sha256), `unscanned`, `partial`, `scannedChars` and `truncated`. Names are withheld while a round runs.
   - **The leak guard** runs the 80-character window of step 30 over the text of every reference that can be read against the prompt and against every new and edited file of any kind: plain text, the text of a Word, Excel or slide file, RTF, a file with no extension and the rest, whether the windows of the references are one set (a large folder) or a list. It covers the whole folder (the scan cap, `referenceScanChars`, is 12 million characters, which is more than the 8 MB the folder may hold). A text the cap cut short, or left out, is named in `references.unscanned`, and `references.partial` names those that were scanned in part; `truncated` is then true. A reference with no readable text (a PDF) is in `references.unscanned` too. The sha256 of every reference file joins the withheld hashes, so a byte for byte copy of one (a PDF, say) is refused in `readDesign` and by both `verifyPacket` calls as a copy of withheld material; a task with no references adds none. The repair turn is the same as for any other leak, and the public reason says only that a file holds a long passage of the reference documents (the designer is told which file).
12. **The brief.** The designer also writes `out/brief.json` and, for each permitted alternative, `out/answers/alt-N.md` (at most two). The brief holds `taskType`, `decision`, `files` with roles (`authority`, `evidence`, `decoy`, `baseline`), at most three `traps` with exactly one primary (rule file and clause, correct and wrong path with action and figures, `changesDecision`, why it is tempting, its consequence, the strongest alternative and the clause that rules it out), `permittedAlternatives` (with a reason when empty) and `controls`. `readDesign` checks, without a model:
   - every field, role and kind; the files exist in the packet or in `out/new`; no evaluator file (`guideline.md`, `golden-answer.md`, `brief.json`, `traps.json`, `answers.json`, anything under `answers/`) is listed as pilot-facing; the trap ids are those of `traps.json`;
   - the wrong path changes a required conclusion (the actions differ after folding case and punctuation) or a required calculation (a figure differs by more than the larger tolerance), and `changesDecision` is not `neither`; arithmetic movement alone does not satisfy a conclusion, and a different action with the same arithmetic does;
   - with more than one trap, controls for the baseline, each single wrong path and the combination, each different from the baseline in its action or beyond tolerance; figures are matched by label, so a figure that is relabelled or has no partner in the baseline does not count as different;
   - the clause of each rule is found word for word (white space and typography folded, case kept) in the named packet file or the prompt, and the quote that rules the strongest alternative out is found in an authority or evidence file or the prompt. The floor of such a quote is `MIN_CLAUSE_QUOTE_CHARS` (40) characters, or, when shorter, a whole sentence of at least `MIN_SENTENCE_QUOTE_CHARS` (20); a quote is held to the file it names, a name that is not a file of the packet fails it, and the rest of the packet is not searched instead;
   - `decision.decisionDate` is optional; when it is given it is an ISO date that exists (the day the decision of the task is taken);
   - a workflow that no readable reference text mentions is a warning in `design.notes`, not a failure.

   A failure goes through the repair turn and then rejects the attempt. The brief and the alternative answers are evaluator material: their hashes are withheld, their texts join the leak windows, and they are exported but never given to a pilot or to the blind reviewer.
13. **The reviews.** After the design reads and the answer set (item 14) passes, and before any pilot:
   - **Stage 1, the blind review.** A run with the Read, Glob and Grep tools, effort medium, cap USD 1.50, in `<tmpRoot>/finance-studio-pipelines/<id>/runs/review-<attempt>-<round>-<try>/`, which holds a copy of the packet built exactly as the pilots' (`filesystem/`) and `prompt.txt`, and its own scratch folder. It is told nothing else. Its tool calls are audited like a pilot's, and a violation (a read outside the folder, `/proc/<pid>/fd/0`, the network) discards the run. It answers with the best-supported answer, the governing document and why, and the strongest different answer. An unusable or discarded run is repeated once, then the attempt is rejected.
   - **Stage 2, the reveal.** One tool-less call (cap USD 0.50) gets the prompt, the guideline, the golden answer, the brief, the stage 1 answer and the packet text, and answers with the strongest alternative, a quote for it and one against it, an objection class (`overlooked_dependency`, `permitted_discretion`, `missing_requirement`, `conflicting_authority`, `inaccessible_evidence`, `rubric_requirement_absent_from_packet`, `equivalent_result`, `none`) and a disposition (`excluded_by_clause`, `permitted`, `equivalent_result`, `unresolved`, or `no_alternative` with class `none`). The harness looks for each quote in what the reviewer was shown of the packet (and the prompt), held to the file it names and to the floor of item 12: an `excluded_by_clause` without its against-quote, or a `permitted` without its for-quote, is `unresolved`. An objection class that names a missing requirement (`missing_requirement`, `conflicting_authority`, `inaccessible_evidence`, `rubric_requirement_absent_from_packet`) makes the review `unresolved` whatever disposition it gave, `permitted` and `equivalent_result` included. When the blind reader reached a different answer (a different alternative, or another document as the one that governs), `no_alternative` is a contradiction and is `unresolved` unless the review quotes a clause against that answer (which then goes to the application check), and `equivalent_result` needs its for-quote. A second model agreeing with the golden answer settles nothing.
   - **Stage 2b, the application check.** Mandatory for every `excluded_by_clause`, for a `permitted` that is settled without a repair, and for the rule and the strongest alternative of every trap of the brief, not only the primary one (a repeat of the same clause and alternative is not run twice). One tool-less call (cap USD 0.50) must answer with quotes: which scope sentence covers this decision (and, for a policy and a procedure, which document is higher and whether the lower one implements or varies it; a lower document that varies the higher fails), the effective date and the decision date as ISO dates, each with the quote it stands in, how each hit of supersession language changes the clause, and how the clause's words rule the alternative out. The harness verifies every quote, compares the dates itself (effective on or before the decision date; a missing or unparseable date fails; each date has to be one of the dates its quote holds, and when the brief gives `decision.decisionDate` the reviewer's decision date has to be that day), fails a hierarchy whose relation is not `none` or `implements` or has no quote (fail closed), finds the supersession hits itself (`supersede`, `replace`, `amend`, `rescind`, `retire`, `no longer`, `withdrawn`, `revised`, `effective from` and the like, within 300 characters of the clause's document name with or without its date, its section number or its first words) and fails the check if a hit is not addressed or changes the clause. A packet file with no readable text is listed as a hit of kind `unreadable` (ids `u1`, `u2`), which the reviewer has to address too and which `unscanned` names; passages beyond the first 40 are counted in one last hit of kind `more`, never dropped. The packet is shown to each reviewer by `packetView`: the authority file, the files the brief lists as authority or evidence and the files its rules name come first and may use three fifths of the cap, the other files share the rest, and a file that is cut ends with a marker that says so; the quotes are held to exactly what was shown, and the files that were cut are named in `fairness.stage2.cut`.
   - **What follows.** `no_alternative` and a verified `excluded_by_clause` pass. `equivalent_result` is accepted; when the guideline lacks it, one repair turn adds a line to the acceptable variation, and a repair that changes the packet sends the design through stage 1 and the reveal again (a second change with no review left rejects the attempt: "The repair changed the packet and there is no review left"). `permitted` is not a rejection, but it is not settled by `guidelineCovers` alone: it is settled when the design has a permitted alternative with an answer file, the guideline grades each such answer at `ALTERNATIVE_MIN` or more, and the review says the guideline covers it. Otherwise one repair turn (cap USD 1.00) adds the alternative to the acceptable variation, writes `out/answers/alt-N.md` and updates the brief. The harness then checks that something changed, that an alternative with an answer file now exists and that `guideline.md` changed (when the guideline did not already cover it), and rejects the attempt with "The repair did not write an answer for the permitted alternative" or "The repair did not add the permitted alternative to the guideline" when that is missing; the answer set is graded again and the reveal runs once more (stage 1 only when the packet changed). A second reveal that reports the same alternative resolves when the revised guideline now covers it and its answer scores `ALTERNATIVE_MIN`; otherwise the attempt is rejected ("The reviews found an answer that the packet allows, and the guideline does not yet accept it with a graded answer"). `unresolved` and the classes that name a missing requirement get one repair turn; if the packet changed, stage 1 and the answer set run again; the reveal runs once more. At most two reveals and two repairs per attempt. Still unresolved, or a repair that changed nothing, rejects the attempt with `rejection.kind: 'review'`. What a repair changed is found by hashing `out/` before and after: the prompt, `new/` and `edited/` are the packet, everything else is evaluator material.
   - The record is `attempt.fairness`: `{status: 'pending' | 'passed' | 'rejected' | 'incomplete' | 'not-reached', stage1: {state, tries, runs, packetSha256, discarded?}, stage2: {disposition, objectionClass, evaluations, application, briefApplication, cut}, repairs}`, where `application` is `{pass, failed, checks, dates, hits, unscanned}` and `briefApplication` is `{pass, count, failures: [{trap, part: 'rule' | 'whyRejected', failed}], unscanned}` (`count` is the number of clauses checked, `trap` the number of the trap from 1). It is kept apart from `attempt.difficulty` (`{status, screen, test}`: passed, explained, belowBar, of, need and the counts by class). The detail (the blind answer, the reveal, the application checks) is `attempts/<n>/fairness.json`; the blind reviewer's transcript is `review-<round>-<try>.transcript.jsonl` in the same folder, and `private/pipelines/` is the only place it is written.
14. **The answer set (mandatory).** The golden answer (at least `GOLDEN_MIN` 0.90) and each permitted alternative (at least `ALTERNATIVE_MIN` 0.85) are graded against the guideline by the pipeline's own grader (effort at least medium, the grader model). Each answer is graded twice; two grades on the same side of the threshold decide, two that straddle it get a third and the majority decides, and the answer is marked `unstable: true` with all its grades. A grade that is null or refused is asked for once more; a second one fails the check. An answer below its threshold rejects the attempt with `rejection.kind: 'answer-set'`, as a defect of the guideline or the golden answer, before any review or pilot. After any guideline revision inside the attempt (a review repair, the guideline repair of item 15) the same fixed answers are graded again with the same rule, and the old and the new grades are kept side by side: `attempt.answerSet = {goldenMin, alternativeMin, answers: [{name, kind, file, threshold, sha256, score, grades, passed, unstable, runs: [{why, guidelineSha256, answerSha256, grades, score, passed, unstable}]}], passed}`. The optional diagnostic suite (`fairnessSet: true`, up to USD 3.00 per attempt) grades the six answers the designer lists in `out/answers.json` once each: a `high` answer must reach 0.85 and a `low` one stay under the screen bar, or the attempt is rejected with `rejection.kind: 'diagnostic'`; the result is `attempt.diagnostic`.
15. **Explained lows (the pass rule of the new mode).** After a pilot is graded, a score below its bar gets one adjudication call (cap USD 0.50, effort at least medium, tool-less) with the answer and its output text, the grader's reason, the guideline, the brief, the packet text and a deterministic hint (does the answer match a fingerprint or the wrong path's figures; the hint never counts by itself). The class is one of:
   - `intended`: counts when the quoted adopted action and the quoted rationale are both found in the answer text and the call says how they match the brief;
   - `other_valid_error`: counts when the guideline item is named, the packet clause it violates is found word for word (held to the file it names and to the floor of item 12), the action the answer took (`adoptedAction`) is found word for word in the answer, and the application check (item 13) passes for the clause with that action as the alternative it must rule out;
   - `permitted_alternative`, `grader_defect`, `ambiguous`, `unsupported`: do not count; an adjudication that cannot be read twice is `unsupported`, and a claim the harness cannot back is demoted to `unsupported`;
   - `tool_failure`: the pilot becomes a missing one (no usable score) and the usual replacement round follows.

   A pilot has `adjudication: {class, claimed, counts, note, application}` and `countsTowardPass` (true, false, or null before the call). The screen passes when both pilots count and the test when at least four of five count; a stage ends as soon as this is decided, a score at or above the bar and an unexplained low being pilots that do not count. While the guideline repair is still open, a low whose class puts the fault in the evaluator material (`permitted_alternative`, `grader_defect`) does not end a stage early, so that every answer exists to be graded again. The stage carries `explained`, `lows: {lowScorers, intended, otherValid, permittedAlternative, graderDefect, ambiguous, toolFailure, unsupported, counted}` and `unexplained: [{pilot, class, score}]`.
   - **The guideline-only repair.** When a stage fails and some low is `permitted_alternative` or `grader_defect`, one repair turn (cap USD 1.00, once per attempt) may change only `guideline.md` and `golden-answer.md`. A repair that changes anything else (the hash of every other file of `out/` is compared), changes nothing, no longer reads as a design, or leaves a fixed answer under its threshold is not used: `out/` is restored from the attempt's copy and nothing is run again. Otherwise the answer set is graded again, the saved answers of the stage are graded again (calls with the reference `<round>#<run>-regrade`; no new pilot), every low except an `intended` one is adjudicated again against the revised guideline, a second freeze record is written, and the stage is counted again (`stage.recount`, `attempt.guidelineRepair = {stage, outcome, classes, changed, regrade, recounted, ...}`).
   - **Reruns follow what changed.** Evaluator material only: saved answers are graded again. The prompt, a file of the packet or the mandate: fresh solves (a redesign). Nothing material: nothing is run. Failures from `ambiguous` or `unsupported` lows go to a redesign whose `feedback.md` carries each pilot's score, class, grader's reason and final answer, and says that the traps may not be what is making these pilots fail.
16. **The freeze record.** Each attempt of the new mode records `attempt.freeze[]`: `{n, at, reason, packetSha256, packetFiles, promptSha256, guidelineSha256, goldenSha256, answerSetSha256, answers: [{name, sha256}], pilot: {model, effort, capUsd}, grader: {model, effort}, budget: {totalCapUsd, designCapUsd, pilotCapUsd}}`, once before the pilots (`reason: 'before the pilots'`) and once after a guideline repair. The packet hash is the sha256 of the lines `name`, `sha256` and `bytes` separated by tabs, one per packet file in name order, and the packet the pilots get must equal the packet the blind reader read, or the run stops on a safety error. Each record is also `attempts/<n>/freeze-<k>.json`. The export README prints them, and the export carries `packet-manifest.json` and `SHA256SUMS.txt` (the sha256 of every other file it ships) so that the packet that was tested can be compared byte for byte with what was shipped.
17. **Isolation.** "Isolated" means the run is given none of the designer's information: its conversation and logs, the reference documents, the brief, the guideline, the golden answer, any grading guidance, the answer set and inherited project or user memory all stay out. A pilot still gets the fixed pilot text, the prompt and the packet.
   - **What is checked.** `isolation.cjs` `isolationProblems({args, env, cwd, tmpRoot, projectRoot, homeDir, forbiddenText})` looks at what a run is started with: the options `--strict-mcp-config`, `--disable-slash-commands`, `--no-session-persistence` and an empty `--setting-sources` are present (the pre-flight already refuses a Claude Code whose `claude --help` lacks one of them); none of `--resume`, `--continue`, `--add-dir`, `--mcp-config`, `--plugin-dir`, `--settings`, `--agents`, `--append-system-prompt`, `--system-prompt` and similar is given; `CLAUDE_CODE_DISABLE_AUTO_MEMORY` and `CLAUDE_CODE_DISABLE_CLAUDE_MDS` are `1`; the configuration and scratch folders are inside the working folder; no value names `<root>/private`; the companion's `FINANCE_STUDIO_PILOT_TOKEN` is not passed; and the working folder is under the temporary root and never under the project or the home folder. The pipeline runs it before every blind, reveal, application and adjudication run (`models.cjs`, option `isolated`) and does not start a run that fails it; the tests run it over every process the stub records, pilots included. The reveal-side reviews run in `<tmpRoot>/finance-studio-pipelines/<id>/runs/`.
   - **Logs.** The blind reviewer's and the pilots' transcripts, evidence copies and prompts hold no reference text (the tests plant a marker in a reference and look for it in every pilot round folder, every reviewer transcript, every prompt, argument list, environment and working folder other than the designer's). The designer's own transcript is under `private/pipelines/<id>/attempts/<n>/`, which no route serves, and a pilot that reads it is flagged by the path audit.
   - **Not enforced by the installed CLI.** The checks above cover the arguments and the environment the Studio gives. They do not make the CLI a sandbox. The path audit is after the fact: a read of `/proc/<pid>/fd/0` (another process's open input), `/dev/stdin` or `/dev/fd/N` is flagged as `abs` and discards the run, but it was not prevented. Every run shares the account's sign-in (`CLAUDE_SECURESTORAGE_CONFIG_DIR`), the network and shell rules are the audit's, and a program the run starts is seen only by the text of the call.
18. **The budget and the incomplete result.** Before an attempt starts, the pipeline reserves `attemptReserveUsd` (the designer, its repair turn, the blind review and the reveal twice, the application check seven times (the reveal's clause and, for up to three traps, the rule and the strongest alternative of each), two review repairs, three grades of each of the golden answer and two alternatives, and one adjudication for each of the seven pilots; USD 23.50 at the default designer cap) with the 1.15 headroom on top (USD 27.03). A cap that cannot pay stops the run before a designer is paid for: `stage: 'budget'`, `result: {verdict: 'incomplete', validation: 'incomplete'}`. A stop (budget, Stop, or an error) while an attempt's mandatory checks are unfinished leaves `attempt.validation: 'incomplete'`; a stop after they finished is an ordinary `budget` with `validation: 'complete'`. A pass needs `attempt.validation: 'complete'`, and a run that would pass without it ends as incomplete instead. `config.minCap` for the new mode is `fixedUsd` 20.50 (classifier 0.50, designer 5.00, one repair 1.00, blind review and reveal twice, seven application checks, two repairs, nine grades) and `perPilotUsd` 1.50 (two grades and one adjudication); a full attempt at the default pilot cap needs USD 59.80, which the default total cap of USD 60 pays for with USD 0.20 to spare (with the diagnostic suite USD 63.25; `harden`: USD 41.40). A second pass of the reviews, a regrade and a guideline repair beyond these are reserved when they are needed and end the run as incomplete when the cap cannot pay.
19. **What the view carries (designer v2).** `config.designMode`, `config.keepAsWorld`, `config.fairnessSet`, `config.references.default.problemList`; `references` (with `unscanned` and `partial`); `import.keepAsWorld[]`; `classification.keptAsWorld[]`; in each `attempts[]` entry of the new mode: `mode: 'new'`, `validation` (`pending`, `complete`, `incomplete`, `failed`), `fairness`, `difficulty`, `answerSet`, `calibration` (the golden answer's last mean grade), `freeze[]`, `guidelineRepair`, `diagnostic`, `taskType`; in each stage: `explained`, `lows`, `unexplained`, `recount`; in each pilot: `adjudication`, `countsTowardPass`, `toolFailure`, `regraded` and `previous`; in `design`: `taskType`, `brief`, `alternatives`, `answerSet`, `freeze`; in `result`: `validation`. Every one of these may be `{withheld: true}` while a round runs (item 9).

## 21. Link loader

`backend/links/` is part of the companion and calls no model. `createLinkLoader({root, chromePath, spawnFn, clock, headless, signIn, timeouts, limits})` returns `start(url) -> id`, `get(id)`, `continue(id)`, `cancel(id)`, `waitFor(id)` and `shutdown()`, and throws `LinkError` with `.status` and `.code`.

1. **Chrome.** It uses a dedicated profile in `private/link-profile/`, with mode 0700, and the first Chrome or Chromium found from `FINANCE_STUDIO_CHROME`, `CHROME_BIN`, the `Applications` folders (macOS) and the usual Linux binaries. The profile is seeded so that downloads are refused before the first navigation and sign-in to the browser itself is off.
   - Chrome is driven over `--remote-debugging-pipe` rather than a debugging port, with an environment allow list, in an isolated world and without `Runtime.enable`.
   - The link and its query reach Chrome only through the pipe. They are never on a command line, in a log, in the state or in `page.json`.
2. **Sign-in** (`signIn: 'window'`, the default). When the page asks for a sign-in, the loader closes its Chrome and opens a plain Chrome on the same profile with only the site's origin. The owner signs in there and presses *Continue*, or closes that window. The loader stops the window (SIGINT, then SIGTERM, then the process group, because only SIGINT makes Chrome write its session cookies), relaunches on the pipe and opens the full link. If the page still asks, it repeats once, then fails with the folder-import hint. `signIn: 'piped'` keeps one controlled window instead.
3. **All files.** The loader finds the platform's show-all-files switch by label, role or a learned key, and turns it on. The label or key is stored per host in `private/link-mappings.json`. If no switch is found, the state is `needs-person`, with the message "Turn on the option that shows all files in the Chrome window, then press Continue."
4. **Expansion.** Before the final snapshot, it opens details and aria-expanded expanders, up to 4 passes until nothing new opens. It repeats this after the switch, after the person step, after a reload and in every tab. It also presses *Load more*, *Show more* or *View more* in every tab, scrolls long lists, and covers open shadow roots and same-origin frames. A step cut off by its time budget is reported in `notes`. Snapshots are unioned and re-taken until two in a row agree. A page that kept changing is reported as `settled: false`.
5. **Downloads, by allowlist.** Files are saved to `private/links/<id>/files/` with mode 0600, and the page text to `page.json`. The loader requests or presses only these:
   - an `<a>` whose path ends in a known file extension, or whose last segment is exactly `download`, with no action word in any directory of the path and none in a query parameter;
   - an `<a download>` whose address passes the same test;
   - a control named as a download ("Download", "Download all (12)", "Download Q3.pdf", an icon titled Download) that is not in a form and cannot submit;
   - for exposing content only: tabs, `<details>`, aria-expanded expanders and tree items, *Load more*, *Show more*, *View all*, pagers, and the show-all-files toggle. The toggle's label must say show or view all (or every, or world) files, attachments or documents, and must contain none of clear, delete, remove, reset, archive, move, apply, bulk, select all, share, send, upload and the like.

   Every press re-checks the live element against its kind's rule. Every press the loader makes runs under a write guard, which lasts until the page settles: tabs, expanders, *Load more*, pagers, the toggle and downloads.
   - The guard lets GET, HEAD and OPTIONS through, plus a POST whose body is a GraphQL query with no mutation or subscription.
   - Everything else is failed in the browser before it leaves.
   - A blocked control is not pressed again. Its note reads "The page tried to save a change when '<label>' was pressed; it was blocked".
   - A tab or pager that is a link must stay on the same origin and pass the address rules.
   - A pager needs navigational evidence: a nav or pagination container, or links that change only a page parameter.
   - A toggle inside a form that posts, or one that submits on change, is never pressed.
   - Permission and visibility words (access, permission, public, client, edit, role, default and the like) also rule out a toggle.

   Anything else that names a file is listed in `skipped: [{label, group, reason}]`, with the reason "not clearly a download: download it yourself", "looks like an action", "would submit a form" or "the button is disabled". This covers a file name used as link text with an address such as `/documents/42`.
   - Each file is identified by its name cell, its group, its tab and its address, so identical *Download* buttons stay distinct. Before each click, the page is put back in the view the file was seen in.
   - A click that started no download is listed and not pressed again. A failed download moves the state to `needs-person`.
   - Every place the loader could not fully cover becomes a sentence in `notes`, which the pipeline shows on its *Check the files* card. That includes:
     - a cap hit (50 tabs, 50 *Load more* controls, 2000 buttons or links);
     - pagination it did not follow;
     - a scroller it could not bring to its end;
     - a *Load more* still on the page;
     - a closed dialog that names files;
     - a frame from another site;
     - a request that never answered.
6. **States.** `starting`, `loading`, `needs-sign-in`, `needs-person`, `downloading`, then `done`, `failed` or `cancelled`. A cancel shows "Cancelling..." until Chrome is closed and the profile's history scrubbed. Closing the task window ends the load with "You closed the Chrome window before the load finished. Start again." When the profile is already in use, the message is "Quit the loader's Chrome (Cmd+Q) and try again."

Not verified: real macOS Chrome behaviour (the Dock, Cmd+Q, finding the `.app` bundle, the synced-folder warning) and a human signing in to the real platform. The browser suite drives a real headless Chromium against local fixture pages, including a sign-in with a two-step check, and plays the person with a second headless Chromium.
